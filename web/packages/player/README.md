# @cha/player

The browser side of a session (plan §6.1). Framework-agnostic: give it a `<video>` element and a function that carries a WebRTC offer to the environment. In the portal, that is `POST /api/environments/{id}/connect`.

```ts
const player = new Player({
  video,
  signal: async (offer, codec) => (await api.connect(id, { codec, offer })).answer,
});
await player.connect();
```

- **Transports.** `transport: "auto"` (the default) takes WebTransport where the browser has WebTransport, WebCodecs and track generators (Chromium), and falls back to WebRTC. Pass `webTransport` (the portal's URLs and certificate hash) to allow it.
  - **WebTransport** (`wt-worker.ts`): `cha-stream/1` datagrams reassembled in a worker, frames handed over in order from a keyframe or recovery frame; WebCodecs decodes into track generators feeding `<video>` and `<audio>`.
    - **FEC** (`fec.ts`, the Reed-Solomon code of `cha-proto::fec`) rebuilds a frame's lost fragments from its parity as soon as enough are in.
    - **Lost frames:** a frame still incomplete once a later one has completed (15 ms on), or once nothing of it came for 250 ms, is lost, and the worker resyncs (below). A browser busy for a moment delivers late but in order, so that costs nothing.
    - **Resync:** after a loss the worker drops frames until a keyframe, or a recovery frame that answers the loss. It sends `{"t":"rfi","id":N}` on the control stream (N the first lost frame's id), so the streamer encodes the next frame around the loss rather than as a keyframe. If the recovery frame is itself lost (overtaken by later frames, or silent for 250 ms) it asks again at once, and if nothing comes 250 ms after asking it asks for a keyframe. H.264 and AV1 decoders show a missing reference as garbage with no error (S8), so nothing else is fed past a loss.
    - **Reports:** every 100 ms the worker reports to the streamer's rate control: send → complete (the median of 150 ms), what arrived (200 ms), and the share of datagrams that never did. A frame's datagrams count for 200 ms after its first, so ones FEC made unnecessary, or that came reordered, aren't counted lost. The worker sends them because its timers keep running when the page is hidden.
  - **WebRTC:** recvonly video and audio tracks; the streamer stamps playout-delay 0 on video. The node streams straight to the browser, while the portal only brokers the offer and answer, with a 60 s media token.
    - **Reports:** every 100 ms the page sends the streamer's rate control the same report the WebTransport worker does, over the control DataChannel. Send times come from the RTP timestamp, and the delay is the lower quartile of presented frames' (retransmissions delay some frames, a queue all of them).
    - **Resync:** when frames stop decoding for 300 ms while data still arrives, the page asks for a keyframe rather than wait on retransmissions.
- **Codec.** The best this browser can receive, in the order measured on the baseline (P1.3): HEVC, then H.264, then AV1.
  - **`switchCodec()`** changes codec in place over WebTransport: a decoder for the new codec is ready first, and the picture stays up until the new stream's first frame (gaps under 35 ms). Over WebRTC, or when the streamer doesn't answer within 3 s, it reconnects.
  - **PyroWave** (`pyrowave420`, `pyrowave444`; `pyro.ts`): the LAN tier, over WebTransport only, where WebGPU has subgroups (`supportsPyroWave()`). Frames are intra-only, so the worker hands over every frame, partial ones at the deadline, and never waits for a keyframe. `@cha/pyrowave-webgpu` decodes into an offscreen canvas; each frame becomes a VideoFrame for the same track generator as WebCodecs.
- **Input** (`input.ts`) goes up the `control` DataChannel.
  - **Pointer:** absolute positions on the picture. With `lockPointer()`, raw relative motion scaled to stream pixels, for games.
  - **Keyboard:** keys by `KeyboardEvent.code`. Held keys and buttons are released on blur, so nothing sticks. On a Mac, ⌘ goes as Ctrl (`commandAsControl`), so the Mac's shortcuts work in Linux apps. The keys of a ⌘ chord are released with ⌘, since macOS sends no keyups for them.
  - **Floor:** one page has the controls (`onFloor(control, viewers)`); a watching page sends no input or resizes, draws the controller's pointer over the picture when the picture doesn't show it, and can ask for the controls (`takeControl()`).
  - **Cursor:** in desktop mode the environment's cursor is the element's CSS cursor (a CSS keyword, or the app's image through `image-set()` at the stream's scale), so it moves with no stream delay. With a locked pointer the picture has it.
  - **Clipboard:** on Ctrl/⌘+V the V is held back until the browser's own paste event (no permission prompt) supplies the device's clipboard, which goes up first. Text an app copies arrives as a control message and is written to the device's clipboard (`onClipboard` says whether that worked or waits for the next click).
  - **Mouse capture:** `lockPointer()` captures the mouse (raw motion on Chromium). When the browser releases it (Esc), a click on the picture captures it again and is not sent to the app; `onMouseCapture` reports `recapture` and a `hint` ("Click to capture the mouse", hidden after 4 s idle), and `turnOffMouseCapture()` leaves that mode. In Chromium full screen with the mouse captured, Keyboard Lock sends every key, Esc and ⌘W included, to the stream; holding Esc is Chrome's own exit (`keyboardLocked`). State machine: `captureMode.ts`.
  - **Fallback:** events with no physical key (on-screen keyboards) map unshifted US characters. Full text input comes with the text-input protocol.
- **Sound.** Stereo Opus, 10 ms frames, NetEq kept at its minimum, in its own MediaStream so video is never held back for lip sync. Over WebTransport the packets go through a small adaptive playout buffer (`audio-jitter.ts`, pure and unit-tested) before the decoder:
  - **Order:** packets play in id order; a duplicate, or one that arrives after its slot was passed, is dropped. A packet that never comes is concealed with 10 ms of silence when its slot arrives (WebCodecs' `AudioDecoder` doesn't expose Opus PLC), so the sound doesn't stall. One more than 50 ms past its slot is dropped to catch up rather than queue in the sink, and a gap over 100 packets (a stall, or the streamer restarting its count) is skipped with no silence.
  - **Delay:** a packet's slot is its send time + the smallest transit of the last 10 s (so the two clocks' offset cancels) + the delay. The delay is the p99 of the queueing over the last 5 s, clamped to 0–80 ms: it rises at once and falls 2 ms per second. On a quiet LAN the p99 is under 1.5 ms, the delay is 0, and a packet plays the moment it arrives (click → sound stays at WebTransport's 55 ms). It is `audioJitterMs` in the stats, as on WebRTC (where it is NetEq's).
  - **Arrival** is stamped in the worker (`at` on the `audio` message), so the main thread being busy doesn't count as network jitter. Browsers play sound only after a click or key press; `onAudioBlocked` says when it's waiting, `setMuted()` turns it on or off, and `volume` / `setVolume()` set its level (0..1) on this page.
- **Setup status** (`onStatus(status | null)`): what the app's long first-run setup is doing while its picture may still be black, such as Steam's 500 MB download. `status` is `{ label, done?, total?, unit? }`, and with no `total` the progress is indeterminate. `null` means there is nothing to show; a page starts there. Every session gets it, watching ones too, and a page that joins midway is told the current status at once. The app writes it to `/run/cha/status` (`images/README.md`); the streamer sends it as `{"t":"status",…}`, with no `label` once cleared.
- **Controllers** (`controllers/`): a manager over two backends, sending each pad to the streamer in a slot 0–3, where it becomes the virtual controller the user chose for the app (Xbox 360, DualSense or Steam Controller; `docs/controllers.md`). Unfocused, pads are released.
  - **State** is always the standard layout: 17 buttons (0..1; the triggers are 6 and 7, analog) and 4 axes (LX, LY, RX, RY), whatever the physical pad is, then the extras 17–23 (`EXTRA`): touchpad click (a DualSense's, or a Steam Controller's right trackpad's), left trackpad click, back paddles or grips L4 and R4, L5, R5, and mute or quick access. A pad without one leaves it released. Some backends add `gyro` (rad/s, x pitch, y yaw, z roll), `accel` (m/s²), `touch` (the fingers on a pad, only those touching: a Steam Controller's left trackpad is id 0 and its right one id 1, a DualSense's finger slots are 0 and 1) and `battery`.
  - **Gamepad API** (`gamepad-api.ts`): polled at 250 Hz; pads appear after their first button press. Rumble through `vibrationActuator`. macOS keeps some Bluetooth pads from the browser, and Steam Controllers sit in a vendor HID collection, so neither shows up here.
  - **WebHID** (`webhid.ts`): Chrome and Edge only, and only on a secure page (HTTPS, or `http://localhost`; a plain-http LAN address has no `navigator.hid`; `hidUnavailableReason()` says which). The user grants each device once in the browser's picker, which a click has to open (`connectHidController()`); granted devices reopen on their own. A device opens in one tab at a time. Drivers:
    - **Generic HID gamepad** (`hid-generic.ts`): built from the report descriptor WebHID exposes: Generic Desktop axes and hat, the Button page, Simulation Controls accelerator and brake as triggers, report ids, signed ranges and the hat's null state. By usage it maps to the standard layout (an Xbox-style layout by default); `hid-quirks.ts` holds per-VID/PID overrides, so far only a placeholder for 8BitDo (unverified until someone checks a real pad's raw view).
    - **Steam Controller, original** (`steam-controller.ts`; wired, dongle and Bluetooth): turns lizard mode off with the feature reports SDL sends, reads sticks, the pads (also as `touch`, with their clicks), the grips, gyro, accelerometer and battery, and restores lizard mode on close. No rumble: the controller has no motors, but a haptic pulse plays on its trackpads (feature report 0x8F).
    - **Steam Controller, 2026** (`steam-triton.ts`; wired, Bluetooth, puck, receiver): lizard mode off (resent every 3 s, as its watchdog expects), buttons (grips and quick access among them), sticks, triggers, both pads, gyro, accelerometer, battery, and rumble through its output report; a haptic pulse plays on its trackpads (output report 0x81; SDL defines it but never sends it, so the side encoding is assumed), and both pad clicks are read. A puck or receiver shows a controller only once one is awake behind it.
    - **DualSense and DualSense Edge** (`dualsense.ts`; USB and Bluetooth): sticks, triggers, buttons, gyro and accelerometer (calibrated with feature report 0x05, which over Bluetooth is also what turns the full reports on), the touchpad's two fingers, battery, and the extras (touchpad click, mute, the Edge's paddles as L4/R4 and function buttons as L5/R5). It drives rumble, the lightbar, the player LEDs and the adaptive triggers through output report 0x02 (USB) or 0x31 (Bluetooth: sequence, tag and CRC-32); every report carries all of what is set, and closing turns it off. Adapted from SDL3's `SDL_hidapi_ps5.c` (zlib licence; attribution in `dualsense.ts`). Preferred over the Gamepad API for the same pad.
    - Both Steam drivers are ported from SDL3 (zlib licence; attribution in `steam-protocol.ts`). If claiming fails, Steam may be holding the controller: quit it.
  - **Dedupe:** a pad that WebHID has opened isn't also taken from the Gamepad API (matched by vendor and product id).
  - **Wire:** `{"t":"input","k":"pad","i":slot,"b":[17],"a":[4],"ty":"xbox"|"playstation"|"switch"|"steam"|"generic","gyro":[x,y,z],"accel":[x,y,z],"touch":[{"id","x","y","down"}],"bat":0..1}` (`b` has 24 entries: the standard 17 and the extras) when something changed (motion within noise doesn't count), and `{"k":"pad","i":slot,"gone":true}` when a pad leaves or the page loses focus. The pad's type is `ty`, not `t`: `t` is the control channel's message type. The streamer's `{"t":"rumble","i":slot,"lo":0..1,"hi":0..1,"ms":N}` plays on the physical pad in that slot (`ms` 0 stops it). The others go to the pad in the slot the same way, and are ignored by a pad that can't do them: `{"t":"haptic","i","side":"left"|"right","amp","on_us","off_us","count"}` (a trackpad pulse train: played on a Steam Controller's pad, as a short rumble elsewhere), `{"t":"led","i","r","g","b"}` (DualSense lightbar), `{"t":"players","i","mask"}` (its player LEDs) and `{"t":"trigger","i","side","effect":[11 bytes]}` (its adaptive trigger).
  - **Portal:** the Controllers page (`/controllers`) lists what each backend sees with a live view and a raw view (Gamepad buttons and axes, or the last HID report in hex), shows each pad's extras and touch areas, connects WebHID devices and tests rumble (and a DualSense's lightbar and triggers), and lets the user pick each app's virtual controller (`/api/controllers/apps`; hidden on a server without it); the session toolbar has a small menu for the same.
- **Size.** The picture follows the element: device pixels, capped at 2560×1440 by default, resized when the element settles. With `fixedSize` (apps whose display can't change size, such as Steam's gamescope) it never asks for a resize, and the picture is letterboxed in the element.
- **Frame rate** (`setFps(60 | 90 | 120)`, `fps`, `onFps`): the streamer encodes at 60 by default, and the app's setting at launch. `setFps()` changes it live, with no gap: the streamer reconfigures its encoder in place and scales the bitrate (the NVENC codecs by (fps / 60)^0.75; PyroWave's budget is per frame, capped at 600 Mbit/s). It resolves with the rate now and rejects if this page doesn't have the controls, the streamer refuses (`{"t":"fps","fps":N,"error":"…"}`) or doesn't answer in 3 s. The page sends `{"t":"fps","fps":N}`; the streamer's `hello`, its `stats` messages and the answer carry `fps`, so `onFps` and `fps` follow whoever changed it. Not for apps with a `fixedSize` display (gamescope can't change refresh while running); the portal's session toolbar offers it only when the app isn't one.
- **Performance overlay** (`setOverlay(0 | 1 | 2 | 3 | 4)`, `overlay`, `onOverlay`): for an app with a MangoHud overlay (Steam), 0 is off, then FPS only, bar, extended, full. `setOverlay()` resolves with the level now and rejects if this page doesn't have the controls, the app has no overlay, or the streamer refuses (`{"t":"overlay","level":N,"error":"…"}`) or doesn't answer in 3 s. The `hello` and `stats` carry `overlay`, so `onOverlay(level)` and `overlay` follow whoever changed it: a level 0 to 4, `"custom"` when the user wrote their own config, or `null` when the app has no overlay (the portal's session toolbar then offers nothing).
- **Stats** (`readStats()`): codec, size, fps (shown; `targetFps` is what the streamer encodes, `sentFps` the rate it actually sent, from the cumulative `frames_sent` in its `stats` messages, null until two have come in), bitrate, RTT, decode and jitter-buffer time, losses, and **send → shown**. That last one comes from the server's per-frame send times, matched by RTP timestamp, with the clock synced by pings. Over WebTransport, also send → complete (p50, p95), the longest wait between frames, and the frames FEC rebuilt. `node` is the node's own load: CPU (whole machine, cores, 1-minute load), RAM, and for an NVIDIA GPU its use, VRAM, NVENC and NVDEC use, temperature, power and SM clock (each left out if unread), plus the streamer's own CPU (percent of one core). The streamer sends it about once a second as `{"t":"system","cpu","cores","load1","mem_used","mem_total","gpu"?,"vram_used"?,"vram_total"?,"enc"?,"dec"?,"temp"?,"power"?,"power_limit"?,"clock"?,"streamer_cpu"}` (percent 0..100, bytes, °C, W, MHz); `node` is `null` before the first report and when the last is over 3 s old.
- **Health grade** (`assessHealth(history, { visible, intervalMs? })`, `health.ts`): a letter A–F, a 0–100 score, a one-line summary ("Smooth", "Slow decoding", …) and a list of issues (`id`, `severity`, `title`, `detail` with the numbers, `hint` on what it means and what to try), most severe first. A pure function of the last `HEALTH_WINDOW` (8) stats snapshots; the portal polls once a second, whether or not the Stats panel is open, and shows the letter on the toolbar's Stats button. It returns a null grade while the page is hidden (a hidden page's stats are throttled; the portal drops its history then) and until two snapshots are in.
  - **Window:** each signal is levelled per snapshot (0 below its threshold, 0.2 at it, 1 at the bad end) and the window's level is the larger of the mean (sustained trouble) and 0.35 × the worst (a spike counts, but one alone stays minor). Under 0.1 isn't reported; from 0.4 an issue is major, from 0.75 critical. Counters (`packetsLost`, `framesDropped`, `framesRecovered`) are judged by their growth over the window, so an old total is forgotten and a reset on reconnect counts as nothing. PyroWave frames that miss packets past the 60 ms deadline still show, decoded from the packets that came (softer where blocks are missing, for one frame): they count in `framesPartial` and the minor "Frames shown incomplete" issue (from 2 a second, weight 8, like FEC repairs), not in `packetsLost`. On PyroWave the frames that never showed (a packet missing, overtaken by the next whole frame) cost only themselves: they are "Frames skipped" (weight 20), judged as a share of the target rate like the browser's dropped frames (from 1 %), and "Packet loss" (weight 40, from 0.2 a second) is left to the codecs where a lost frame breaks the ones after it. The node's GPU load counts toward "Node overloaded" only while the streamer's composited → encoded p99 (`encodeP99Ms`, from its `stats`) is past half the frame budget: a game using the whole GPU is a game running.
  - **Score:** 100 minus each issue's weight × its level, then capped by severity: any issue rules out an A (89), a major one a B (79), a critical one a C (69). A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 55, F below.
  - **Signals** (first value that counts → as bad as it gets; weight in points):
    - **Stutter** (30): shown fps under 95% of the fps the streamer sent → 60%.
    - **Browser drops** (20): frames dropped per second, 1% of the target rate → 15%.
    - **Decode** (35): decode time per frame, 0.5 → 1.2 of the frame budget (1000 / target fps, so it scales: 8 ms is half a frame at 60 fps and a whole one at 120).
    - **Freezes** (45): the longest wait between frames, 3 frame budgets (at least 50 ms) → 500 ms. WebRTC has no gap measure, so a snapshot with 0 fps counts as a 1 s freeze. Stutter and freezes are judged only in snapshots where the streamer sent at least 10 frames/s (`sentFps`; the freeze gap must also beat 3 send intervals): the streamer sends only when the picture changes, so a still desktop sends and shows almost nothing and is an A. Without `sentFps` (an older streamer) neither is judged.
    - **Latency** (30): send → shown p50, 20 ms → 100 ms (about 35 is minor, 60 major, 100 critical).
    - **Uneven latency** (15), the worst of: delivery p95 − p50 (WebTransport), 8 → 40 ms; the interquartile range of the latency p50 across the window, 6 → 30 ms; the WebRTC jitter buffer, 25 → 80 ms.
    - **Loss** (40): lost frames per second over WebTransport, 0.2 → 6; lost packets per second over WebRTC (which retransmits), 2 → 60.
    - **FEC repairs** (8): frames rebuilt per second, 2 → 30. Harmless now, but the link is dropping packets.
    - **Round trip** (12): 10 ms → 80 ms.
    - **Node overloaded** (30), one issue naming whatever is over: CPU 90 → 100%, RAM 95%, GPU 95%, VRAM 95%, NVENC 95%, the streamer's CPU 90% of the machine (or of one core without a core count). Skipped when the node report is missing or stale.
    - **Sound** (10): audio jitter buffer, 40 → 200 ms.
  - **Missing fields** are skipped, never penalised: a snapshot from the other transport, an older streamer, or a node without a GPU. The delivered bitrate isn't judged: the streamer's target isn't sent to the page. 
- **Recording** (`summarizeRecording(snapshots, health, meta)`, `recordingMarkdown()`, `recording.ts`; `Player.collectLatencies()`): the numbers an exit pass in a real browser hands back. The portal's stats panel has "Record 30 s": it keeps each second's snapshot and health assessment for 30 s of wall clock (a hidden tab adds none), then shows the summary in a dialog with "Copy as JSON" and "Copy as Markdown". The summary has the user agent, transport, codec, decoded size, environment and app, ISO timestamp; shown fps (p50, min) against the target, and the mean the streamer sent; send → shown p50/p95/p99 over every frame of the run (`collectLatencies()`; per-second p50s if none were collected, and `latencyMs.source` says which); decode p50/p95 (of the per-second means: WebRTC reports only those); send → decoded p95 and RTT p50; mean bitrate; frames lost, recovered and dropped, and PyroWave frames shown incomplete (counter growth; a reset on reconnect counts what followed); freezes (seconds with a gap of 250 ms or more, and the longest gap; WebTransport only); audio buffer delay (mean, max); and the worst and final health grade with the worst moment's issues. A field the transport or streamer doesn't give is `null`, not 0.
- **Probe** (`runProbe()`): click → screen, using synthetic clicks and the test pattern's centre flash; with sound on, also click → speaker and the A/V offset, from the test pattern's tone (timed by an AudioWorklet, mapped to output time).
