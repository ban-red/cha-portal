# @cha/player

The browser side of a session (plan §6.1). Framework-agnostic: give it a `<video>` element and a function that carries a WebRTC offer to the environment. In the portal, that is `POST /api/environments/{id}/connect`.

```ts
const player = new Player({
  video,
  signal: async (offer, codec) => (await api.connect(id, { codec, offer })).answer,
});
await player.connect();
```

- **Transports.** `transport: "auto"` (the default) takes WebTransport where the browser has WebTransport, WebCodecs and track generators (Chromium), and falls back to WebRTC. Pass `webTransport` (the portal's URLs and certificate hash) to allow it.
  - **WebTransport** (`wt-worker.ts`): `cha-stream/1` datagrams reassembled in a worker, frames handed over in order from a keyframe or recovery frame; WebCodecs decodes into track generators feeding `<video>` and `<audio>`.
    - **FEC** (`fec.ts`, the Reed-Solomon code of `cha-proto::fec`) rebuilds a frame's lost fragments from its parity as soon as enough are in.
    - **Lost frames:** a frame still incomplete once a later one has completed (15 ms on), or once nothing of it came for 250 ms, is lost, and the worker resyncs (below). A browser busy for a moment delivers late but in order, so that costs nothing.
    - **Resync:** after a loss the worker drops frames until a keyframe, or a recovery frame that answers the loss. It sends `{"t":"rfi","id":N}` on the control stream (N the first lost frame's id), so the streamer encodes the next frame around the loss rather than as a keyframe. If the recovery frame is itself lost (overtaken by later frames, or silent for 250 ms) it asks again at once, and if nothing comes 250 ms after asking it asks for a keyframe. H.264 and AV1 decoders show a missing reference as garbage with no error (S8), so nothing else is fed past a loss.
    - **Reports:** every 100 ms the worker reports to the streamer's rate control: send → complete (the median of 150 ms), what arrived (200 ms), and the share of datagrams that never did. A frame's datagrams count for 200 ms after its first, so ones FEC made unnecessary, or that came reordered, aren't counted lost. The worker sends them because its timers keep running when the page is hidden.
  - **WebRTC:** recvonly video and audio tracks; the streamer stamps playout-delay 0 on video. The node streams straight to the browser, while the portal only brokers the offer and answer, with a 60 s media token.
    - **Reports:** every 100 ms the page sends the streamer's rate control the same report the WebTransport worker does, over the control DataChannel. Send times come from the RTP timestamp, and the delay is the lower quartile of presented frames' (retransmissions delay some frames, a queue all of them).
    - **Resync:** when frames stop decoding for 300 ms while data still arrives, the page asks for a keyframe rather than wait on retransmissions.
- **Codec.** The best this browser can receive, in the order measured on the baseline (P1.3): HEVC, then H.264, then AV1.
  - **`switchCodec()`** changes codec in place over WebTransport: a decoder for the new codec is ready first, and the picture stays up until the new stream's first frame (gaps under 35 ms). Over WebRTC, or when the streamer doesn't answer within 3 s, it reconnects.
  - **PyroWave** (`pyrowave420`, `pyrowave444`; `pyro.ts`): the LAN tier, over WebTransport only, where WebGPU has subgroups (`supportsPyroWave()`). Frames are intra-only, so the worker hands over every frame, partial ones at the deadline, and never waits for a keyframe. `@cha/pyrowave-webgpu` decodes into an offscreen canvas; each frame becomes a VideoFrame for the same track generator as WebCodecs.
- **Input** (`input.ts`) goes up the `control` DataChannel.
  - **Pointer:** absolute positions on the picture. With `lockPointer()`, raw relative motion scaled to stream pixels, for games.
  - **Keyboard:** keys by `KeyboardEvent.code`. Held keys and buttons are released on blur, so nothing sticks. On a Mac, ⌘ goes as Ctrl (`commandAsControl`), so the Mac's shortcuts work in Linux apps. The keys of a ⌘ chord are released with ⌘, since macOS sends no keyups for them.
  - **Floor:** one page has the controls (`onFloor(control, viewers)`); a watching page sends no input or resizes, draws the controller's pointer over the picture when the picture doesn't show it, and can ask for the controls (`takeControl()`).
  - **Cursor:** in desktop mode the environment's cursor is the element's CSS cursor (a CSS keyword, or the app's image through `image-set()` at the stream's scale), so it moves with no stream delay. With a locked pointer the picture has it.
  - **Clipboard:** on Ctrl/⌘+V the V is held back until the browser's own paste event (no permission prompt) supplies the device's clipboard, which goes up first. Text an app copies arrives as a control message and is written to the device's clipboard (`onClipboard` says whether that worked or waits for the next click).
  - **Fallback:** events with no physical key (on-screen keyboards) map unshifted US characters. Full text input comes with the text-input protocol.
- **Sound.** Stereo Opus, 10 ms frames, NetEq kept at its minimum, in its own MediaStream so video is never held back for lip sync. Browsers play sound only after a click or key press; `onAudioBlocked` says when it's waiting, `setMuted()` turns it on or off.
- **Setup status** (`onStatus(status | null)`): what the app's long first-run setup is doing while its picture may still be black, such as Steam's 500 MB download. `status` is `{ label, done?, total?, unit? }`, and with no `total` the progress is indeterminate. `null` means there is nothing to show; a page starts there. Every session gets it, watching ones too, and a page that joins midway is told the current status at once. The app writes it to `/run/cha/status` (`images/README.md`); the streamer sends it as `{"t":"status",…}`, with no `label` once cleared.
- **Controllers** (`controllers/`): a manager over two backends, sending each pad to the streamer as a virtual Xbox 360 controller in a slot 0–3. Unfocused, pads are released.
  - **State** is always the standard layout: 17 buttons (0..1; the triggers are 6 and 7, analog) and 4 axes (LX, LY, RX, RY), whatever the physical pad is. Some backends add `gyro` (rad/s, x pitch, y yaw, z roll), `accel` (m/s²), `touch` (touchpad points) and `battery`.
  - **Gamepad API** (`gamepad-api.ts`): polled at 250 Hz; pads appear after their first button press. Rumble through `vibrationActuator`. macOS keeps some Bluetooth pads from the browser, and Steam Controllers sit in a vendor HID collection, so neither shows up here.
  - **WebHID** (`webhid.ts`): Chrome and Edge only, and only on a secure page (HTTPS, or `http://localhost`; a plain-http LAN address has no `navigator.hid`; `hidUnavailableReason()` says which). The user grants each device once in the browser's picker, which a click has to open (`connectHidController()`); granted devices reopen on their own. A device opens in one tab at a time. Drivers:
    - **Generic HID gamepad** (`hid-generic.ts`): built from the report descriptor WebHID exposes: Generic Desktop axes and hat, the Button page, Simulation Controls accelerator and brake as triggers, report ids, signed ranges and the hat's null state. By usage it maps to the standard layout (an Xbox-style layout by default); `hid-quirks.ts` holds per-VID/PID overrides, so far only a placeholder for 8BitDo (unverified until someone checks a real pad's raw view).
    - **Steam Controller, original** (`steam-controller.ts`; wired, dongle and Bluetooth): turns lizard mode off with the feature reports SDL sends, reads sticks, the pads (also as `touch`), gyro, accelerometer and battery, and restores lizard mode on close. No rumble: the controller has no motors.
    - **Steam Controller, 2026** (`steam-triton.ts`; wired, Bluetooth, puck, receiver): lizard mode off (resent every 3 s, as its watchdog expects), buttons, sticks, triggers, both pads, gyro, accelerometer, battery, and rumble through its output report. A puck or receiver shows a controller only once one is awake behind it.
    - Both Steam drivers are ported from SDL3 (zlib licence; attribution in `steam-protocol.ts`). If claiming fails, Steam may be holding the controller: quit it.
  - **Dedupe:** a pad that WebHID has opened isn't also taken from the Gamepad API (matched by vendor and product id).
  - **Wire:** `{"t":"input","k":"pad","i":slot,"b":[17],"a":[4],"ty":"xbox"|"playstation"|"switch"|"steam"|"generic","gyro":[x,y,z],"accel":[x,y,z],"touch":[{"id","x","y","down"}],"bat":0..1}` when something changed (motion within noise doesn't count), and `{"k":"pad","i":slot,"gone":true}` when a pad leaves or the page loses focus. The pad's type is `ty`, not `t`: `t` is the control channel's message type. The streamer's `{"t":"rumble","i":slot,"lo":0..1,"hi":0..1,"ms":N}` plays on the physical pad in that slot (`ms` 0 stops it).
  - **Portal:** the Controllers page (`/controllers`) lists what each backend sees with a live view and a raw view (Gamepad buttons and axes, or the last HID report in hex), connects WebHID devices and tests rumble; the session toolbar has a small menu for the same.
- **Size.** The picture follows the element: device pixels, capped at 2560×1440 by default, resized when the element settles. With `fixedSize` (apps whose display can't change size, such as Steam's gamescope) it never asks for a resize, and the picture is letterboxed in the element.
- **Stats** (`readStats()`): codec, size, fps, bitrate, RTT, decode and jitter-buffer time, losses, and **send → shown**. That last one comes from the server's per-frame send times, matched by RTP timestamp, with the clock synced by pings. Over WebTransport, also send → complete (p50, p95), the longest wait between frames, and the frames FEC rebuilt.
- **Probe** (`runProbe()`): click → screen, using synthetic clicks and the test pattern's centre flash; with sound on, also click → speaker and the A/V offset, from the test pattern's tone (timed by an AudioWorklet, mapped to output time).
