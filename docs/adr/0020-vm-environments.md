# 0020: Virtual machines inside environments

- **Status:** accepted (2026-10-08).
- **Context:** an experimental external catalog image runs Windows 11 in QEMU/KVM inside the app container: QEMU's GTK window is the Wayland app, and the guest's D3D11 goes through virtio-gpu to virglrenderer, which runs it on DXVK over the node's Vulkan GPU, with no GPU passthrough. The image lives in its own repository and is loaded through a catalog ([0019](0019-catalogs-loaded-by-the-admin.md)). It needs `/dev/kvm` in the app container, `/dev/udmabuf` when the host has it, and the host groups that own them. A catalog may not name devices (image-spec sections 3 and 6.3), and an older agent drops its connection on a security profile it can't parse (`ToNode` is read with `?`), so the portal can't just send the new profile to every node.
- **Decision:**
  - **A `vm` security profile, not catalog-named devices.** The profile means Docker's default seccomp and AppArmor, no capabilities, and: `/dev/kvm` (rw), `/dev/udmabuf` (rw, only when the host has it), the host groups of those devices in `GroupAdd`, a memory limit and a longer stop. The catalog says only `"security": "vm"`; the devices stay the node's choice. Like `browser` and `steam`, an external template with it waits for an admin's approval (0019), and the approval says what it grants.
  - **The node reports KVM and the portal enforces it.** `Inventory.kvm` is true when the agent's sysfs has `/sys/class/misc/kvm`. Absent means an older agent, which reads as no. Placement allows a `vm` template only on a node that reports it, saying "no KVM" for the others, and a manual choice of another node is refused the same way. The portal therefore never sends a `vm` spec to an agent that can't parse it. The agent also refuses one on a node without `/dev/kvm`, with a message that says so.
  - **Group ids come from the same probe as the render node's.** The agent's container has neither device, so it asks a throwaway container of the streamer image to `stat` them. That probe takes an allowlist of exactly `/dev/kvm` and `/dev/udmabuf` besides DRM nodes. If KVM's group can't be found, the launch fails with that reason rather than starting a guest that can't open `/dev/kvm`.
  - **A memory cap.** The app's `Memory` and `MemorySwap` are both `CHA_VM_MEMORY_MB` (default 12 GiB, at least 1 GiB). A guest's RAM plus QEMU's own must not be able to push a shared host into memory exhaustion; an earlier test froze a node.
  - **A 30 s stop grace** for the app container (5 s for all others), so the guest OS can shut down on SIGTERM. The app carries a `sh.cha.profile=vm` label, which the stop reads, so it also holds after an agent restart. It is under the portal's 60 s stop timeout.
  - `cha-node --check-image --profile vm` doesn't pass KVM into the check; an image that stops for want of it is a `warn`, not a `FAIL`. `--doctor` reports whether `/dev/kvm` is there (info, not a failure: most nodes need not run VMs).
- **Consequences:** a catalog can offer a virtual machine without being able to name a device or a mount. The cost is real: KVM's ioctl surface is exposed to the container, and an approved `vm` image runs code as a guest that shares the node's CPU and RAM up to the cap. That is why it needs approval and why it is not the default for anything. A guest uses CPU and memory the cap bounds, but not the GPU's memory or the node's disk I/O, which placement doesn't weigh. Nested virtualisation (a Proxmox VM or LXC node) needs the outer host to pass KVM through; the node then reports no KVM and is skipped. Windows itself, its licence and its image are the catalog author's matter, not the portal's.
