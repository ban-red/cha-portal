# 0008: Moonlight hosts found and adopted by a node, streamed through cha-gateway

- **Status:** accepted (2026-10-07). Starts Phase 3's *External GameStream hosts* (PLAN.md §9), on the gateway S3 proved.
- **Context:** many owners already run Sunshine or Apollo on a gaming PC. They advertise themselves on the LAN (`_nvstream._tcp`), and Moonlight clients pair with them by PIN. Spike S3 showed a gateway can take such a host's H.264/HEVC through `moonlight-common-rust` and pass it, untouched, into a WebRTC track. What's missing is finding hosts, pairing from the portal, putting their apps in front of users, and launching them like any environment.
- **Decision:**
  - **Nodes find and pair; the portal shows.** The gateway must sit on the host's LAN, and the portal may not (a VM, a tailnet), so each node browses `_nvstream._tcp.local.`, reads each host's `/serverinfo` (name, `uniqueid`, ports, codecs, whether this node is paired), and pushes the list to the portal (`ToPortal::MoonlightHosts`, sent only to a portal that says it reads it, and again whenever it changes). The node is the Moonlight client: one client identity per node (`client-cert.pem`, `client-key.pem`) and each paired host's certificate (`hosts/<uniqueid>/server-cert.pem`), under `<CHA_DATA_ROOT>/node/moonlight/` (root, 0700; keys 0600).
  - **Adopting a host is one action.** An admin clicks **Adopt** on a found host. If the node isn't paired yet, it starts Moonlight's PIN pairing and the portal shows the 4-digit PIN and a link to the host's PIN page (Sunshine and Apollo: `https://<host>:47990/pin`); the node finishes once the PIN is entered there, and the portal polls. A paired host is then stored as adopted (table `moonlight_hosts`), with its app list (`/applist`, through the node) cached and refreshed when the node reconnects, hourly, and on demand.
  - **A host is one section of the dashboard.** Every signed-in user sees each adopted host as its own section, named after it, listing the apps the host offers. Each app launches as an environment whose template id is `moonlight:<host id>:<app id>`; these templates come from the database beside the built-in catalog. A host streams one session at a time (GameStream allows one client), so a second launch is refused (`409 host_busy`) while one runs.
  - **The gateway stands in for the streamer.** A launch is placed on the node that paired the host, needs no GPU, and runs one container: `cha-gateway` (image `cha/gateway:dev`, published as `cha-gateway`, `CHA_GATEWAY_IMAGE`), labelled as the environment's streamer so the agent's start, adoption, exit and connect paths work unchanged, with no app container. It takes the streamer's arguments plus the host's address, ports, `uniqueid` and app id, and the identity directory read-only. On start it launches the app on the host at the environment's size and rate; on stop it quits it. It serves `/info` (no WebTransport) and `/webrtc/media` with the portal's media tokens like the streamer, passes video (H.264 or HEVC, the host's choice among what the browser asked) and Opus audio through without transcoding, maps the player's control messages to Moonlight input (keyboard by `code` to Windows virtual keys, mouse absolute, relative, buttons and wheel, gamepads by the standard mapping), turns a keyframe request into an IDR request, and answers `ping`. The size is fixed for the session (`fixedSize`).
- **Consequences:**
  - A gaming PC on the LAN becomes a set of apps in the portal, played in the browser, with nothing installed on it beyond Sunshine or Apollo.
  - `moonlight-common-rust` (GPL-3.0-or-later, compatible with our AGPL) enters the node agent and the gateway, pinned to the commit S3 used. Its limits are ours for now: no AV1, no video encryption (we ask for none; acceptable on the LAN between node and host, while the browser leg is WebRTC's DTLS), loss recovery by IDR only.
  - Hosts on another subnet aren't found; adding one by address is later work.
  - Pairing gives the node control of the host's apps the way any Moonlight client has. Unadopting doesn't unpair; the host's own client list does.
