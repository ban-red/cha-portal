# 0009: A GameStream host module, ported from Moonshine, so Moonlight clients can play our environments

- **Status:** accepted (2026-10-07), including the one-host-per-node topology, confirmed by the owner the same day.
- **Context:** stock Moonlight and Artemis clients (desktop, Steam Deck, phones, TVs) are the best native clients there are, and the PLAN backlog has a "Moonlight host façade inside `cha-streamer`". [Moonshine](https://github.com/hgaiser/moonshine) (BSD-2-Clause) is a Rust GameStream host whose engine mirrors ours (Smithay, a PulseAudio-protocol server, Opus); shipping it whole would add a second engine, systemd and `inputtino` (ADR 0004), so we port its protocol code only. A survey (2026-10-07) found about 6.4k lines of protocol code cleanly separable from its engine, little test coverage, and some gaps: an unauthenticated PIN endpoint, video and audio sockets that follow whoever sends `PING`, sessions not bound to the launching client, a no-op `/unpair`, a malformed control packet ending the session.
- **Decision:**
  - **One crate, `cha-gamestream`, holds the whole protocol and nothing of our engine.** It knows GameStream (nvhttp, pairing, TLS, RTSP, the ENet control channel and its encryption, input packets, video RTP with Reed-Solomon FEC and AES-GCM, audio RTP with RS(4,2) and AES-CBC, mDNS) and talks to the rest of the world only through traits it defines:
    - `Directory`: the apps a paired client sees, and launch, resume and cancel;
    - `PairingStore`: paired clients' certificate fingerprints;
    - `MediaBackend`: encoded video in (Annex-B or OBUs, a keyframe flag, an index for RFI), Opus in, keyframe and invalidate requests, bitrate, and input and gamepad events out in its own neutral types.

    The crate keeps Moonshine's copyright and licence (`LICENSE-MOONSHINE`, and a line at the top of each ported file); our changes are AGPL-3.0-or-later like the rest. It is tested on its own, on any OS: golden-packet tests for the packetisers and the crypto, and loopback tests that drive it with `moonlight-common-rust` (already in the workspace) as a real client against fake traits.
  - **Our code adapts to it from outside, behind a cargo feature.** `cha-streamer` gets a `gamestream` feature and one module implementing `MediaBackend` by delegating to `Media`, `Audio`, `Gamepads` and `Viewers`; the node, later, a module implementing `Directory` and `PairingStore`. Removing the feature (or the crate) removes GameStream with nothing else to change; the browser transports never see it.
  - **Security gaps closed while porting:** a PIN is only accepted through the `PairingStore`/`Directory` side (from the portal, by a signed-in user), never over plain HTTP; video and audio follow `PING` only from the address of the client whose RTSP session it is; a session belongs to the client certificate that launched it; `/unpair` unpairs; a malformed control packet is dropped and counted, not fatal; feedback (rumble, LEDs) is drained, not one message per tick.
  - **Topology:** one GameStream host **per node**, run by the agent (it holds the host's identity, advertises over mDNS and serves nvhttp, pairing and RTSP), listing as apps the environments of the users whose devices are paired; the environment's streamer serves that session's video, audio and control on a separate port block (`CHA_GAMESTREAM_PORT_BASE`, six ports per environment), which RTSP reports to the client. Pairing a device once (its PIN typed into the portal) then covers every environment of that user on that node. The alternative, a host per environment inside the streamer, is simpler but makes users pair every environment, since Moonlight pairs per host.
  - **Shared encoder, stated plainly:** the streamer encodes once per codec for everyone watching, so a Moonlight session's resolution and frame rate become the environment's (it holds the floor like any controlling viewer), and its bitrate caps co-viewers on the same codec. Per-viewer encoders are later work.
- **Milestones:** **G1** the crate, with its tests (no integration). **G2** the streamer's `MediaBackend` and port block. **G3** the node's host, pairing in the portal, apps from environments. **G4** what the shared encoder and audio don't do yet (5 ms Opus packets, surround, encoder slices, the pad kind per client).
- **Consequences:** about 6.4k ported lines plus adapters, in one crate that can be read, tested and removed as a unit. New dependencies only in that crate, each checked for an AGPL-compatible licence before it is added.
