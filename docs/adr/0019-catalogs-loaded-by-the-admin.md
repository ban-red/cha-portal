# 0019: Catalogs loaded by the admin

- **Status:** accepted (2026-10-08). Supersedes the id wording in [0017](0017-images-pulled-on-demand.md) (`<catalog>/<app>`).
- **Context:** ADR 0017 made the entry and launch shapes ready for catalogs from outside: JSON documents of templates, whose images live in registries of their own. This decision loads them. A catalog is third-party text that ends up as a container the portal starts on an owner's GPU machine, so what it may ask for, who vouches for it and what happens when it changes need to be fixed first.
- **Decision:**
  - **Ids use a dot, not a slash: `<catalog>.<app>`.** Ids appear in URL path segments (`/api/catalog/{id}/icon`, `/api/apps/settings/{template}`), in node directory names (`users/<user>/<template>`), in Docker labels and volume names. A slash breaks the first two; a dot is legal in all of them. Built-in ids stay bare (`chrome`). The catalog slug is the admin's choice (`^[a-z0-9][a-z0-9-]{0,31}$`, never a built-in id or `moonlight`); an id inside a document is local (`^[a-z0-9][a-z0-9-]{0,39}$`), so a namespaced id can't be forged by a document.
  - **An admin adds a catalog by URL (http or https) or by pasting its JSON.** JSON only, at most 1 MiB and 64 templates. The same document shape as `images/catalog.json`, plus optional top-level `id` (a suggested slug) and `name`. Fetches time out after 10 s, follow at most 3 redirects and are size-capped. The portal fetches from wherever the admin points it, so the URL is the admin's responsibility.
  - **What a document may hold.** Every `image` names a registry; no `localImage`; `security` is one of the existing profiles; `class` is never `moonlight`; `shared.perUser` holds plain relative paths. Errors are 400s that name the template and the field. A document that doesn't pass is stored nowhere.
  - **Trust.** Adding a catalog trusts its `standard` templates: they are available to players at once. A `browser` or `steam` template stays unavailable (visible to admins only, with the reason) until an admin approves that template. The approval records the profile and the image's registry host; a refresh that changes either one clears it. A new tag on the same host keeps it. Removing a template from a catalog drops its approval.
  - **Icons are fetched when the catalog is loaded or refreshed**, from an `https://` URL or a path relative to the catalog's URL (a pasted catalog has none, so only absolute URLs). SVG only, at most 256 KiB, stored in the database and served from `/api/catalog/{id}/icon` with the same headers and CSP as built-in icons, so the portal never sends a player to a third party's server. A failed icon is logged and shown to the admin; the template gets the generic icon. A failed fetch of an unchanged icon keeps the one already stored.
  - **Refresh is by the admin's request only.** A failed refresh (unreachable, bad status, too large, doesn't pass) leaves the last good document in force and records the error and time on the catalog. A timer that refreshes on its own is future work: it needs a place to show "changed, needs approval" first.
  - **Removing a catalog is refused (409) while an environment of one of its templates is starting, running or stopping.** Otherwise it goes, with its approvals and icons. A refresh may drop a template that has a live environment: that environment keeps running and is named by its id until it stops. Per-user choices (frame rate, controller, saved-data settings) and app data on the nodes (`users/<user>/<catalog>.<app>`) are left alone: re-adding a catalog under the same slug finds them again, and deleting data is a separate, deliberate act.
  - Adds, refreshes, approvals and removals are in the audit log (`catalog.added`, `catalog.refreshed`, `catalog.template_approved`, `catalog.template_unapproved`, `catalog.removed`).
- **Known limit:** nodes accept only ids of the old shape for app data (`cha_wire::valid_template_id`: letters, digits, hyphens, 32 characters). A dotted id would be refused there, so the portal refuses a launch of a loaded app that needs a home or shared directory (409 `storage_unsupported`) instead of sending it. Apps from loaded catalogs run without saved data until the node side accepts the new ids; that change touches `cha-wire` and `cha-node`.
  - *Lifted 2026-10-08:* `valid_template_id` now accepts `<catalog>.<app>` (one dot; parts of at most 32 and 40 characters), so nodes keep app data for loaded apps and the portal no longer refuses those launches. The portal now checks slugs and app ids with the node's own functions (`valid_catalog_slug`, `valid_catalog_app`): neither may end with a hyphen, and an app may not be called `migrated` or `migrating`, the node's marks beside a home. An agent older than that release still refuses them, with its own message.
- **Consequences:** an admin can offer third-party environments without being able to be handed a privileged container by a document: privilege is the portal's, per template, and explicit. Players only ever see approved, launchable templates. Loaded catalogs live in the database and in memory in the portal; nodes learn nothing about catalogs, they get a launch spec as before.
