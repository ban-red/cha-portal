# 0010: A native client, macOS first: a Rust core, pluggable transports, GameStream first

- **Status:** accepted (2026-10-07). Starts Phase 4 (PLAN §6.2, `cha-player`) early, and changes its macOS rendering choice.
- **Context:** the browser player is good, but a native client gets raw input (full keyboard capture, pointer lock without browser chrome), lower and steadier latency (no browser compositor), and every controller's haptics. With ADR 0008 (Moonlight hosts) and ADR 0009 (our nodes as GameStream hosts) built, one Moonlight-protocol client already plays both Sunshine/Apollo PCs and our environments. The owner chose macOS (the M4 baseline) first, a pure-Rust UI, and GameStream as the first transport.
- **Decision:**
  - **Crates, each removable:**
    - `cha-client`: the platform-neutral core. Session lifecycle, frame pacing, stats, and the `Transport` / `Session` traits, with an input model identical to the browser player's (keys by W3C `KeyboardEvent.code`, mouse absolute/relative/buttons/wheel, gamepads in the W3C standard mapping) so a `cha-stream/1` transport can pass input through and the GameStream mapping is shared.
    - `cha-moonlight-input`: the browser-model → Moonlight input mapping (W3C code → Windows VK, mouse, wheel, standard-mapping pads → Moonlight controller state), extracted from `cha-gateway` so the gateway and the client share one tested table.
    - `cha-client-gamestream`: the GameStream transport on `moonlight-common-rust` (pinned as in the gateway): mDNS discovery, PIN pairing with a per-install client identity, app lists, launch/resume/quit, video and Opus out, input and rumble in. It plays Sunshine and Apollo hosts and our nodes (ADR 0009).
    - `cha-player`: the macOS app. `winit` window with pointer lock and raw keyboard; `wgpu` on Metal for everything drawn; VideoToolbox decode (H.264, HEVC, AV1 where the hardware has it) with the decoded `CVPixelBuffer` shown through a Metal texture without a copy; Opus decode to CoreAudio; SDL3 for gamepads and their haptics only; `egui` (on the same `wgpu` device) for the launcher, pairing and settings, and a stats overlay.
  - **Changed from PLAN §6.2:** on macOS we render with Metal through `wgpu` instead of Vulkan (MoltenVK), and decode with VideoToolbox directly instead of FFmpeg; SDL3 covers gamepads, not the window. Linux and Windows get their own decode and present modules behind the same core later.
  - **Platform features we use (from a 2026-10-07 survey):**
    - **Game Mode:** the app bundle declares itself a game (`LSApplicationCategoryType = public.app-category.games`), so macOS gives it Game Mode in full screen: double Bluetooth sampling for controllers and AirPods, and CPU/GPU priority. (C1)
    - **AWDL:** Apple's AirDrop/Continuity radio makes the Wi-Fi hop channels, which shows as periodic latency spikes; an app can't turn it off. The client detects the pattern in its stats and says so, and the README explains how to turn it off. (C1)
    - **Upscaling on the client:** an optional MetalFX spatial upscaling pass (Metal 4, macOS 26) after decode, so the node can send 1080p or 1440p at a lower bitrate and the Mac scales it to the display. MetalFX frame interpolation needs a renderer's motion vectors and depth, which a video stream doesn't have, so it isn't used. VideoToolbox's own video processing (`VTFrameProcessor`, low-latency super-resolution and frame-rate conversion) is checked against MetalFX before choosing. (C2)
    - **iroh 1.0 for reaching nodes:** QUIC addressed by public key, with NAT hole-punching and relays we host ourselves, so the native client reaches a node behind CGNAT without a port-forward, TURN or a mesh, and without a cha.sh service. Browsers can only use iroh through a relay, so it is the native client's transport. (C2)
    - **ECN and L4S:** the native client can read ECN marks, which the browser can't easily, so it is where an L4S-aware controller (SCReAMv2) is tried first. (C2, an experiment)
  - **Milestones:**
    - **C1** the macOS player and the GameStream transport (Sunshine/Apollo hosts and our nodes), with Game Mode and the AWDL hint;
    - **C2** the `cha-stream/1` transport through the portal (sign-in by device login, launch, media tokens; our rate control, FEC, RFI, clipboard, AV1, later PyroWave via our WGSL decoder on `wgpu`), over WebTransport on the LAN and iroh beyond it, plus MetalFX upscaling and the L4S experiment;
    - **C3** `cha://` links from the dashboard, settings, a signed and notarised build.
- **Consequences:** one Rust codebase for the client, sharing the input mapping with the gateway and, later, `cha-proto` with the streamer. It ships first as a direct download (and a Homebrew cask), which raises no licence question; notarisation needs the owner's Apple Developer ID. The Mac App Store is possible but not free: Apple's usage terms add restrictions that the GPL family forbids passing on (GPL-3 §10), so App Store distribution needs every copyright holder's permission. Ours is the owner's; `moonlight-common-rust` (GPL-3.0-or-later) would need its author's permission or an App Store exception, or a transport without it; future contributors' AGPL code would need the same (a CLA or an exception in our licence, decided before outside contributions arrive). The App Store sandbox also limits raw HID and keyboard capture.
