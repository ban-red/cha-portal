# 0007: Claim nodes found on the LAN with a pairing code

- **Status:** accepted (2026-10-07). Adds a way to enroll beside the join token ([0001](0001-node-channel-json-over-websocket.md)); join tokens stay.
- **Context:** a node enrolls by redeeming a join token that the owner copies from the portal to the node. That proves the person enrolling controls both ends, which matters: whoever enrolls a node controls it, and the agent holds the Docker socket, so that is root on the machine. Copying the token is the fiddliest step of setting a node up. On a LAN the portal could find unclaimed nodes itself, but "the first portal to answer gets the machine" would hand root to anything on the network that answers first, and "the first node the portal sees" would let anything on the network pose as a node and receive users' sessions.
- **Decision:**
  - **An unclaimed node advertises itself.** An agent with no identity and no join token generates its key, picks an 8-digit pairing code (`4821-9375`, from the OS's random source), writes it to its log and to `claim-code` in its state directory (mode 0600, so `--doctor` can show it), and advertises `_cha-node._tcp.local.` over mDNS: port 7679, TXT `v=1`, `name`, `gpu` (a short summary), `fp` (the first 16 hex characters of SHA-256 of its public key). It listens for a claim on TCP 7679 (`CHA_CLAIM_PORT`), only while unclaimed. `CHA_DISCOVERY=false` turns all of this off.
  - **The portal lists what it finds.** `cha-control` browses `_cha-node._tcp.local.` (`CHA_DISCOVER_NODES`, on by default) and keeps what it saw in the last 60 s in memory. Admins see them under **Admin → Nodes → Found on your network**, with name, GPU, address and fingerprint; a node already enrolled (same fingerprint) isn't listed.
  - **Claiming takes the code.** The admin clicks **Claim** and types the code from the node's log. The portal and the node run SPAKE2 (Ed25519 group, identities `cha-portal` and `cha-node`) with the code as the password, so each proves it knows the code without sending it, and they share a key K. Over the claim port (`/claim/start`, `/claim/finish`, `/claim/done`, JSON over HTTP):
    1. portal → node: its SPAKE2 message and the portal's URL; node → portal: its SPAKE2 message and a claim id;
    2. portal → node: `HMAC-SHA256(K, "cha-claim portal" ‖ transcript)`; node → portal, once that checks: its public key, name and `HMAC-SHA256(K, "cha-claim node" ‖ transcript ‖ key)`;
    3. the portal records the node as enrolled with that key (as redeeming a join token does) and sends `{ node_id, mac }`; the node saves its identity (the portal's URL, the id, its key), stops advertising, closes the claim port and connects as usual.

    The transcript is both SPAKE2 messages, the portal URL and the claim id, so neither the URL nor the key can be swapped in transit. No secret crosses the network: the node never receives a token, only an id for the key the portal now trusts.
  - **Telling nodes apart.** The node logs its fingerprint beside the code, the portal lists it, and the claim form asks the admin to compare them, warning when two found nodes share a name. That matters because the portal sends its confirmation first: something posing as a node, if given the code, gets a value it can test codes against offline. The node, which is what's worth taking, never sends anything testable before the portal has proved it knows the code, so it can't be attacked that way.
  - **Guessing is bounded.** Five failed claims replace the code (logged, with the attempt's address) and pause claims for 30 s. 10⁸ codes at five tries per code make an online guess hopeless; there is nothing to guess offline.
  - **Which URL the node dials.** The portal sends the URL its admin is using (the request's origin, or `CHA_PUBLIC_URL` when set). The node connects to its own `CHA_PORTAL_URL` when it has one (the quick start's agent reaches the portal over loopback) and to the claimed URL otherwise, and it refuses a claim it couldn't use: plain `http://` to another machine without `CHA_ALLOW_INSECURE_PORTAL`, said back to the admin in the portal. A node with a join token enrolls with that, as before, and never advertises.
- **Consequences:**
  - Setting up a node on the LAN is: start the agent, then claim it in the portal with the code from its log. The quick start needs no token at all.
  - mDNS is link-local: it works on one LAN, not across subnets or a tailnet, where the join token remains the way.
  - The portal must see multicast, which Docker's bridge network doesn't pass, so the portal's compose files move it to host networking (`CHA_LISTEN` replaces the published port).
  - An unclaimed node accepts connections on TCP 7679 from the LAN until it is claimed. All it offers there is the claim exchange.
  - New dependencies: `mdns-sd` (MIT or Apache-2.0) and `spake2` (RustCrypto, MIT or Apache-2.0).
