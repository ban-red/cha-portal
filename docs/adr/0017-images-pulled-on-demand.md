# 0017: Images pulled on demand, named by the catalog

- **Status:** accepted (2026-10-08).
- **Context:** a node runs an app only if its image is already there. Dev nodes use local builds (`cha/env-chrome:dev`) and never pull, since a bare name would come from Docker Hub's `cha` namespace. Quick-start nodes map every catalog name to one registry and tag (`CHA_IMAGE_REGISTRY`, `CHA_IMAGE_TAG`). A dev node that lacks an image fails ("isn't on this node: build it"), even though a published copy exists. A pull shows nothing while it runs, though environment images are hundreds of MB. Placement doesn't know which node already has the image. The portal is also meant to load **catalogs**: YAML or JSON listings of environments, including third-party ones whose images live in registries of their own, with no local dev names.
- **Decision:**
  - **A catalog entry names its images.** `image` is the reference to run, and for anything pullable it names a registry (`ghcr.io/ban-red/cha-env-chrome:{version}`). An optional `localImage` is a dev build to prefer when present (`cha/env-chrome:dev`). `{version}` is filled with the node agent's release, so a node pulls the image built for its own contract. A bare `image` (the built-in catalog today) keeps working as it does.
  - **The portal hands the node an ordered list of candidates** (`imageCandidates` in the launch spec): the local name first, then the published reference, with the old `image` field kept for older nodes. The node uses the first candidate it has. If it has none, it pulls the first one that names a registry. It never pulls a bare name. `CHA_IMAGE_REGISTRY` and `CHA_IMAGE_TAG` still map bare names for nodes set up that way. The streamer's own image follows the same rule.
  - **A pull reports its progress.** The node reads the engine's pull stream as it arrives, sums the layers' bytes, and sends the portal `EnvironmentProgress` at most twice a second, with optional structured fields (`done`, `total`, `unit`) beside the text. The portal shows a progress bar on the launching card and the session's "Starting…" screen. A failed pull says what was tried.
  - **Nodes report the images they hold**, and placement prefers a node that already has one of the candidates over an otherwise equal one that would have to pull.
  - **A node can be kept out of automatic placement** (`CHA_PLACEMENT=manual`). It is still choosable by hand: for test beds such as an encoder node.
  - **Catalogs, for later, fit this shape:** a catalog is a document with `version: 1` and `templates: [...]` (the built-in `images/catalog.json` is one). An admin adds one by URL or file. Its entries get namespaced ids (`<catalog>/<app>`), may only name the existing security profiles, and must give registry references (no bare names, no `localImage`). Loading catalogs is a separate step; this decision only makes the entry and launch shapes ready for it.
- **Consequences:** the first launch of an app on a node takes as long as its download, with progress, instead of failing. Images published per release become part of the node contract (`{version}`). A third-party catalog can't escalate privileges: the profile is the portal's, and pulls stay explicit about their registry.
