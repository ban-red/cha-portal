# 0013: Cha Player on `cha-stream/1`: device sign-in and WebTransport

- **Status:** accepted (2026-10-07). Shapes milestone C2 of [0010](0010-native-client-macos-first.md).
- **Context:** C1 plays Moonlight hosts, our nodes included, over GameStream: the host's own rate control, keyframe recovery only past FEC, no clipboard, no PyroWave, and pairing per node. The browser player already has everything C2 needs on the node's side: the portal launches an environment and hands back WebTransport URLs for every node address, the streamer's certificate hash and a signed media token; the streamer serves `cha-stream/1` over WebTransport; `cha-proto` (framing, FEC, reassembly) is Rust. What the native player lacks is a way to be signed in to the portal, since browser sessions are cookies, and a Rust client for the protocol.
- **Decision:**
  - **Device tokens.** The portal issues each installed player a revocable, random 256-bit token (stored as its SHA-256, like sessions), sent as `Authorization: Bearer`. A token belongs to one user and one install (a random id the player keeps); a new sign-in from the same install replaces its token. It opens only what a player needs (the catalog, environments, launch, connect, stop, the user's preferences), through its own extractor; account, admin and device management stay cookie-only. The Devices page lists them (name, last used, address) and revokes them.
  - **Two ways to sign in**, both ending in a device token:
    1. **A `cha://` link, first.** "Open in Cha Player" on the dashboard makes a one-time ticket (60 seconds, hashed in the database) and opens `cha://connect?portal=<origin>&ticket=<ticket>`, optionally naming an app to launch. The player swaps the ticket for a token. A portal it hasn't signed in to before is shown first ("Sign in to `<origin>` as `<user>`?"), and a token is only ever sent to the origin that issued it, so a link from elsewhere can't move a token between portals.
    2. **A device code** for a Mac without a signed-in browser, shaped like RFC 8628: the player shows a short code and the portal's address, the user approves it in the portal, and the player polls for its token.
  - **The player speaks WebTransport**, through the `wtransport` client, to the streamer's existing endpoint, with the certificate pinned to the hash the portal hands out and every address raced, as the browser does. The node needs no changes, and the browser and native player can be measured against each other. A raw-QUIC carrier is kept for later, only if WebTransport's overhead ever shows in measurements.
  - **Plain HTTP to a portal** is refused unless the player is told otherwise for development, as the node is (`CHA_ALLOW_INSECURE_PORTAL`).
  - **Order:** C2.1 sign-in, C2.2 the transport with H.264/HEVC through the existing VideoToolbox path, C2.3 PyroWave on `wgpu` (a port of `pyrowave-webgpu`; its WGSL carries over), C2.4 `CAMetalDisplayLink` pacing and glass-to-glass measurement. iroh (beyond the LAN) and the MetalFX and L4S experiments come after C2.
- **Consequences:** a second kind of credential in the portal, deliberately narrower than a session. The player registers the `cha` URL scheme. The GameStream transport stays beside the new one for Sunshine and Apollo hosts; our nodes can be played either way, and `cha-stream/1` is the one that gets our rate control, FEC, clipboard and PyroWave.
