# 0018: Node agents updated from the portal

- **Status:** accepted (2026-10-08).
- **Context:** a node's agent is updated by hand: change the version in `.env`, `docker compose pull`, `up -d` on each machine. Agents and the portal change together, nodes report their agent's release (ADR 0017), and a node left behind silently lacks fixes (0.2.1's Steam fix, for one). The agent runs in a container that compose made, with the Docker socket, so it can pull images and start containers but can't replace its own container: stopping it ends the process doing the replacing.
- **Decision:**
  - **The portal offers its own release.** A node whose agent is older than the portal, and that runs a published agent image, shows *Update to <portal version>* to admins. The portal never names an image: it sends `UpdateAgent { version }`, and the agent derives the image from the one it runs (same repository, the new tag). A dev build (a bare name such as `cha-node:dev`) can't be updated this way and says so.
  - **The agent prepares while it keeps running.** It pulls the new agent image and the new streamer image first, reporting progress, then hands over. Running environments are not touched: they keep their images until stopped, as with any update.
  - **A one-shot helper swaps the container.** The agent starts a helper container from the *new* image (`cha-node --replace-agent`), with the Docker socket, and the helper: reads the agent container's configuration, renames it `<name>-previous` and stops it, creates and starts one identical but for the image, and waits for the new agent to report itself connected. If it doesn't within 90 s, the helper removes the new container and starts the previous one again. On success it removes the previous container and keeps the previous image for rollback.
  - **Compose's settings follow.** A compose-made container records its project's directory. Where that directory has a `.env` the helper can write, it sets the release there (`CHA_VERSION`, or the version in `CHA_NODE_IMAGE`, `CHA_STREAMER_IMAGE` and `CHA_IMAGE_TAG`), so a later `docker compose up` keeps the new agent. When it can't, the update still happens and the portal says which file to change by hand.
  - **Not covered, and said so:** host files (udev rules, the AppArmor profile, modules) need root on the host, as before (`--doctor`); a release whose compose file changes needs the manual steps in its notes; the quick start's portal is updated by hand for now.
- **Consequences:** an admin brings a node to the portal's release with one click and sees it happen. The helper is the agent binary itself, so the swap logic ships and is tested with each release. The portal gains no new power over nodes: it could already start containers there, and the node, not the portal, chooses the image.
