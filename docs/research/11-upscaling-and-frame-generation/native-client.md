# Native-client upscaling and frame interpolation APIs for live low-latency streamed video (state as of 2026-11-09)

> Evidence for [research note 11](README.md).

Scope: what the Cha Player (Rust, winit, wgpu-on-Metal, VideoToolbox decode to IOSurface-backed CVPixelBuffers, PyroWave compute decode) could call on the client to upscale or interpolate decoded frames. macOS first, then Windows and Linux/Steam Deck. Browser paths, node-side game upscalers and codec-level scaling are out of scope. Budget reference: at 120 Hz one display frame is 8.33 ms, and the glass-to-glass target is ≤12 ms. Dates are given for sources where known. "(unverified)" marks claims I could not confirm from a primary source.

## 1. Apple VideoToolbox `VTFrameProcessor` (macOS 26 / macOS 27)

### Takeaway
`VTFrameProcessor` is real and does include two "low-latency" effects aimed at video conferencing: `VTLowLatencySuperResolutionScalerConfiguration` (LLSR) and `VTLowLatencyFrameInterpolationConfiguration` (LLFI). Both are ML models with tight, per-device size limits. Developers measured LLSR accepting sources only up to about 960×960 at 2× (OS 26; 1.5× added in OS 27). LLFI was capped at 720p–1080p and cost 8–22 ms per interval on an M2 Max. So LLSR suits a sub-1080p source and cannot take Cha's 1080p/1440p streams to 4K/5K. LLFI is too slow and adds too much latency for a ≤12 ms 120 Hz target. The other effects (`VTSuperResolutionScalerConfiguration`, `VTFrameRateConversionConfiguration`, motion blur, temporal noise filter) need next frames or take hundreds of ms per frame, so they are for offline work only.

### Cited Findings
**API shape and availability**
- The `VTFrameProcessor` class is available from macOS 15.4 and from iOS/tvOS/visionOS 26. You call `startSession(configuration:)`, then `process(parameters:completionHandler:)` (or an AsyncSequence variant) for each frame, then `endSession()`. "The caller needs to ensure that all buffers passed to the processWithParameters interface are unmodified (including attachments) until the function returns or the callback is received." — [Apple: VTFrameProcessor](https://developer.apple.com/documentation/videotoolbox/vtframeprocessor)
- There is also a Metal variant, `process(with: MTLCommandBuffer, parameters:)` (macOS 15.4+): "add the effect to an existing Metal command buffer… for clients that have an existing Metal pipeline." It "waits until all previously inserted tasks in the command buffer finish before running. Tasks inserted after the buffer will run after the effect is applied." — [Apple: process(with:parameters:)](https://developer.apple.com/documentation/videotoolbox/vtframeprocessor/process(with:parameters:))
- WWDC25 session 300, "Enhance your app with machine-learning-based video effects", groups the effects by use. Frame rate conversion, super resolution, motion blur and temporal noise filtering are for editing. Low-latency frame interpolation and super resolution are for "applications with real-time processing needs" such as video calls. — [WWDC25 session 300](https://developer.apple.com/videos/play/wwdc2025/300/); transcript excerpts via [WWDC index (nonstrict.eu)](https://nonstrict.eu/wwdcindex/wwdc2025/300/)

**`VTLowLatencySuperResolutionScalerConfiguration` (LLSR)**
- Available on macOS/iOS/tvOS/visionOS 26.0+. The initialiser is `init(frameWidth:frameHeight:scaleFactor: Float)`. Class queries are `isSupported`, `supportedScaleFactors(frameWidth:frameHeight:)`, `maximumDimensions`, `minimumDimensions`, and (newer) `maximumDimension(forSpatialScaleFactor:)` and `maximumPixelCount(forSpatialScaleFactor:)`. Instance properties are `sourcePixelBufferAttributes`, `destinationPixelBufferAttributes` and `frameSupportedPixelFormats`. Apple warns that "ML model loading may take longer than a frame time. Avoid blocking the UI thread or stalling frame rendering pipelines" during `startSession`. — [Apple: VTLowLatencySuperResolutionScalerConfiguration](https://developer.apple.com/documentation/videotoolbox/vtlowlatencysuperresolutionscalerconfiguration)
- From the WWDC25 transcript: it is "a lightweight super scaler… specifically optimized to enhance the video conferencing experience". It "reduces coding artifacts and sharpens edges". The configuration "only needs frame width, height, as well as the scaling ratio", and the parameters "only require source and destination frame buffers". So it needs no previous or next frame. — [WWDC index transcript](https://nonstrict.eu/wwdcindex/wwdc2025/300/)
- `supportedScaleFactorsForFrameWidth:frameHeight:` "returns an empty list if the processor doesn't support those dimensions". The scale factor passed to the initialiser "must be a supported value" from that call. — [objc2-video-toolbox 0.3.2 docs](https://docs.rs/objc2-video-toolbox/latest/objc2_video_toolbox/struct.VTLowLatencySuperResolutionScalerConfiguration.html)
- A developer measured on an M3 Pro (PR merged 2026-10-25): LLSR accepts sources "up to 960×960 only", "2× only", "8-bit 420v only", on macOS/iOS 26 and not in the simulator. Cost was "about 1.7 ms of wall time per 480p frame… with no added GPU time", with no extra dropped frames at 30 or 60 fps. In the same harness, MetalFX spatial cost "5–10 ms GPU time per frame". — [rkanjani/airwave PR #12](https://github.com/rkanjani/airwave/pull/12)
- A shipping tvOS/Apple player (AetherEngine 7.53.0, published 30 Oct, year not shown) runs `VTLowLatencySuperResolutionScaler` "2x for SD, 1.5x for 720p, read at runtime" on 8-bit SDR sources "below 1920x1080", outputting 420v. MetalFX Spatial then takes the result to display size. On an Apple TV 4K (A15) it measured "ML 3 to 8 ms per frame, MetalFX to 4K 16 to 21 ms". HDR, Dolby Vision, 10-bit and ≥1080p sources are not upscaled. — [AetherEngine release 7.53.0](https://github.com/superuser404notfound/AetherEngine/releases/tag/7.53.0)
- The tvOS 27 Beta 8 notes (build 24J5360a, 2026-08-31) say: "VTLowLatencySuperResolutionScalerConfiguration now supports a 1.5x scale factor." — [betaprofile.dev summary of Apple release notes](https://betaprofile.dev/tvos-27-beta-8/) (third-party mirror of Apple notes; the Apple original was not fetched)
- One offline tool reports that LLSR "accepts no scale factor at 1080p" (M5 Max, macOS 27). — [tsonubin/metafx-upscale](https://github.com/tsonubin/metafx-upscale)
- MetalDuck (a macOS capture-and-upscale tool, draft PR of 2026-09-14) uses `VTLowLatencySuperResolutionScalerConfiguration` and "downscales only the model input when the captured frame is larger than the Apple scaler accepts". It is unvalidated on hardware. — [MetalDuck PR #1](https://github.com/YanisThePie/MetalDuck/pull/1)

**`VTLowLatencyFrameInterpolationConfiguration` (LLFI)**
- Available on macOS 26.0+. There are two initialisers: `init?(frameWidth:frameHeight:numberOfInterpolatedFrames:)` for frame-rate conversion only, and `init?(frameWidth:frameHeight:spatialScaleFactor: Int)` for scaling plus FRC. "This processor requires a source frame and a previous frame… interpolates frames between the previous frame and the source frame. When performing both temporal and spatial interpolation, the processor can only perform 2x upscaling, and a single frame of temporal interpolation… it does not upscale the previous reference frame." The ML-load warning applies here too. — [Apple: VTLowLatencyFrameInterpolationConfiguration](https://developer.apple.com/documentation/videotoolbox/vtlowlatencyframeinterpolationconfiguration)
- WWDC25: it is "intended for enhancing real-time video conferencing" and "upsamples the frame rate with real-time performance". — [WWDC index transcript](https://nonstrict.eu/wwdcindex/wwdc2025/300/)
- On OS 26, `maximumDimensions` and `minimumDimensions` returned nil, and 4K input gave `VTFrameProcessorErrorDomain -19730 "Processor is not initialized"` even though `startSession` succeeded. On an M1 Pro the maximum was 720p (Nov 2025). An Apple engineer replied in June 2026: "In OS 27, we've added APIs for querying the maximum dimensions… `maximumDimension(forSpatialScaleFactor:)`, `maximumPixelCount(forSpatialScaleFactor:)`". The same thread notes that LLFI runs while the app is backgrounded but `VTFrameRateConversion` does not "(due to gpu usage)". — [Apple Developer Forums thread 805338](https://developer.apple.com/forums/thread/805338)
- The tvOS 27 Beta 8 notes say: "VTLowLatencyFrameInterpolationConfiguration now supports arbitrary source dimensions up to 1080p." — [betaprofile.dev](https://betaprofile.dev/tvos-27-beta-8/)
- The macOS 27 SDK diff lists only 5 new VideoToolbox APIs: `maximumDimension(forSpatialScaleFactor:)` and `maximumPixelCount(forSpatialScaleFactor:)`, which return 0 for an unsupported factor, plus compression keys and an Apple Immersive Video projection kind. No new VTFrameProcessor effects were added. — [miniswift.run What's new in VideoToolbox (27 SDK)](https://miniswift.run/whats-new/videotoolbox/)
- Measurements from 60FPSVideo on an M2 Max, macOS 27.0.1: "The low-latency path stops at 1920×1080. At 1280×720 an interval takes 7.99 ms, and at 1920×1080 it takes 22.24 ms. Larger sizes fail silently with -19730, and startSession still reports success." It also reports that `frameSupportedPixelFormats` misreports which formats work, that the Swift `async process()` "silently does no work", and that allocating buffers per frame causes crashes (reuse a pool). With the non-low-latency FRC path, 4K 24→60 cost 84 ms per interval and 1080p cost 31.7 ms. — [wasim-osman/60FPSVideo](https://github.com/wasim-osman/60FPSVideo)

**`VTSuperResolutionScalerConfiguration` (offline, high quality)**
- Available on macOS 26.0+. The initialiser is `init?(frameWidth:frameHeight:scaleFactor: Int, inputType:, usePrecomputedFlow:, qualityPrioritization:, revision:)`. It "may require ML models which the framework needs to download". Check `configurationModelStatus` and call `downloadConfigurationModel(completionHandler:)` "with user awareness". There is also `configurationModelPercentageAvailable`. — [Apple: VTSuperResolutionScalerConfiguration](https://developer.apple.com/documentation/videotoolbox/vtsuperresolutionscalerconfiguration)
- WWDC25: "Two ML models are available for super resolution, one for images and the other for videos." — [WWDC index transcript](https://nonstrict.eu/wwdcindex/wwdc2025/300/)
- Measured: exactly 4×, input at most 1920×1080, half-float RGBA input, about 0.35 s per frame for 720p→4K (≈3 fps) on an M5 Max with macOS 27. SDR only. — [tsonubin/metafx-upscale](https://github.com/tsonubin/metafx-upscale). On an M4 MacBook Air with macOS 27.0.1, 854×480 at 4× took 424 ms per frame of scaling. Header limit is "1920x1080… for video input". On macOS 27 / M4 it accepts only 16-bit float RGBA. (PR merged 2026-10-26.) — [oittaa/vidcut PR #564](https://github.com/oittaa/vidcut/pull/564)

**Frame-rate conversion, optical flow, motion blur, temporal noise filter**
- `VTFrameRateConversionParameters` (macOS 15.4+) takes `sourceFrame`, `nextFrame` ("the next source frame in presentation time order"), optional `opticalFlow`, `interpolationPhase: [Float]`, `submissionMode` and `destinationFrames`. — [Apple: VTFrameRateConversionParameters](https://developer.apple.com/documentation/videotoolbox/vtframerateconversionparameters)
- `VTOpticalFlowConfiguration` (macOS 15.4+): `init?(frameWidth:frameHeight:qualityPrioritization:revision:)`, with `isSupported` and source/destination pixel-buffer attributes. Its output can be passed as precomputed flow to FRC or SR. — [Apple: VTOpticalFlowConfiguration](https://developer.apple.com/documentation/videotoolbox/vtopticalflowconfiguration)
- Motion blur: "Two reference frames are needed… next and previous", and nil is used at the clip boundaries. — [WWDC index transcript](https://nonstrict.eu/wwdcindex/wwdc2025/300/)
- `VTTemporalNoiseFilterConfiguration` (macOS 26.0+): `init?(frameWidth:frameHeight:sourcePixelFormat:)`, `maximumDimensions`/`minimumDimensions`, and `previousFrameCount`/`nextFrameCount` ("maximum number of preceding and subsequent reference frames… to achieve optimum noise-reduction quality"). — [Apple: VTTemporalNoiseFilterConfiguration](https://developer.apple.com/documentation/videotoolbox/vttemporalnoisefilterconfiguration)

### Inferences
- LLSR fits Cha only if the node sends a small stream (≤ about 960 px per side on OS 26, or whatever `maximumDimension(forSpatialScaleFactor:)` reports on OS 27) and the client scales it 1.5× or 2×. Example: 960×540 → 1920×1080, then MetalFX or a shader pass to the panel. It cannot take 1080p/1440p→4K/5K, which was the stated goal ("node sends 1080p/1440p at a lower bitrate"). Cha should still query it at runtime, since limits differ by device and OS.
- LLSR cost looks low (about 1.7 ms wall at 480p on M3 Pro with "no added GPU time"; 3–8 ms on A15). That, plus LLFI running while backgrounded, hints that both run on the Neural Engine rather than the GPU. Apple does not document this (unverified). If true, LLSR would not compete with the PyroWave compute decode for GPU time, but it adds ANE round-trip latency.
- Every interpolation effect (LLFI, FRC) has to hold back the newest decoded frame N until the in-between frame (N-1→N) has been shown. At 60→120 that adds at least one 8.33 ms display interval plus compute (8–22 ms measured for LLFI), which on its own exceeds the 12 ms glass-to-glass target. LLFI could only be an opt-in "smoothness" mode for 60 fps streams where latency matters less.
- FRC, motion blur and TNF need `nextFrame` or future reference frames, which adds at least one source-frame of latency. They are not real-time-capable for interactive streaming.
- Integration pattern: build the destination `CVPixelBufferPool` from `destinationPixelBufferAttributes` merged with Metal-compatible and IOSurface attributes, and pass VideoToolbox decode output in as `VTFrameProcessorFrame`. Check `sourcePixelBufferAttributes` against the decoder's output format, because LLSR is reported as 420v (8-bit video-range NV12) only, so 10-bit HEVC/HDR streams are excluded.

### Gaps
- Apple publishes no official table of LLSR/LLFI scale factors, maximum dimensions, compute unit (ANE vs GPU) or supported Mac models. All numbers above come from developer measurements. No M4 Pro (Cha's dev machine) measurement of LLSR or LLFI was found.
- I could not confirm whether `process(with: MTLCommandBuffer, parameters:)` supports LLSR/LLFI, or only some configurations.
- No WWDC26 session on new VTFrameProcessor effects was found. The macOS 27 SDK diff suggests none were added beyond the dimension queries.
- I did not fetch the `VTMotionBlurConfiguration` page directly.

## 2. Apple MetalFX in Metal 4 (macOS 26) and WWDC26

### Takeaway
MetalFX offers four effects. `MTLFXSpatialScaler` (macOS 13+) is a single-input, game-agnostic upscaler that can run on any decoded video texture and has an `hdr` colour mode. `MTLFXTemporalScaler` and `MTLFXTemporalDenoisedScaler` need renderer jitter, depth and motion vectors. `MTLFXFrameInterpolator` (macOS 26) interpolates between two rendered frames and needs game depth, motion vectors and camera matrices; measured cost was about 11–18 ms per frame on an iPhone 17. For a video client, only the spatial scaler is directly usable. Measured spatial costs conflict (from about 1–2 ms added latency to 5–10 ms of GPU time), so Cha must benchmark at 1440p→4K/5K on M-series. Using video-derived optical flow in the frame interpolator is undocumented and would still carry interpolation latency.

### Cited Findings
- `MTLFXSpatialScalerDescriptor` (macOS 13+) has `inputWidth/Height`, `colorTextureFormat`, `colorProcessingMode`, `outputWidth/Height` and `outputTextureFormat`, plus `supportsDevice(_:)`. Metal 4 adds `makeSpatialScaler(device:compiler:) -> MTL4FXSpatialScaler` and `supportsMetal4FX(_:)`. tvOS availability starts at 27.1. — [Apple: MTLFXSpatialScalerDescriptor](https://developer.apple.com/documentation/metalfx/mtlfxspatialscalerdescriptor)
- `MTLFXSpatialScalerColorProcessingMode` cases are `perceptual`, `linear` and `hdr` ("input and output textures use a high dynamic range color space"). — [Apple: MTLFXSpatialScalerColorProcessingMode](https://developer.apple.com/documentation/metalfx/mtlfxspatialscalercolorprocessingmode)
- `MTLFXFrameInterpolatorDescriptor` (macOS/iOS 26, tvOS 27.1) "inspects two frames your game or app renders and… generates an extra frame". It has `colorTextureFormat`, `depthTextureFormat`, `motionTextureFormat`, `outputTextureFormat`, `uiTextureFormat`, `inputWidth/Height` (motion and depth), `outputWidth/Height`, `requiresPrevColorTexture`, `isDistortionTextureEnabled`, and an optional `scaler: MTLFXFrameInterpolatableScaler`. Methods are `makeFrameInterpolator(device:)` and `makeFrameInterpolator(device:compiler:) -> MTL4FXFrameInterpolator`, plus `supportsDevice` and `supportsMetal4FX`. — [Apple: MTLFXFrameInterpolatorDescriptor](https://developer.apple.com/documentation/metalfx/mtlfxframeinterpolatordescriptor)
- The per-frame properties of `MTLFXFrameInterpolatorBase` are `colorTexture`, `prevColorTexture`, `motionTexture`, `depthTexture`, `uiTexture`, `outputTexture`, `motionVectorScaleX/Y`, `deltaTime`, `fieldOfView`, `aspectRatio`, `nearPlane`, `farPlane`, `jitterOffsetX/Y`, `isDepthReversed`, `isUITextureComposited`, `shouldResetHistory`, `worldToViewMatrix`, `viewToClipMatrix`, an optional `fence: MTLFence`, and `*TextureUsage` minimums for each input and output texture. — [Apple: MTLFXFrameInterpolatorBase](https://developer.apple.com/documentation/metalfx/mtlfxframeinterpolatorbase)
- Measured on an iPhone 17 (A19), iOS 26.6: MetalFX frame interpolation cost about 18 ms per interpolated frame in a game and about 11 ms in a triangle demo at 2622×1206, rising to about 30 ms after thermal state changes. Formats were RGBA16Float colour, Depth32Float and RG16Float motion. Apple DTS replied that it "didn't find published frame interpolation timings for any device". It also pointed to WWDC25 "Go further with Metal 4 games" advice: bind the upscaler via `scaler` "for higher combined performance", set `requiresSynchronousInitialization` when benchmarking temporal scalers, and have "at least 30 frames per second before interpolation". — [Apple Developer Forums thread 853871](https://developer.apple.com/forums/thread/853871) (late Oct / early Nov 2026, relative dates only), referencing [WWDC25 session 211](https://developer.apple.com/videos/play/wwdc2025/211/)
- "MetalFX temporal… needs depth and motion vectors from a game engine, so it can't be used on video files." On an M5 Max, MetalFX spatial ran at about 125 fps for 720p→4K in an offline pipeline. — [tsonubin/metafx-upscale](https://github.com/tsonubin/metafx-upscale)
- MetalFX spatial measured "5–10 ms GPU time per frame" on an M3 Pro with "no visible gain over AVPlayerLayer at 720p". — [airwave PR #12](https://github.com/rkanjani/airwave/pull/12). MetalFX to 4K cost 16–21 ms on an Apple TV 4K (A15). — [AetherEngine 7.53.0](https://github.com/superuser404notfound/AetherEngine/releases/tag/7.53.0)
- Moonlight-qt PR #1557 (open, first posted 2025-03-15) implements macOS upscaling with `MTLFXSpatialScalerDescriptor` in `vt_metal.mm`, tested on M1 Pro and M3 Pro. The author reports "an additional latency less than 1ms in most of the cases, at the maximum I observed 2ms" for 1440p 120 fps 150 Mbps on a dedicated GPU, a figure mostly from Windows testing. "The Mac code has no option to set sharpening." — [moonlight-qt PR #1557](https://github.com/moonlight-stream/moonlight-qt/pull/1557)
- WWDC26: session 357, "Speedrun your game port with agentic coding", covers MetalFX upscaling and frame-interpolation integration "skills" (jitter, motion-vector conventions, a dedicated present thread). It also covers new macOS 27 Metal HUD overlays for checking a MetalFX integration and overriding jitter or motion-vector scales at runtime. — [WWDC26 session 357](https://developer.apple.com/videos/play/wwdc2026/357/) (from a search-result summary; the session page itself was not read)

### Inferences
- The spatial scaler is the only MetalFX effect that fits decoded video. It takes one colour texture and needs no history, so it adds no frame of latency. Feed it the RGB output of Cha's YCbCr→RGB pass rather than raw bi-planar video, rendered at source resolution into an intermediate texture, then letterbox the output. That moves the colour conversion before scaling, unlike today's single pass. For HDR/PQ streams use `colorProcessingMode = .hdr` with a float format such as RGBA16Float. For SDR use `.perceptual`.
- The measured cost spread (sub-ms to 21 ms) probably reflects different devices (A15 vs M-series Pro/Max), different output sizes, and wall time vs GPU time. On M4 Pro at 1440p→2560p/4K, MetalFX spatial should be benchmarked against a WGSL FSR1/SGSR pass before committing (see §7).
- Feeding `MTLFXFrameInterpolator` video optical flow (from `VTOpticalFlowConfiguration` or Vision) with a constant or dummy depth and identity matrices is not documented by Apple and might work poorly (unverified). It would also interpolate between `prevColorTexture` and `colorTexture`, so it has the same at-least-one-frame latency penalty as §1. On the A19 data, even the interpolation compute alone (11 ms+) would exceed the budget.
- wgpu drives classic `MTLCommandBuffer`s, not Metal 4 `MTL4CommandBuffer`, so Cha would use the non-MTL4 factory methods (`makeSpatialScaler(device:)`) (inference).

### Gaps
- No Apple-published cost figure for any MetalFX effect, and no independent M4/M4 Pro measurement of `MTLFXSpatialScaler` at 1440p→4K/5K.
- I did not confirm the maximum spatial scale factor or the input size limits for `MTLFXSpatialScaler`.
- No new MetalFX API from WWDC26 was confirmed beyond tooling (HUD overlays) and tvOS 27.1 availability.

## 3. Interop with wgpu (Metal HAL, IOSurface/CVPixelBuffer, sync) and Rust crates

### Takeaway
Zero-copy interop is possible, through wgpu's HAL escape hatches. Get the `MTLDevice` with `Device::as_hal::<Metal>`. Make `MTLTexture`s from IOSurface-backed CVPixelBuffers via `CVMetalTextureCache`, and wrap them as wgpu textures with `create_texture_from_hal::<Metal>` / `texture_from_raw`. Run MetalFX or `VTFrameProcessor` on those raw textures and command buffers. `objc2-video-toolbox` 0.3.2 and `objc2-metal-fx` 0.3.2 already bind LLSR, VTFrameProcessor, the spatial and temporal scalers and the frame interpolator, including the MTL4FX variants. Synchronisation has to be handled by hand: same-queue ordering, `MTLFence`, `MTLSharedEvent`, or `process(with: commandBuffer, …)`.

### Cited Findings
- `vtsampler` 0.1.1 gets the raw `MTLDevice` with `wgpu_device.as_hal::<Metal, _, _>(…)` → `device.raw_device().lock().clone()`. It makes a `CVMetalTextureCache`, calls `CVMetalTextureCacheCreateTextureFromImage` per plane (NV12 → Y `R8Unorm` plane 0, UV `RG8Unorm` plane 1) and `CVMetalTextureGetTexture`, then wraps the result with `create_texture_from_hal::<Metal>(<Metal as Api>::Device::texture_from_raw(…))` and calls `CVMetalTextureCacheFlush`. It then does `copy_texture_to_texture` into a wgpu-owned texture, so it is not fully zero-copy, and it uses no explicit fences. — [vtsampler 0.1.1 bridge/metal.rs](https://docs.rs/crate/vtsampler/0.1.1/source/src/bridge/metal.rs)
- "You can't create a CVMetalTextureRef if your CVPixelBuffer doesn't have an IOSurface", so IOSurface backing is required for zero-copy. — [Apple Developer Forums thread 670457 (via search summary)](https://developer.apple.com/forums/thread/670457)
- `objc2-video-toolbox` 0.3.2 exposes `VTLowLatencySuperResolutionScalerConfiguration` behind the feature `VTFrameProcessor_LowLatencySuperResolutionScaler`, plus `objc2-foundation`/`objc2-core-media` for the dictionary and dimension getters. Methods include `initWithFrameWidth_frameHeight_scaleFactor`, `supportedScaleFactorsForFrameWidth_frameHeight`, `maximumDimensions`, `frameSupportedPixelFormats`, and `source/destinationPixelBufferAttributes`. — [docs.rs objc2-video-toolbox](https://docs.rs/objc2-video-toolbox/latest/objc2_video_toolbox/struct.VTLowLatencySuperResolutionScalerConfiguration.html)
- `objc2-metal-fx` 0.3.2 (Zlib/Apache-2.0/MIT; depends on objc2-metal ^0.3.2) exports `MTLFXSpatialScalerDescriptor`, `MTLFXTemporalScalerDescriptor`, `MTLFXTemporalDenoisedScalerDescriptor`, `MTLFXFrameInterpolatorDescriptor` and `MTLFXSpatialScalerColorProcessingMode`. Its traits include `MTLFXSpatialScaler`, `MTLFXFrameInterpolator`, `MTLFXFrameInterpolatableScaler`, `MTL4FXSpatialScaler` and `MTL4FXFrameInterpolator`. — [docs.rs objc2-metal-fx](https://docs.rs/objc2-metal-fx/latest/objc2_metal_fx/)
- MetalFX interpolator objects take an optional `fence: MTLFence` ("waits for and updates") and declare minimum `MTLTextureUsage` per texture (`colorTextureUsage`, `outputTextureUsage`, …). — [Apple: MTLFXFrameInterpolatorBase](https://developer.apple.com/documentation/metalfx/mtlfxframeinterpolatorbase)
- `VTFrameProcessor.process(with:parameters:)` inserts the effect into an existing `MTLCommandBuffer`, ordered after earlier work and before later work. — [Apple](https://developer.apple.com/documentation/videotoolbox/vtframeprocessor/process(with:parameters:))

### Inferences
- Recommended Cha pattern on macOS:
  1. Allocate IOSurface-backed CVPixelBuffer pools, with LLSR's `destinationPixelBufferAttributes` if LLSR is used.
  2. Create the MetalFX input and output textures yourself with the usage flags MetalFX asks for (`shaderRead`, `shaderWrite`, `renderTarget`, private storage). wgpu-created textures may not carry them.
  3. Import those textures into wgpu with `texture_from_raw` so egui and the letterbox pass can sample them.
  4. Encode MetalFX on a raw `MTLCommandBuffer` from the same `MTLCommandQueue` wgpu uses, which gives implicit queue ordering. Otherwise use a separate queue and signal or wait on an `MTLSharedEvent` around wgpu's submission.
- How to reach wgpu's raw queue or command buffer depends on the wgpu version (`Queue::as_hal`, `CommandEncoder::as_hal_mut`). I did not verify the current method names (unverified). Pin a wgpu version and check `wgpu-hal::metal` before implementing.
- The VTFrameProcessor completion-handler path is asynchronous on its own queue. Cha should treat it like decode output: wait for the callback, then hand the destination CVPixelBuffer to the render thread. The `process(with: MTLCommandBuffer)` variant could avoid a CPU hop if Cha has the raw command buffer.

### Gaps
- No wgpu issue or PR describing an official external-texture or IOSurface import API for Metal (as of 2026-11) was found in this pass.
- No measured overhead for the CVPixelBuffer→MTLTexture→wgpu wrap.
- No public Rust example of VTFrameProcessor or MetalFX driven from wgpu was found, only `vtsampler` (texture import) and Moonlight's Objective-C++ (`vt_metal.mm`).

## 4. Optical flow on Apple platforms for client-side interpolation

### Takeaway
Two flow sources exist: `VTOpticalFlowConfiguration` (VideoToolbox, macOS 15.4+, made to feed FRC/SR) and Vision's `VNGenerateOpticalFlowRequest` (macOS 11+). Neither publishes a per-frame cost. Vision calls its requests "very resource intensive". Neither is a low-latency path, and any interpolation built on them inherits the hold-back latency of §1.

### Cited Findings
- `VTOpticalFlowConfiguration`: `init?(frameWidth:frameHeight:qualityPrioritization:revision:)`, `isSupported`, `supportedRevisions`. Flow is a `VTFrameProcessorOpticalFlow` that can be passed to `VTFrameRateConversionParameters(opticalFlow:)`, and `VTSuperResolutionScalerConfiguration` has `usesPrecomputedFlow`. — [Apple: VTOpticalFlowConfiguration](https://developer.apple.com/documentation/videotoolbox/vtopticalflowconfiguration); [Apple: VTFrameRateConversionParameters](https://developer.apple.com/documentation/videotoolbox/vtframerateconversionparameters); [Apple: VTSuperResolutionScalerConfiguration](https://developer.apple.com/documentation/videotoolbox/vtsuperresolutionscalerconfiguration)
- `VNGenerateOpticalFlowRequest` (iOS 14 / macOS 11+): Apple says to create one request at a time and release it right after use because these requests are resource-intensive. The two frames must match in size, a region of interest is still reported at full resolution, and `computationAccuracy` is Low/Medium/High/VeryHigh. — [Apple: VNGenerateOpticalFlowRequest](https://developer.apple.com/documentation/vision/vngenerateopticalflowrequest); [objc2-vision 0.3.2](https://docs.rs/objc2-vision/0.3.2/objc2_vision/struct.VNGenerateOpticalFlowRequest.html)
- Non-low-latency FRC (flow plus interpolation) on M2 Max cost 31.7 ms per interval at 1080p and 84 ms at 4K. — [60FPSVideo](https://github.com/wasim-osman/60FPSVideo)

### Inferences
- Client-side flow plus warp could only make sense as extrapolation (warping frame N forward with flow from N-1→N) to avoid holding frames back. None of the Apple APIs offers extrapolation, and its quality on game content is unproven.
- A cheaper "motion" source for a game stream is the node: encoder motion vectors or the game's own vectors. That is covered by other researchers (node side / codec side).

### Gaps
- No published ms-per-frame for `VNGenerateOpticalFlowRequest` or `VTOpticalFlowConfiguration` on any M-series chip.
- No documentation of the flow texture format or resolution of `VTFrameProcessorOpticalFlow` was retrieved.

## 5. Windows: NVIDIA, Microsoft, AMD, Intel

### Takeaway
On Windows the practical client-side upscalers for live game video are (a) NVIDIA RTX Video Super Resolution, either through the RTX Video SDK (v1.1: DX11/DX12/Vulkan/CUDA, RTX 20+) or through the driver's D3D11/D3D12 video-processor extension that mpv, VLC and Moonlight's PR use, (b) AMD's AMF Video Upscaling and Intel's VSR / FSR1 shaders, and (c) your own FSR1/SGSR/NIS shader. Microsoft's Windows App SDK `VideoScaler` (VSR) is an NPU/CPU-only model for "people in conversation", capped at 1440p output and 15–60 fps, so it does not fit 120 fps game streams. Auto SR, DirectSR and AFMF are game or driver features with no app API. All frame-generation options on Windows (NvOFFRUC, AFMF, Lossless Scaling) are interpolation-based and add latency.

### Cited Findings
**NVIDIA**
- RTX Video SDK provides VSR ("1080p, low-bitrate video into a crisp, clear 4K image", which also removes blocky compression artifacts) and RTX Video HDR (SDR→HDR10). It is aimed at "creative and media playback apps" and "real-time, video-enhanced playback". — [NVIDIA RTX Video SDK](https://developer.nvidia.com/rtx-video-sdk)
- Getting started: download `rtx_video_sdk_v1.1.0.zip`. APIs are "DX11, DX12, Vulcan [sic], CUDA", on "64-bit Win10+". Requires "GeForce RTX 20 series or newer (Turing), NVIDIA RTX 1000 or higher". Release notes add "Native CUDA support", "Support for RTX 50 series (Blackwell)" and "Super resolution support for 10-bit video". Effects are super resolution, artifact reduction and SDR→HDR. No Linux is listed. — [NVIDIA RTX Video SDK getting started](https://developer.nvidia.com/rtx-video-sdk/getting-started)
- The model family is "DLPP, aka RTX VSR… lightweight deep-learning networks trained for video post-processing", and its runtime is the CASK SDK. — [NGC DLPP 2.0](https://catalog.ngc.nvidia.com/orgs/nvidia/multimedia/models/dlpp/2.0) (via search summary)
- Driver path: mpv `vf=d3d11vpp=scale=2:scaling-mode=nvidia` (also `intel`, `standard`) hands frames to the D3D11 video processor and the driver does VSR. It needs "Super Resolution" enabled under RTX Video Enhancements in the NVIDIA App. A community script switches 10-bit HEVC to NV12 because VSR did not support it. — [ithome guide](https://ithelp.ithome.com.tw/articles/10402152); [mpv PR #14155](https://github.com/mpv-player/mpv/pull/14155); [autoscale gist](https://gist.github.com/natyusha/e230a176d41e3092676c4e941ded406a) (community sources, via search summary)
- Moonlight-qt PR #1557 (open since 2025-03-15): NVIDIA VSR is implemented as "a Video Processor component added to D3D12VA". AMD uses "AMF Video Upscaling, a ML model based on FSR1". Intel uses an FSR1 shader ("IntelVPL shall be workable but could not make it work yet"). Linux and macOS are also covered. Tested on RTX 4070 Ti, GTX 1050, RX 7600, 780M, Arc A380, N95 and Snapdragon Adreno. Added latency was "less than 1ms in most of the cases, at the maximum I observed 2ms" at 1440p120 150 Mbps on a dGPU, and an N95 iGPU topped out at 1440p60. "Nvidia does not support HDR yet so the application automatically disables the enhancement." Quality ranking: "AMD delivers the best results, followed by Nvidia, then Intel." — [moonlight-qt PR #1557](https://github.com/moonlight-stream/moonlight-qt/pull/1557)
- NVIDIA Optical Flow SDK runs on Turing/Ampere/Ada hardware ("independent of CUDA cores"). SDK 3.0 adds "a DirectX12 Interface, forward and backward flow and a global flow vector". "NvOFFRUC interpolates new frames using optical flow vectors to double the effective frame rate of a video." No numeric cost is given in the text. — [NVIDIA Optical Flow SDK](https://developer.nvidia.com/optical-flow-sdk)

**Microsoft**
- Windows App SDK VSR (`Microsoft.Windows.AI.Video.VideoScaler`, doc updated 2026-10-01) runs on the NPU on Copilot+ PCs, or on the CPU otherwise; "GPU ❌ Not supported". It is "designed specifically for… video calling and conferencing apps and social and short-form videos that feature human faces". Input 240p–1440p, output 480p–1440p (4K only offline), 15–60 fps. The Direct3D path takes NV12 and outputs BGRA or NV12. The API flow is `GetReadyState` → `EnsureReadyAsync` → `CreateAsync` → `Scale(inputD3dSurface, outputD3dSurface, VideoScalerOptions)`. The model ships with the SDK (no download). — [Microsoft Learn: Video super resolution](https://learn.microsoft.com/en-us/windows/ai/apis/video-super-resolution)
- `VideoScaler` reportedly reached stable in Windows App SDK 2.2.0 (2026-06-09), and Clipchamp uses it (Sept 2026). — [Windows App SDK 2.x release notes](https://learn.microsoft.com/en-my/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-2-0); [Impress Forest Watch](https://forest.watch.impress.co.jp/docs/news/2143092.html) (via search summary; exact version unverified)
- Auto SR (2026-04-30 preview on ROG Xbox Ally X, docked) is for "DirectX games (DX10 or later)" and runs on the NPU. It gives "high-quality super resolution… in exchange for a frame of latency" with "essentially no frame time overhead", whereas "GPU-based models are limited to about 1–2 ms per frame". It is enabled through Game Bar with no developer API. — [DirectX blog: Auto SR preview](https://devblogs.microsoft.com/directx/autosrpreview/). It was extended to Intel Core Ultra Series 3 Copilot+ PCs on 2026-09-16. — [DirectX blog: Auto SR on Intel](https://devblogs.microsoft.com/directx/autosr-on-intel/) (via search summary). The support page lists Snapdragon X/X2 Copilot+ and Windows 11 24H2+. — [Microsoft Support: Auto SR](https://support.microsoft.com/topic/5d6d95fa-cc02-4673-b62c-2c50f06385aa)
- DirectSR is Microsoft's game super-resolution API spec. — [DirectSR spec](https://microsoft.github.io/DirectX-Specs/DirectSR/DirectSR.html) (not re-read in this pass; that it requires depth, motion vectors and jitter like other temporal game upscalers is unverified here)

**AMD / Intel**
- AFMF 2 (Adrenalin 24.9.1) supports "OpenGL, Vulkan, DX11, and DX12 games" and "improved compatibility with borderless windowed mode". The windowed-video feature that shipped alongside it is Geometric Downscaling (RDNA 3 only), not frame generation. — [Tom's Hardware, 24.9.1](https://www.tomshardware.com/pc-components/gpu-drivers/amd-2491-drivers-mark-the-proper-debut-of-universal-fluid-motion-frames-2-along-with-improved-geometric-downscaling)
- AFMF 2.1 added "Fast Motion Response" (Adrenalin 25.9.2) for fast game scenes. — [Igor'sLAB](https://www.igorslab.de/en/amd-expands-afmf-2-1-with-fast-motion-response-finally-an-answer-to-fast-game-scenes/) (via search summary). A user report that AFMF worked on video via Vulkan/DXVK in MPC-HC applied only to an old preview driver. — [KitGuru](https://www.kitguru.net/gaming/joao-silva/amd-fluid-motion-frames-also-works-for-video/) (dated, unofficial)
- Lossless Scaling 3 (Windows, any window): at a 40→80 fps base it measured 41.70 ms total latency vs 54.31 ms for LSFG 2. The developer advises keeping high multipliers for 240 Hz+ displays. — [Tom's Hardware](https://www.tomshardware.com/video-games/pc-gaming/lossless-scaling-3-update-touts-greatly-improved-latency-and-performance-universal-frame-gen-tool-boasts-24-percent-reduced-latency)

### Inferences
- For a Windows Cha Player (likely wgpu on D3D12 or Vulkan), the best ML option is the RTX Video SDK on RTX 20+ GPUs, called on the decoded NV12/P010 texture before presentation. A widely used fallback is the D3D11/D3D12 video-processor path with the NVIDIA or Intel extension, which needs the NVIDIA App toggle. Moonlight's PR suggests about 1–2 ms added at 1440p120 on dGPUs. For AMD, AMF Video Upscaling is the vendor option.
- The RTX Video SDK licence and AGPL compatibility are unknown. A proprietary NVIDIA runtime loaded dynamically is the usual pattern (unverified for this SDK).
- Windows `VideoScaler` is out for Cha's main use: no GPU path, a 60 fps cap, a 1440p output cap, and a face-content focus. Auto SR, DirectSR and AFMF cannot be called by an app on decoded frames. AFMF and Lossless Scaling are user-toggled overlays that interpolate, adding at least one frame of latency.
- NvOFFRUC is a callable frame interpolator for apps but has the same hold-back latency. It is only reasonable as an opt-in 60→120 "smooth" mode.

### Gaps
- No RTX Video SDK per-frame cost table, input/output limits, quality-level list or licence text was retrieved.
- No NvOFFRUC ms-per-frame figure was found (the chart had no values in the text).
- The AMD 2026 article "Upscale Everything: Super-Resolution Across AMD Hardware" returned HTTP 503. AMF Video Upscaling cost and limits are unconfirmed.
- No Intel frame-generation driver feature for arbitrary apps was found. Intel VSR is available only via the D3D11 VP extension (community sources).

## 6. Linux / Steam Deck client

### Takeaway
On Linux the client-side options are compositor-level (gamescope `-F fsr|nis|sgsr` applies to whatever runs nested, including a streaming client), a Vulkan-layer frame generator (lsfg-vk, Lossless Scaling FG v3.1, now CC BY-NC-ND 4.0 and needing the paid Windows app), or the client's own compute pass (FSR1/SGSR on Vulkan). No NVIDIA RTX Video SDK exists for Linux. I found no evidence of a VA-API super-resolution filter usable for this.

### Cited Findings
- gamescope filters: `-F fsr` ("AMD FidelityFX Super Resolution 1.0"), `-F nis` ("NVIDIA Image Scaling v1.0.3") and `-F sgsr` ("Snapdragon Game Super Resolution 1 with RCAS sharpening"). `-w/-h` set the nested app's resolution and `-W/-H` the output. FSR sharpness is adjusted at runtime with Super+I/O. Compositing uses "async Vulkan compute, meaning you get to see your frame quick even if the game already has the GPU busy". ReShade effects "will increase latency". — [ValveSoftware/gamescope README](https://github.com/ValveSoftware/gamescope)
- lsfg-vk "ports the most popular feature from the Windows-exclusive Lossless Scaling program to Linux". It uses a Vulkan layer for "Lossless Scaling Frame Generation v3.1 in every Vulkan application". It is "licensed under CC BY-NC-ND 4.0", has a Qt6 GUI, and has moved to lsfg-vk.dev. — [lsfg-vk.dev](https://lsfg-vk.dev/); [GitHub migration notice](https://github.com/PancakeTAS/lsfg-vk)
- lsfg-vk requires that you "have purchased Lossless Scaling on Steam" (2025-07-07). — [GamingOnLinux](https://www.gamingonlinux.com/2025/07/lsfg-vk-aims-to-bring-lossless-scalings-frame-generation-to-linux/)
- Moonlight-qt PR #1557 claims Linux support and was tested on RTX 4070 Ti and GTX 1050 under Linux. The backend used on Linux is not stated in the captured text. — [moonlight-qt PR #1557](https://github.com/moonlight-stream/moonlight-qt/pull/1557)
- The RTX Video SDK lists only "64-bit Win10+". — [NVIDIA](https://developer.nvidia.com/rtx-video-sdk/getting-started)

### Inferences
- Steam Deck (1280×800 panel) rarely needs client upscaling on its own screen. Docked to a 4K TV, the cheapest route is to let gamescope apply FSR/NIS/SGSR to the Cha Player window (zero code), or to ship an in-client FSR1/SGSR Vulkan compute pass after Vulkan Video or VA-API decode.
- lsfg-vk cannot be bundled with or recommended as part of an AGPL project: its licence is non-commercial and no-derivatives, and it depends on a paid proprietary DLL. It also interpolates, adding latency. At most it is something a user could add themselves.

### Gaps
- No measurements of lsfg-vk or gamescope FSR applied to a streaming client (Moonlight or similar) were found.
- No VA-API super-resolution or AI-scaling filter (e.g. Intel media-driver VPP SR) was confirmed in this pass.
- No Vulkan Video decode → compute upscaler latency measurement on Steam Deck was found.

## 7. Cross-platform shader and ML options for a native renderer

### Takeaway
The most portable low-latency choice is a single-pass spatial shader written once in WGSL and run in Cha's existing wgpu pipeline on all three OSes: SGSR1 (one pass, 12-tap, BSD-3), FSR1 (EASU + optional RCAS), or NIS. It needs no history and no vendor runtime, and GPU-based SR is commonly budgeted at about 1–2 ms per frame. Vendor ML paths (Apple LLSR on ANE, NVIDIA RTX VSR, Windows VSR on NPU) give better artefact removal but are size-limited, platform-specific, or (Windows VSR) not designed for 120 fps. Offline-quality ML SR (VTSuperResolutionScaler, Real-ESRGAN) costs hundreds of ms per frame.

### Cited Findings
- FSR1 = EASU (edge-adaptive spatial upsampling) + optional RCAS. Input "should already be well anti-aliased", "normalized to [0-1] and be in perceptual color space (sRGB, not linear)" and noise-free. It is applied after tone mapping and before film grain and UI. "A negative input to RCAS will output NaN!" — [AMD GPUOpen FSR1 manual](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-spatial/)
- SGSR1 "integrates upscaling and sharpening in one single GPU shader pass", "requires only a single input texture" and uses a "12-tap Lanczos-like scaling filter". It is BSD 3-clause. SGSR2 is the temporal variant. — [SnapdragonStudios/snapdragon-gsr](https://github.com/SnapdragonStudios/snapdragon-gsr)
- gamescope ships FSR1, NIS v1.0.3 and SGSR1 as compositor filters, which shows they are fast enough for per-frame compositor use. — [gamescope README](https://github.com/ValveSoftware/gamescope)
- "GPU-based models are limited to about 1–2 ms per frame" (Microsoft's framing for game SR), whereas the NPU-based Auto SR costs "a frame of latency". — [DirectX blog](https://devblogs.microsoft.com/directx/autosrpreview/)
- Offline ML SR, 720p→4K seconds per frame: bicubic 0.09, Real-ESRGAN general-x4v3 0.48, Real-ESRGAN x4plus 6.4, RealBasicVSR 2.7 (engine not specified). Apple `VTSuperResolutionScaler` about 0.35 s. Measured on an M5 Max with macOS 27. — [tsonubin/metafx-upscale](https://github.com/tsonubin/metafx-upscale)
- Apple's real-time ML option, LLSR, measured about 1.7 ms wall per 480p frame (M3 Pro) and 3–8 ms (A15), size-limited as in §1. — [airwave PR #12](https://github.com/rkanjani/airwave/pull/12); [AetherEngine 7.53.0](https://github.com/superuser404notfound/AetherEngine/releases/tag/7.53.0)
- Windows' NPU VSR: 15–60 fps, ≤1440p output, no GPU path. — [Microsoft Learn](https://learn.microsoft.com/en-us/windows/ai/apis/video-super-resolution)

### Inferences
- For Cha, a WGSL port of SGSR1 or FSR1 EASU+RCAS is the baseline to build first. It slots in after the YCbCr→RGB pass (sRGB-encoded, [0,1]) and before egui and letterboxing, and works on Metal, Vulkan and D3D12 through wgpu. Expected cost on M4 Pro at 1440p→4K is around 1 ms or less, but this is an estimate (unverified; not measured in any source found). Compression noise breaks FSR1's "noise-free" assumption, so a light deblock or denoise step, or keeping RCAS sharpening low, may be needed for low-bitrate streams.
- Platform-specific ML paths can then be added behind capability checks: MetalFX spatial on macOS (benchmark it against the WGSL pass), Apple LLSR for sub-960 px streams, and RTX VSR or AMF on Windows.
- A custom Core ML or ONNX Runtime (DirectML/CoreML EP) SR model is possible, but I found no real-time (≤2 ms at 1440p→4K) measured example. Real-time SR models in that cost class are typically tiny CNNs. This is a research effort, not an off-the-shelf API.
- Frame interpolation on the client, from any vendor, conflicts with a ≤12 ms 120 Hz target because it holds back real frames. If Cha wants more frames, the better levers are a higher source fps from the node or extrapolation/reprojection with node-supplied motion data (other researchers' scope).

### Gaps
- No measured WGSL or wgpu FSR1/SGSR/NIS timings on Apple M-series were found.
- No ONNX Runtime/DirectML or Core ML real-time video-SR benchmark at 1080p/1440p input was found.
- No data on ANE contention between Core ML models and VideoToolbox's LLSR/LLFI.
