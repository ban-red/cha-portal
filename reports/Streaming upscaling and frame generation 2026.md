# Upscale inside the game, ration generated frames

Cha Portal should upscale where the motion vectors live and treat frame generation as a latency cost it spends only on request. The strongest move available in November 2026 sits on the node: the game's own temporal upscaler (DLSS 4.5's second-generation transformer on the RTX 4090, FSR 4 or 4.1 on AMD) now runs under Proton and can be forced on headlessly with environment variables in the gamescope launch, for roughly 1–1.4 ms of 4090 GPU time at 4K in one tester's measurement, with nothing changed in gamescope, the compositor, the encoders or any client. On the client, the first build is one MIT- or BSD-licensed WGSL spatial pass (SGSR 1 or FSR 1) for game streams that arrive below panel size, landing in the native Cha Player and the PyroWave WebGPU path first and in the WebCodecs path only if a prototype shows it can keep the fast `<video>` presenter; desktops should not be upscaled at all but streamed at the panel's native size, because no spatial filter restores glyphs the 2560×1440 cap has thrown away. Frame generation runs the other way: every shipping generator interpolates and therefore holds back a real frame, and the measured +6 ms at high base rates (about +10 ms at 60→120) exceeds Cha's entire ~5 ms LAN send→shown path, so it earns only an opt-in node-side DLSS FG 2× mode for slow games, while the client-side synthesis worth building adds no hold at all — warping a late or lost frame now, rotation-only input reprojection in the native player later. AV1 superres (Chrome's hardware decoder rejects it), LCEVC (patent royalties), lsfg-vk and Framegen's weights (non-commercial licences), Apple's low-latency interpolator (8–22 ms per interval) and browser ML super-resolution (WebNN unshipped, ~30 ms per 1440p frame estimated on a base M4) should all be rejected. Because nearly every client-side cost figure is a single developer's measurement or a researcher's extrapolation, and Cha still cannot measure glass-to-glass latency, the first task is instrumentation and the second is a short list of benchmarks that decides everything after rank four.

*Evidence tags used throughout:* **[V]** vendor claim; **[D]** single developer, single tester or PR author; **[R]** research paper measuring its own method; **[I]** independent measurement by a press lab or third-party study; **[E]** the researchers' own estimate or arithmetic, measured by nobody; **[C]** Cha Portal's own measurement.

## Node-side temporal upscaling is the cheapest win and changes nothing downstream

The game process is the only point in Cha's pipeline that holds per-pixel motion vectors, depth, camera jitter and a HUD-less colour buffer, and upscaling there also cuts render time, so frames finish sooner rather than later. By late 2026 that path works on the test node. NVIDIA's Linux gaming guide (595–615 editions) says DXVK-NVAPI ships with Proton and exposes **DLSS Super Resolution, Frame Generation, Ray Reconstruction and DLAA** to NVAPI games ([NVIDIA driver guide](https://docs.nvidia.com/datacenter/tesla/driver-installation-guide/gaming.html)). DLSS 4.5's second-generation SR model, announced at CES 2026, runs on every RTX generation, while 6× and Dynamic Multi Frame Generation are RTX 50 only ([NVIDIA](https://www.nvidia.com/en-us/geforce/news/dlss-4-5-dynamic-multi-frame-gen-6x-2nd-gen-transformer-super-res/)). One tester measured DLSS SR at 4K Performance on an RTX 4090 at **0.51 ms (CNN), 1.06 ms (transformer preset K) and 1.39 ms (4.5 model M) per frame [D]** ([Medium](https://medium.com/@opinali/dlss-strikes-again-transformer-v2-04e44e63d5fc)) — small against the render time saved by shading a quarter of the pixels. AMD nodes have a matching path: vkd3d-proton 3.0 enabled FSR 4 on RDNA 4 through FP8 cooperative matrices, and Proton Experimental brought FSR 4.1's INT8 model to RDNA 3 dGPUs in June 2026 ([vkd3d-proton](https://github.com/HansKristian-Work/vkd3d-proton/releases); [GamingOnLinux](https://www.gamingonlinux.com/2026/06/amd-fsr-4-lands-on-rdna3-dgpus-for-linux-steamos-and-steam-machine-via-proton-experimental/)). Intel nodes lag, since XeSS under Proton runs only its non-XMX fallback with no frame generation ([TweakTown](https://www.tweaktown.com/news/114176/intel-is-working-on-adding-xmx-acceleration-for-xess-to-valves-proton/index.html)), and FSR Redstone's ML frame generation has launched only on Windows ([Phoronix](https://www.phoronix.com/news/AMD-FSR-SDK-2.1)).

### Environment variables replace the NVIDIA app's overrides

Everything the NVIDIA app's DLSS override does on Windows, Cha can do per container. `PROTON_ENABLE_NGX_UPDATER=1` swaps a game's shipped DLSS SR, FG and RR DLLs for current ones; `DXVK_NVAPI_DRS_NGX_DLSS_SR_OVERRIDE=on` with `DXVK_NVAPI_DRS_NGX_DLSS_SR_OVERRIDE_RENDER_PRESET_SELECTION=render_preset_latest` forces SR and the newest preset; and `DXVK_NVAPI_SET_NGX_DEBUG_OPTIONS=DLSSIndicator=1024` draws NVIDIA's on-screen indicator, which is how to prove DLSS is running inside the container (it persists in the prefix, so reset it to 0 afterwards) ([NVIDIA 615 guide](https://docs.nvidia.com/datacenter/tesla/driver-installation-guide/615/gaming.html)). dxvk-nvapi 0.9.1 added DRS variables that pin the SR scaling ratio, and with it the internal resolution ([dxvk-nvapi](https://github.com/jp7677/dxvk-nvapi/releases)). In Cha's stack these belong in the environment of [`images/steam/steam-gaming`](../images/steam/steam-gaming), which Steam and its games inherit, or in per-title launch options, on top of the `nvngx.dll` bind the node already makes through `CHA_NVIDIA_WINE_DIR`. The recipe only helps games that already integrate DLSS; some titles block DLL updates, preset overrides do not reach native Linux games, and the available presets depend on the Proton release. On AMD nodes the equivalent is Proton Experimental's built-in FSR 4.1, or `PROTON_FSR4_UPGRADE` and `PROTON_FSR4_RDNA3_UPGRADE` in Proton-CachyOS and GE ([proton-cachyos](https://github.com/DevL0rd/proton-cachyos)). OptiScaler, which can redirect DLSS-only games to FSR 4, is a per-game DLL drop-in whose licence nobody on the research team checked, so Cha should permit it as user-supplied and not bundle it.

### Reflex needs driver R615 for Vulkan games

Reflex belongs in the same launch because it shortens the render queue whether or not frame generation is on. D3D games get it from dxvk-nvapi with no setup. Vulkan games need either the `DXVK_NVAPI_VKREFLEX=1` layer, which required a vkroots fix in dxvk-nvapi 0.9.2 to coexist with gamescope's WSI layer, or the layer-less `VK_NV_low_latency2` path in dxvk-nvapi 0.9.3 (30 October 2026), which requires **driver R615** ([dxvk-nvapi](https://github.com/jp7677/dxvk-nvapi/releases)). A fleet pinned to the 580 series misses the newest Linux features, so tracking R615 is a prerequisite rather than an option.

### gamescope's filters stay off by default

gamescope is the wrong place for upscaling. Upstream gamescope 3.17.0 (23 October 2026) still has no frame generation and only spatial filters — FSR 1, NIS and, according to its README, SGSR 1, although one researcher found no SGSR in upstream sources, so `gamescope --help` on the node should settle it ([gamescope README](https://github.com/ValveSoftware/gamescope); [tags](https://github.com/ValveSoftware/gamescope/tags)). Those filters run only when `-w/-h` is smaller than `-W/-H`, and Cha launches with `-W "$w" -H "$h" -w "$w" -h "$h"`, so no filter runs; that should remain the default. Setting `-w` below `-W` with `-F fsr|nis` is worth keeping only as a node-capacity fallback for heavy games with no temporal upscaler on weak GPUs, because it is the same spatial algorithm the client could run, applied before the encoder: it saves render time but no bandwidth.

### LAN sessions should let DLSS reconstruct to panel size

This settles where most game-session upscaling should happen. When bits are plentiful — 1 GbE with PyroWave or high-rate HEVC/AV1 — DLSS should reconstruct straight to the size the client displays and the stream should carry that size, leaving the client to decode. When bits are scarce, the same DLSS output targets a reduced stream size and the client's spatial pass does the last step. Industry practice agrees: Apollo, Vibepollo and Punktfunk all converged on per-client virtual displays at the client's native resolution ([Apollo](https://github.com/ClassicOldSong/Apollo); [Punktfunk](https://docs.punktfunk.unom.io/docs)), and Valve shipped PyroWave in Steam Remote Play on the bet that, on wired LANs, more bits beat reconstruction ([GamingOnLinux](https://www.gamingonlinux.com/2026/09/steam-beta-adds-experimental-new-pyrowave-video-codec-for-remote-play/)).

## The 2560×1440 cap creates the client's upscaling problem, and one WGSL pass solves most of it

`requestSize` in [`web/packages/player/src/player.ts`](../web/packages/player/src/player.ts) scales the element's device-pixel size by `min(1, 2560/w, 1440/h)`, so a full-screen element on a 3024×1964 MacBook Pro panel requests about **2216×1440** — the height binds — and Chrome stretches it **1.36× bilinearly**.

### Desktops need native pixels, not a sharper stretch

For desktops the fix is not a filter. No spatial upscaler recreates glyph detail at a non-integer ratio and sharpeners put halos on text [E], whereas AV1's screen-content tools save **up to 80% versus H.264** by Meta's account [V] ([@Scale](https://atscaleconference.com/av1-improving-rtc-video-quality-at-scale/)) and Intel's Xe2/Xe3 VA-API AV1 encoder exposes palette and IntraBC ([intel/media-driver caps](https://raw.githubusercontent.com/intel/media-driver/master/media_softlet/linux/xe2_hpm_r0/encode/av1/ddi/capstable_data_av1_encode_xe2_hpm_r0_specific.h)). Desktop mode should therefore request the panel's native size — **1.86× today's pixels** — spend bits on screen-content tools and 4:4:4, and cut frame rate rather than resolution under congestion. The cost is real on PyroWave: Cha's plan records that 4:4:4 at 580 Mbit/s already saturated the owner's link and that PyroWave's byte budget does not yet follow the rate controller [C] ([docs/PLAN.md](../docs/PLAN.md)), and an intra-only codec's bits grow roughly with pixel count [E], so that budget has to be fixed before PyroWave's cap rises.

### Single-frame shaders are the only upscalers that fit the budget

Game streams below panel size are where client upscaling earns its place, and the evidence favours cheap single-frame spatial shaders.

| Option | Licence | Cost evidence | Role for Cha |
|---|---|---|---|
| Bilinear (today) | n/a | free in the compositor | baseline |
| Catmull-Rom/Lanczos, optional CAS | n/a / MIT | 0.26 ms (40-core) to 0.72 ms (12-core base chip) at 1080p output, WebGPU on Apple Silicon [D]; ~1–2 ms at 3024×1964 on a base M4 [E] | desktop fallback; deadline-controller floor |
| SGSR 1 (one pass, 12-tap) | BSD-3 | no browser timing found; assumed ≤ FSR 1 [E] | first choice for games |

| MetalFX spatial | macOS API | 5–10 ms GPU on M3 Pro [D]; under 1 ms typical, 2 ms max at 1440p120 [D, mostly Windows testing]; 16–21 ms to 4K on A15 [D] | native macOS; benchmark against WGSL |
| VideoToolbox low-latency SR (LLSR) | macOS API | ~1.7 ms wall per 480p frame with no added GPU time on M3 Pro [D]; sources ≤ ~960×960 at 2× only on OS 26 [D] | only a sub-960 px WAN tier |
| WebGPU ML SR (webgpu-vsr "low") | MIT code; NVIDIA weights, not redistributable | 6.69 ms for 1080p→4K on a 40-core GPU [D]; ~30 ms at 1440p input on a base-class Apple GPU [E] | reject for now |

### The native player gains one pass after colour conversion

Today [`crates/cha-player/src/render/video.wgsl`](../crates/cha-player/src/render/video.wgsl) converts YCbCr→RGB straight into the letterboxed viewport in a single pass. An upscaler needs that conversion to happen first, at source resolution, into an sRGB-encoded intermediate — FSR 1 expects anti-aliased, perceptual-space, noise-free input, and RCAS outputs NaN on negative values ([AMD FSR 1 manual](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-spatial/)) — followed by a second pass that writes the panel-sized letterbox. Compression noise violates the noise-free assumption, so RCAS strength should fall with bitrate. Because the pass is WGSL, the same file runs unchanged on `cha-pyrowave-wgpu`'s output, through wgpu on Vulkan and D3D12 for the later Linux and Windows players, and fused into the final pass of [`web/packages/pyrowave-webgpu`](../web/packages/pyrowave-webgpu) in the browser. Cha measured PyroWave decode at **1.8–3.4 ms of GPU time per 1440p frame on an M4 Pro** [C]; a ~1 ms pass [E] fits inside the 8.33 ms latch at 120 Hz, but Apple GPUs drop clocks at a 60 fps duty cycle — webgpu-vsr's author saw the same [D] — so a 1–2 ms shader can measure 2–4 ms. Every working WebGPU video upscaler the researchers studied uses a deadline controller that steps quality down on late frames, and Cha's should step SGSR/EASU → Catmull-Rom → bilinear on presented-frame deadlines, the same yardstick the planned `CAMetalDisplayLink` pacing work (PLAN item C2.4) uses.

### VTFrameProcessor fails Phase 4's check at Cha's sizes

PLAN.md Phase 4 says the MetalFX pass should be "checked against VideoToolbox's `VTFrameProcessor` first", and external evidence already answers that check for Cha's sizes. `VTFrameProcessor`'s two real-time effects, low-latency super-resolution and low-latency frame interpolation, target video calls ([WWDC25 session 300](https://developer.apple.com/videos/play/wwdc2025/300/)). One developer found LLSR accepts sources only up to about 960×960, at 2× only and in 8-bit 420v only on OS 26 [D] ([airwave PR #12](https://github.com/rkanjani/airwave/pull/12)); OS 27 adds a 1.5× factor and dimension queries ([tvOS 27 beta notes, third-party mirror](https://betaprofile.dev/tvos-27-beta-8/)); and another tool found it "accepts no scale factor at 1080p" on macOS 27 [D] ([metafx-upscale](https://github.com/tsonubin/metafx-upscale)). LLSR therefore cannot take 1440p to 3024×1964; at most it is the first stage of a sub-960p WAN tier, followed by a spatial pass, as AetherEngine chains it on tvOS [D]. The high-quality `VTSuperResolutionScalerConfiguration` takes 0.35–0.42 s per frame and is offline only [D] ([vidcut PR #564](https://github.com/oittaa/vidcut/pull/564)). That leaves MetalFX spatial, whose measured costs disagree by about tenfold, so it should be benchmarked against the WGSL pass rather than presumed better. The interop exists: `objc2-metal-fx` 0.3.2 binds the spatial scaler, wgpu's `as_hal::<Metal>` exposes the raw device, `texture_from_raw` wraps textures Cha creates itself with the usage flags MetalFX demands, the non-MTL4 factory matches wgpu's classic `MTLCommandBuffer`s, and encoding on wgpu's own queue gives ordering for free ([objc2-metal-fx](https://docs.rs/objc2-metal-fx/latest/objc2_metal_fx/); [vtsampler](https://docs.rs/crate/vtsampler/0.1.1/source/src/bridge/metal.rs)).

### Browser presentation, not the shader, sets the cost

WebRTC's `<video>` offers no shader access short of moving to `requestVideoFrameCallback` and a canvas, which gives up the video overlay and adds at least one vsync [E], so that path should stay as it is. Its only free upscaler lives on Windows: Chromium's `swap_chain_presenter.cc` switches on NVIDIA RTX Video Super Resolution (and Intel's, behind a flag) inside the D3D11 video-processor blit that already scales DirectComposition overlays, disables it on battery, and gives pages no way to enable or detect it ([Chromium](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/ui/gl/swap_chain_presenter.cc)). Nobody has tested whether it engages on WebRTC or `VideoTrackGenerator` video, and macOS has no equivalent.

On WebTransport/WebCodecs, Cha measured ~3 ms send→compositor through `<video>` and 4–5 ms more when drawing through WebGPU on an M4 Pro [C]. The import is not the expensive step — one blog measured ~1230 fps through `importExternalTexture` on an M4 MacBook Pro [D] ([WebCodecs Fundamentals](https://webcodecsfundamentals.org/basics/rendering/)) — the canvas-to-compositor present is, and Chrome's low-latency canvas mode remains unavailable on macOS after a Chromium engineer argued against it ([graphics-dev](https://groups.google.com/a/chromium.org/g/graphics-dev/c/20qDm3ZD2f8); [crbug 41449024](https://issues.chromium.org/issues/41449024)). The one route that upscales and keeps the `<video>` presenter is WebGPU → OffscreenCanvas → `new VideoFrame(canvas)` → `VideoTrackGenerator` → `<video>`, which the WebCodecs group intended to be cheap ([w3c/webcodecs #83](https://github.com/w3c/webcodecs/issues/83)). Chromium's `VideoFrame` constructor waits on the GPU, however (one demo measured about 1 ms of GPU processing per frame [D], [tidoust/media-tests](https://www.github.com/tidoust/media-tests)), and WebKit bug 300579 records heavy CPU cost when building frames from an OffscreenCanvas in Safari ([WebKit](https://bugs.webkit.org/show_bug.cgi?id=300579)); nobody has measured the round trip's latency, so it is a prototype, not a plan. PyroWave in the browser already pays the canvas present, which makes fusing the upscale into its last inverse-wavelet or colour pass — with the OffscreenCanvas sized to device pixels — the cheapest marginal addition, now that WebGPU ships in Safari 26 and in Firefox 147 on Apple Silicon ([WebKit](https://webkit.org/blog/17541/webkit-features-for-safari-26-1/); [The Register](https://www.theregister.com/2026/01/14/firefox_and_tbird_147/)).

### ML super-resolution misses the budget by several times

WebNN is not shipping: Chrome pulled its origin trial in March 2026, the trial expired on 11 August 2026, and a new one is pencilled in for "Chrome 160 (TBD)" ([webnn #964](https://github.com/webmachinelearning/webnn/issues/964)). Hand-written WGSL is what remains, and the smallest useful network runs at 120 fps on 720p input on an M4 MacBook Pro [D] ([free.upscaler.video](https://free.upscaler.video/technical/architecture/)), which scales to roughly 30 ms per 1440p frame [E] — several times Cha's budget. For a later Windows player, NVIDIA's RTX Video SDK 1.1 is Windows-only, needs RTX 20 or newer and carries an unchecked licence ([NVIDIA](https://developer.nvidia.com/rtx-video-sdk/getting-started)); AMD's AMF upscaler is the other vendor path, and Moonlight's PR author reports under 1 ms typical and 2 ms at most at 1440p120 on discrete GPUs [D]. Microsoft's `VideoScaler` is out, being NPU- or CPU-only, capped at 60 fps and 1440p, and aimed at faces ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/ai/apis/video-super-resolution)). Industry reception counsels restraint: upstream Moonlight has left its cross-platform super-resolution PR open for 20 months, and its Android port took decode-to-display from 12 to 26 ms on a weak TV SoC [D] ([moonlight-android #1567](https://github.com/moonlight-stream/moonlight-android/pull/1567)). Client SR should ship off by default, off for HDR, and justified by bandwidth rather than latency.

## AV1 reference scaling is the only codec-level trick that survives

### Superres is unusable from encoder to browser

Superres is a normative AV1 decoder tool — horizontal only, from 8/9 down to 1/2 of the width, with loop restoration at full resolution ([AV1 spec](https://aomediacodec.github.io/av1-spec/)) — yet nothing in Cha's stack can use it. Chromium's shared hardware AV1 decoder, which the macOS VideoToolbox and Windows D3D paths both use, returns **`kDecodeError` on any frame whose coded width differs from its upscaled width** ([Chromium av1_decoder.cc](https://chromium.googlesource.com/chromium/src/+/main/media/gpu/av1_decoder.cc)). NVENC API 13.1 has no superres field ([nvEncodeAPI.h](https://raw.githubusercontent.com/FFmpeg/nv-codec-headers/master/include/ffnvcodec/nvEncodeAPI.h)); Intel's VA-API caps advertise `support_superres = 0` with no loop restoration ([intel/media-driver](https://raw.githubusercontent.com/intel/media-driver/master/media_softlet/linux/xe2_hpm_r0/encode/av1/ddi/capstable_data_av1_encode_xe2_hpm_r0_specific.h)); SVT-AV1's own docs say superres loses efficiency at common bitrates and gains only at very low ones ([SVT-AV1](https://gitlab.com/AOMediaCodec/SVT-AV1/-/blob/master/Docs/Appendix-Super-Resolution.md)); and superres frames cannot use IntraBC. `superres_scale_denominator = 8` in [`crates/cha-streamer/src/encoder/vaapi/av1.rs`](../crates/cha-streamer/src/encoder/vaapi/av1.rs) is therefore correct, as is the encoder's refusal to start on a driver that requires superres. The sequence-level `enable_superres` should stay 0 as well, because toggling it between sequence headers forces a Chromium hardware context reset.

### Reference scaling changes size without a keyframe

AV1 lets an inter frame change its coded size and predict from references up to 2× larger or 16× smaller ([AV1 spec](https://aomediacodec.github.io/av1-spec/)). Chromium's decoder accepts such mid-sequence changes and outputs frames at the new coded size, ignoring `render_size` ([Chromium](https://chromium.googlesource.com/chromium/src/+/main/media/gpu/av1_decoder.cc)), so every Cha renderer must scale each frame to the viewport — which the native letterbox pass and a WGSL upscaler do anyway. A Chromium bug titled "AV1 videos encoded using reference frame scaling freeze intermittently" remains visible though its status could not be read ([crbug 338251332](https://issues.chromium.org/issues/338251332)), and Safari's behaviour is unknown. libwebrtc never uses the feature: any width or height change releases and re-initialises its encoder, producing a keyframe ([webrtc](https://webrtc.googlesource.com/src/+/refs/heads/main/video/video_stream_encoder.cc)), and Meta counted about **1.5 keyframes per minute** from resolution switches alone in H.264 calls [V] ([@Scale](https://atscaleconference.com/av1-improving-rtc-video-quality-at-scale/)).

Cha's own sender has to own this, encoder by encoder. NVENC permits resolution changes within `maxEncodeWidth/Height`, but its guide advises forcing an IDR after a reconfigure and says nothing about AV1 reference scaling ([NVENC guide](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html)), so the decisive test is to reconfigure without `forceIDR` and parse the OBUs for `frame_size_override_flag` on inter frames. Intel's VA-API reports `EncDynamicScaling = 0`, so an intra frame on every change is the expectation there [E]. HEVC and H.264 need a new SPS and an IDR, which intra refresh can soften — except that NVENC terminates an in-flight refresh wave on a resolution reconfigure. PyroWave, being intra-only, can change size on any frame once its byte budget follows the rate controller. On the decode side, AMD's Mesa decoders cannot take a frame larger than the size their context was created at ([libva #634](https://github.com/intel/libva/issues/634)), which matters for the later Linux player.

### Fewer pixels pay only below about 0.05 bits per pixel

The published evidence says downscaling pays only when bits are scarce. A 2026 Frontiers study [I] using VVenC random-access encoding of natural 4K60 content at 0.145–16.8 Mbit/s found 1080p plus learned upscaling often matched native 2160p VMAF, for **12–28% savings**, while CPU-only clients missed real-time deadlines ([Frontiers 2026](https://www.frontiersin.org/journals/signal-processing/articles/10.3389/frsip.2026.1802483/full)). LevelUp [R] reported about 70% less bandwidth for a 3–20% VMAF loss in game livestreaming ([LevelUp](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/08/levelup-sec20.pdf)), and SVT-AV1's real-time dynamic resize gained −17.7% SSIM BD-rate on a 720p talking head, but only at low-bitrate CBR [D] ([SVT-AV1 PR #3369](https://github.com/AOMediaCodec/SVT-AV1/pull/3369)). The researchers' arithmetic puts the crossover near **0.03–0.05 bits per pixel at display resolution, roughly 7–11 Mbit/s for 1440p60** [E], and low-delay hardware encoders with no B-frames and a one-frame VBV starve at higher bitrates than the encoders in these studies, which pushes the crossover up [E]. No study covers 20–50 Mbit/s, low-delay hardware AV1 or HEVC, or game and desktop content. Network-adaptive resolution is therefore a game-mode feature for WAN and iroh links, decided inside the delay-based rate controller; it does nothing on the LAN and never applies to desktops.

### LCEVC, AV2, VVC and neural codecs stay out

LCEVC fails on licence grounds alone. Its web decoder runs on MSE, WASM and a WebGL canvas with no WebCodecs or WebRTC path ([V-Nova docs](https://docs.v-nova.com/technologies/mpeg-5.lcevc/decoder/sdk/lcevc-decoder-for-web-lcevcdecjs)); its decoder licence, BSD-3-Clause-Clear, excludes patents ([LCEVCdec](https://github.com/v-novaltd/LCEVCdec)); V-Nova announced service and device royalty programmes in August 2025 ([V-Nova](https://v-nova.com/press-releases/v-nova-announces-licensing-programs-for-mpeg-5-lcevc-to-support-tv-3-0-and-streaming-growth/)); and its cloud-gaming gains are vendor claims ([NVIDIA blog](https://developer.nvidia.com/blog/new-video-creation-and-streaming-features-accelerated-by-the-nvidia-video-codec-sdk/)). AV2 1.0 (28 May 2026) claims about 30% over AV1 [V], drops superres, keeps reference scaling with "bridge frames", and strengthens screen content with IntraBC alongside loop filters, Backward Reference Update and a 4:4:4 profile ([Norkin](https://norkin.org/research/av2_overview/index.html); [AOM](http://aomedia.org/blog%20posts/AV2-What-the-Final-Specification-Means-for-Implementers/)), but no browser or hardware codec supports it yet, so it is a watch item. VVC has no browser decoder, and DCVC-RT reaches only 1080p30 on an RTX 4090 in int16 with no browser path [R] ([arXiv 2502.20762](https://arxiv.org/abs/2502.20762)).

## Every shipping frame generator holds back a real frame

An interpolator must already have real frame N+1 before it can show anything between N and N+1, so for N× output from source interval T with synthesis time C, real frames slip by (N−1)/N·T + C — the constraint GFFE states explicitly ([GFFE](https://arxiv.org/html/2406.18551v1)) — and the measurements fit the arithmetic.

| Case | Real-frame hold (N−1)/N·T [E] | Plus C (≈2–5 ms client, 1–3 ms on the 4090) [E] | Comparable measurement |
|---|---|---|---|

Against Cha's ~5 ms median send→shown [C], a ≤12 ms native glass-to-glass target and ≤25 ms for browsers, interpolating 60→120 alone uses most of the native budget, and for a GPU-bound game, streaming 120 real frames beats 60 frames plus FG to 120 by roughly **17–23 ms of input-to-photon** [E]. On a LAN, frame generation is a smoothness feature, never a latency feature.

### GeForce NOW caps cloud MFG at 4×

GeForce NOW is the only major service generating frames on the server [V]. It shipped DLSS 4.5 overrides around October 2026, caps cloud MFG at 4× dynamic because NVIDIA's testing "showed no benefit for streaming players" beyond that, recommends a stream of at least 90 fps with VRR and Reflex, and shows FG as off in menus and cutscenes ([Club386](https://www.club386.com/nvidia-4x-multi-frame-gen-geforce-now/)). One reviewer found 4× brought "significantly more lag" while 2× stayed acceptable, though only a search snippet of that review was available ([Digitec](https://www.digitec.ch/en/page/trying-out-geforce-now-with-rtx-5080-performance-39272)). Xbox Cloud, PlayStation, Steam Remote Play, Shadow and Parsec ship no stream frame generation; Xbox Cloud raised streams to 1440p with higher bitrate instead ([Xbox Wire](https://news.xbox.com/en-us/2026/02/25/february-xbox-update-1440p-streaming-rog-xbox-ally-updates-and-more/)).

### Nested gamescope pacing turns surplus frames into waste

Node frame generation collides with Cha's pipeline at several points. Nested gamescope paces to `-r`, following the compositor's frame callbacks, so the game's base rate must be capped at the stream rate divided by the multiplier (60→120 with `-r 120`), because frames above `-r` are dropped or back-pressure the game [E]. The node has no VRR, so uneven FG pacing becomes duplicate frames at the encoder [E]. Each generated frame costs a full NVENC or VA-API encode and, on PyroWave, about as many bits as a real one [E]. Smooth Motion receives no UI mask, so HUD ghosting appears on every generated frame and, at a one-frame VBV, consumes bits the real detail then lacks [E]. And no source confirms that DLSS FG or Smooth Motion works inside nested gamescope with `--backend wayland` on a headless node, while the vkroots fix shows that layer ordering against gamescope's WSI layer is a genuine failure surface. Node FG is therefore opt-in per game, off in desktop mode, never forced fleet-wide, and measured before it ships.

### Client interpolators all miss a 12 ms budget

Every client-side interpolator found is too slow, needs data the client lacks, or carries a licence Cha cannot use. Apple's low-latency frame interpolation took 7.99 ms per interval at 720p and 22.24 ms at 1080p on an M2 Max, failing silently above that [D] ([60FPSVideo](https://github.com/wasim-osman/60FPSVideo)). MetalFX's frame interpolator needs depth, motion vectors and camera matrices, and cost 11–18 ms per frame on an iPhone 17 [D] ([Apple forums](https://developer.apple.com/forums/thread/853871)). The browser-side Framegen runs about 2 ms per 720p frame on an RTX 4060 Ti [D] but ships CC BY-NC weights ([Framegen](https://github.com/NimaJafariComp/Framegen)). The moonlight-macos-framegen fork estimates motion with VideoToolbox, masks the UI, halves real frames on 60 Hz panels and publishes no latency figures ([release](https://github.com/AyberkA0/moonlight-macos-framegen/releases/tag/v6.1.0-metalfx.1)). WebCodecs exposes no codec motion vectors and nobody has proposed adding them ([W3C registry](https://w3c.github.io/webcodecs/video_frame_metadata_registry.html)), and PyroWave has none. All of these carry the hold above; none fits a ≤12 ms target at 120 Hz.

### Zero-hold warping hides jitter and round trips

Research has moved to extrapolation, which predicts forward from past frames and so waits for nothing. GFFE extrapolates in 6.62 ms at 1080p on an RTX 4070 Ti Super and explicitly targets cloud gaming, but needs depth, motion vectors and camera poses [R] ([GFFE](https://arxiv.org/html/2406.18551v1)); on the same game scenes, video-only extrapolation (DMVFN) scores 21.73 dB PSNR against interpolation's 24.24 dB [R]; and Amulet (August 2026) needs scene geometry ([arXiv 2608.10423](https://arxiv.org/abs/2608.10423)). NVIDIA's Reflex 2 Frame Warp, the reference design for input-driven warping, still had not shipped in July 2026, 18 months after its announcement ([hwbusters](https://hwbusters.com/news/nvidia-reflex-2-is-18-months-old-and-still-hasnt-shipped/)).

Two uses fit Cha. The first is concealment: while a frame is late, or while RFI recovery is in flight after a loss, the client shows a warped or extrapolated copy of the last frame for one or two slots at most, flags it as synthetic in telemetry, then falls back to repeating. Because this adds no hold, the playout target can sit near median arrival rather than the P99 — in an illustrative 60 fps case with 12 ms of P99 jitter, about **8 ms saved** [E]. No flat-screen streaming product does this and no study measures its quality of experience, while production systems such as Tencent's START attack loss at the transport, reaching 0.049% packet loss [I] ([NSDI '26](https://www.usenix.org/conference/nsdi26/presentation/wang-jing)); concealment is a cheap backup to Cha's FEC and RFI, not a substitute. The second is rotation-only input reprojection: warping the last decoded frame by the mouse movement the node has not yet applied, via the homography K·R·K⁻¹, which removes the network round trip from mouse-look and is worth tens of milliseconds on WAN. It needs `last_input_seq` stamped on each frame, per-game or online calibration of degrees-per-count and field of view, a HUD mask, and edge fill for the strip the warp uncovers — about **8% of the width at 300°/s over a 30 ms loop, 19% over 70 ms** [E] — and it must switch off whenever the game shows a cursor, because game mode composites the cursor into the video and would warp it with the scene. It also needs control of present timing, which places it in the native player behind `CAMetalDisplayLink`.

### Desktop streams are all UI, so frame generation stays off

Every vendor design treats UI as a special case — FSR's interpolator takes a HUD-less buffer and inpaints the UI, MetalFX has dedicated UI modes, and GFFE lists UI as unhandled ([AMD FidelityFX FI](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/frame-interpolation/); [GFFE](https://arxiv.org/html/2406.18551v1)). A desktop stream is nothing but UI, and its damage-driven updates and client-drawn cursor already supply the responsiveness that matters, so desktop mode should turn frame generation off entirely.

## A ranked plan: instrument, build four things, then measure before the rest

The order follows the evidence. Instrumentation comes first because every later gate is a latency or quality comparison Cha cannot yet run — PLAN.md calls the 12 ms native target "unproven" and defers glass-to-glass measurement ([docs/PLAN.md](../docs/PLAN.md)). Ranks 2–4 are low-risk, mutually independent, licence-clean and add little or no latency; ranks 5–7 depend on presentation and codec behaviour where the only evidence is single-developer or absent; ranks 8–10 change what users see in time and wait for both the telemetry and the native pacing work.

## Conclusion

The question arrived as "which upscaler and which frame generator", and the evidence reframes it as where reconstruction should happen and what it may cost. On a wired LAN, Cha's best upscaler is mostly not a client upscaler at all but the game's DLSS or FSR on the node feeding a stream at the panel's native size; client spatial filtering is a bandwidth tool for WAN game sessions. Frame generation's value inverts once it meets a network: the vendor feature sold for smoothness, interpolation, costs more latency than Cha's entire transport path, while the zero-hold variants that research and VR runtimes favour do the opposite, hiding jitter, loss and round-trip time — and Cha, which already carries frame IDs, per-stage timestamps and RFI, is unusually well placed to build them with a few more header fields.

No major service ships browser-side super-resolution or flat-screen input reprojection, so if Cha builds either it will be ahead of the industry rather than catching up, and each has to be justified by Cha's own measurements, not by parity. Those decisive experiments are cheap, local and runnable on the existing RTX 4090 node and M4 clients; what must come first is the glass-to-glass rig, without which every number in this report remains a vendor claim, someone else's benchmark or an estimate.
