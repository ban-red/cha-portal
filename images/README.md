# Environment images

Our own images for the catalog (`catalog.json`, which the portal embeds). Every environment runs one of these as its **app container**, beside a `cha-streamer` container that the agent starts (plan §4.2).

| Image | What runs | Profile |
|---|---|---|
| `base` | Ubuntu 26.04, user `cha` (uid 1000), fonts, cursor theme, the GPU libraries' dispatchers, libpulse | — |
| `test-pattern` | `cha-testpattern`, our own Wayland client: a sweeping bar, a frame counter, a frame-ID strip, a flash and a tone on input, the first gamepad's state | `standard` |
| `chrome` | Google Chrome on Wayland, GPU-rendered, sandbox on | `browser` |
| `firefox` | Firefox (Mozilla's .deb) on Wayland, GPU-rendered, sandbox on; first-run pages off by policy | `browser` |
| `xfce` | XFCE inside one rootful, fullscreen Xwayland, so the compositor needs no X11 window manager, and `cha-x11-clipboard`, which bridges the X clipboard to the streamer | `standard` |
| `kde` | KDE Plasma 6: KWin runs as a Wayland client of our compositor (one window, the whole picture) with its own Xwayland, and Plasma inside it; no systemd. The user's data persists (*App data*, below): the whole home, so Plasma's and KWin's settings, the desktop's files, Konsole and Dolphin, survive stops and node reboots. `start-plasma` copies and sets nothing in the home, so a later launch keeps what Plasma wrote; it first runs `kde-clean-stale`, which clears the Qt lock files, service cache and ICE authority an unclean stop leaves (tested by `test_kde_clean_stale.py`) | `standard` |
| `steam` | Steam's Big Picture (gamepad UI) inside gamescope, which runs as a Wayland client of our compositor and gives Steam its own Xwayland. The user's data persists (*App data*, below), and a library shared by users can be listed in Steam (`steam-library`). `steam-touch-mode` keeps gamescope's touch click mode out of the "passthrough" Big Picture sets, which would drop the pointer's motion. `steam-focus` sends a Proton game `WM_TAKE_FOCUS` whenever it gains the X focus (at launch, and when Steam's in-game menu closes), as a window manager would: gamescope only sets the X focus, and Wine then doesn't make the game the foreground window, so its input, the controller's too, went nowhere until a click (tested by `test_steam_focus.py`). gamescope doesn't pass the clipboard through, so `cha-x11-clipboard` bridges its X server's, as in XFCE. `steam-status` shows the first launch's download and install on the page (*Setup status*, below). `steam-run` keeps gamescope's and Steam's output (`docker logs`, and `~/.local/state/cha/gamescope.log` in the home, the last 5 runs, 1 MiB each) and, when gamescope dies on an error, shows "gamescope crashed (SIGABRT)" on the page and exits with its code, so the environment fails and the node keeps the log tail. gamescope starts MangoHud's `mangoapp`, the performance overlay (*Performance overlay*, below). `start-steam` preloads `libcha-uinput.so` (built in the image from [`steam/uinput-shim/`](steam/uinput-shim), for i386 and amd64) into `steam`, which fakes `/dev/uinput` for Steam's virtual Xbox pad and asks the streamer for it (*Gamepads*, below) | `steam` |

Build them on a node, from the repository root:

```bash
docker compose -f images/compose.yaml build
```

How they're built:

- **The base is pinned by digest** (`ubuntu:26.04@sha256:…`); Dependabot proposes the bumps, and a bump rebuilds every environment at the next release (its inputs hash changes).
- **apt's package and list caches are mounted**, not written into layers: no image holds apt lists. The base keeps Ubuntu's `docker-clean` hook, so images built on it without cache mounts leave no packages behind either.
- **The cargo stages copy only `Cargo.toml`, `Cargo.lock`, `crates/` and the spikes' servers** (workspace members), so editing the web app or the docs doesn't rerun them.
- **Steam's final stage is three layers:** i386 and Mesa (554 MB), Steam and `steam-libs-*` (449 MB), then the patched gamescope and mangoapp (19 MB), so changing gamescope doesn't re-download the rest.
- **Published environment layers are zstd** (level 12, about 15% smaller than gzip on Steam's layers); pulling them needs Docker Engine 23 or newer.

## The contract

The rules any environment image follows (what the node gives the app, what the app must do, the catalog entry's fields) are in [`docs/image-spec.md`](../docs/image-spec.md), with a minimal example in [`example/`](example) and a JSON Schema for the catalog in [`catalog.schema.json`](catalog.schema.json). What follows is what our own images do beyond it: their integrations with the streamer, and the Steam, KDE and XFCE specifics.

- **Performance overlay.** An app that can draw MangoHud's overlay (`steam`, through gamescope's `mangoapp`) makes `/run/cha/mangohud.conf` before it starts, containing `no_display`: each launch starts with the overlay off, and the file existing tells the streamer the app has one. The streamer turns it on and off by replacing the file atomically (temp file, then rename; `mangoapp` re-reads it within ~100 ms): `no_display` is off; `mangoapp_steam` and `preset=N` on a line each, N from 1 to 4, is on. Without `mangoapp_steam` MangoHud draws nothing while Steam's own UI has focus, only over games. The presets are `~/.config/MangoHud/presets.conf` in the user's home if the file exists, else MangoHud's built-in ones (1 frame rate only, 2 a horizontal bar, 3 extended, 4 everything). Steam's own Quick Access Menu doesn't offer the setting under plain `-gamepadui`, so Steam never writes the file. Two parts of the image are built, not installed: `mangoapp` from upstream MangoHud v0.8.2, because Ubuntu's package has no NVML and shows no NVIDIA GPU statistics (NVML is loaded at run time, from the libraries the node's CDI spec brings), and gamescope from Ubuntu's source with [`steam/gamescope-wayland-mangoapp.patch`](steam/gamescope-wayland-mangoapp.patch): nested in a Wayland compositor, gamescope never tells `mangoapp` when a frame was shown for a vsynced plane (Steam's UI, vsynced games), so the overlay never drew. The DRM backend does; the patch makes the Wayland backend do it too. The image holds the patched `gamescope` package (version `+cha1`) so an upgrade doesn't put Ubuntu's back.
- **Setup status.** An app whose first run is long (Steam downloads ~500 MB before it has a window) tells the page what it is doing by writing one JSON object to `/run/cha/status`:

  ```json
  {"label": "Downloading Steam", "done": 123, "total": 496, "unit": "MB"}
  ```

  - **Fields.** Only `label` is required. `done`, `total` and `unit` are optional: with no `total` the page shows an indeterminate bar, and `unit` names `done` and `total`. Removing the file, or writing `{}` (or no label), clears it. The app clears it itself when its UI is up: nothing else will.
  - **Replace it whole.** Write a temp file in `/run/cha`, then rename it over `status`: `printf '{"label":"Installing"}' > /run/cha/status.tmp && mv /run/cha/status.tmp /run/cha/status`. The directory belongs to uid 1000, so the app can. A file that doesn't parse, or is over 4 KiB, is ignored and the last status stands.
  - **Where it goes.** The streamer reads the file every 250 ms and sends every session `{"t":"status",…}` on the control channel, the current one to a page that joins late. The portal shows the label and a progress bar over the picture, and the player's `onStatus` hands it to any other page.
  - **Steam.** `steam-status` (Python, started by `start-steam` beside Steam; its tests are `test_steam_status.py`) follows Steam's bootstrap log, `~/.local/share/Steam/logs/bootstrap_log.txt`, from the moment it starts (the home keeps earlier launches' lines). `Downloading update (493,420 of 496,367 KB)...` becomes "Downloading Steam" with `done` and `total` in MB; `Extracting package...` is "Unpacking Steam", `Installing update...` "Installing Steam", and "Starting Steam" is what it says before, between and after. It ends, clearing the status, when Steam's web helper logs its first window (`PopupHTMLWindow` in `steamui_html.txt`), or when a `steamwebhelper` process has run for 20 s, or when its parent does. A launch with nothing to download only says "Starting Steam", for the few seconds the UI takes.
- **Gamepads.** The streamer makes virtual Xbox 360 pads (uinput) and shares them through two read-only volumes: their device nodes at `/dev/input` (the only input devices the app has) and udev's entries for them at `/run/udev`, where Chrome, Firefox and Wine look. The app's device cgroup allows input devices (major 13). Hotplug events don't reach the container, so one pad exists from the start; SDL is told to skip udev (`SDL_JOYSTICK_DISABLE_UDEV=1`) and watches `/dev/input`, so it sees later ones.
  - **The kind.** The user picks the controller per app (Controllers page): `xbox360`, `dualsense` or `steam` (`docs/controllers.md`). A template may set the default in the catalog with `"gamepad": "dualsense"` (absent is `xbox360`, which every game knows; Steam stays on it too until the user chooses). The kind is fixed for the environment's life.
  - **Steam's own pad.** Steam Input hands games a virtual Xbox pad (`28de:11ff`) that Steam makes through `/dev/uinput`, which no app gets. With the `steam` kind, the streamer listens on `/run/cha/uinput.sock`; the `steam` image's `LD_PRELOAD` shim (`libcha-uinput.so`) turns Steam's `open` of `/dev/uinput` into a connection to it, and the streamer validates the request, makes the device and shares its node and udev entry like its own pads (`crates/cha-streamer/README.md`). What Steam asks for is logged to `/run/cha/uinput-shim.log`. Implemented and tested against the node's kernel with test programs, not yet verified with Steam.
  - **DualSense and Steam Controller.** These are made through uhid. The host kernel's `hid-playstation` binds the DualSense, and its evdev nodes appear in `/dev/input` like the Xbox pad's. The Steam Controller is the 2026 Bluetooth one (`28de:1303`; Steam skips a wired one without a USB interface 2, which a uhid device can't have; the original Bluetooth controller, `28de:1106`, is still in the streamer behind `steam_controller::VARIANT`): `hid-generic` takes it and it has no evdev pad, so only Steam Input reads it. They also have `hidraw` nodes, which SDL's HIDAPI driver, Proton and Steam use. The streamer makes those in the same input volume, under `hidraw/`, and lists them in its `/info`; the agent then mounts each into the app at `/dev/hidraw<n>` (a subpath of the volume, read-only: reports still go through) and allows exactly that device in the app's cgroup (`c <major>:<minor> rwm`). Nothing else of the app's `/dev` changes. Needs the host's `uhid` module (`/dev/uhid`, `CHA_UHID`) and Docker Engine 26 or newer (volume subpaths).
- **App data.** What an app keeps between launches lives on the node ([`deploy/README.md`](../deploy/README.md#app-data) has the layout, permissions and rollout); [`docs/image-spec.md`](../docs/image-spec.md#5-app-data) has the contract with an image (the home, seeding from the image's `/home/cha`, shared directories, `perUser`). What our images do about it:
  - **Start-up scripts must cope with what a stopped container leaves in the home:** `start-steam` clears Steam's stale pid file and pipe. `start-plasma` runs `kde-clean-stale`: KDE's lock files (Qt's `QLockFile` records the host name, which is new in each container, so an old lock never looks stale and the next session waits out its 30 s stale time on every config file), `ksycoca*`, `.ICEauthority*` and `.dbus/session-bus/`. It removes a `*.lock` file only if it is under `~/.config`, `~/.local/share`, `~/.local/state` or `~/.cache`, under 512 bytes and starts with a pid and a host name; settings, saved sessions and the user's files stay. The session's sockets and bus are in the container's `/tmp` and `/run/cha`, which are new each launch. It also stops with a message if the home isn't writable by uid 1000.
  - **`CHA_PER_USER_DIRS`** (colon-separated paths in the container) names the per-user directories laid over the shared one; the node watches that they stay mounted (they come unmounted when the directory under them changes on a NAS), and tells the user if not. Steam's `start-steam` runs `steam-per-user-dirs` first, which exits 1 with a message if any isn't a mount point in `/proc/self/mountinfo`, so Proton never uses the shared prefixes (tested by `test_steam_per_user_dirs.py`). Unset when there are none.
  - **Steam's shared library (experimental).** `start-steam` runs `steam-library "$CHA_SHARED_DIR"` before Steam starts, which lists that directory as a library folder in `~/.local/share/Steam/steamapps/libraryfolders.vdf` and `config/libraryfolders.vdf` (Python, tested by `test_steam_library.py`):
    - **Before Steam starts**, since Steam rewrites its list from memory while it runs.
    - **Idempotent, and only adds:** the other libraries stay; a library already listed leaves the file untouched. A home that hasn't run Steam yet gets both files, with Steam's own folder as entry 0.
    - **Names both libraries.** Steam labels a library with no name after its device, which in a container is `/usr/sbin/docker-init` for both. An empty label becomes "Personal library" (Steam's own folder) and "Shared library" (the shared one, unless its marker has a label). A label already set is kept, so a rename in Steam's Storage settings lasts. (The label field is what Steam's storage list reads, going by its file format; not yet seen on a node.)
    - **Never writes in the shared directory.** If it has Steam's own `libraryfolder.vdf` marker, the entry copies its content id and label; if not, the entry is the path alone and Steam makes the marker.
    - **A directory Steam can't write isn't listed:** Steam refuses a library folder it can't write ("New Steam library folder must be writable"), so read-only sharing is for apps other than Steam, and Steam needs `write`. (Not tried with a game: the refusal is what Steam's own messages and users' reports say.)
    - **What is shared is the downloaded games and their install state** (`steamapps/common`, `appmanifest_*.acf`). Each user's account must own a game to play it. Proton prefixes and shader caches are each user's own (`perUser` above). Two users updating the same game at once can clash: the shared library is experimental.
    - **Steam's old prefixes** in an external library's own `steamapps/compatdata` are hidden under the per-user directories, not migrated: Steam Cloud covers most saves.

## Known gaps

- **bubblewrap.** GTK loads images through glycin, which sandboxes each loader with bubblewrap. bubblewrap can't build its sandbox here: Docker's AppArmor profile denies its mounts, and the host restricts unprivileged user namespaces (Ubuntu's `apparmor_restrict_unprivileged_userns`). The base image therefore puts a stand-in `bwrap` first in `PATH` ([`base/bwrap-shim`](base/bwrap-shim)). It runs the loaders directly, so the container is their sandbox. A `cha-browser` AppArmor profile installed by `cha doctor` (P1.7, with the owner's sudo) will remove the shim. Steam's pressure-vessel needs the same profile.
- **XFCE** has no wallpaper yet.
