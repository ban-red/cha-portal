## 1. macOS EDR: CAMetalLayer settings, colour spaces, pixel formats, metadata, headroom, and macOS 26/27 changes

### Takeaway
On macOS, HDR10 in a custom Metal layer works in one of two ways. (a) Convert PQ to extended linear light yourself into an `RGBA16Float` layer tagged extended-linear (Apple's own WWDC21 recipe), and tone-map in your own shader to the live headroom `NSScreen.maximumExtendedDynamicRangeColorComponentValue`. (b) Pass PQ through to a 10-bit layer tagged `kCGColorSpaceITUR_2100_PQ` and let Core Animation tone-map it, steered by `CAEDRMetadata`, which is what moonlight-qt does. Apple says the CAEDRMetadata tone-mapper "involves an extra processing pass" that "increases latency and bandwidth", and one developer saw the PQ-layer path go near black when headroom drops to 1.0. For a latency-first player, (a) is the better default, with (b) kept as a fallback to compare against.

### Cited Findings
**Headroom: what it is and how it moves**
- EDR headroom is "how many times brighter than the conventional maximum SDR white the brightest EDR pixels can be rendered". It "varies based on display capability, as well as other parameters, including the current brightness slider setting." Apple's examples: conventional backlit Mac/iPad displays "up to… 2x SDR"; external HDR10 displays driven by a Mac "roughly 5x"; Pro Display XDR "400x SDR in the default XDR preset, when brightness is set to the minimum 4-nit value"; in the XDR preset "peak white is always 1,600 nits… EDRmax… is 3.2" at a 500-nit reference white. — [WWDC21 10161 "Explore HDR rendering with EDR"](https://developer.apple.com/videos/play/wwdc2021/10161/) [vendor session]
- `maximumExtendedDynamicRangeColorComponentValue` (EDRmax) "may dynamically change, since it is dependent on characteristics, such as display brightness or True Tone". "EDR values greater than EDRmax will clip to EDRmax." — [WWDC21 10161](https://developer.apple.com/videos/play/wwdc2021/10161/) [vendor session]
- `maximumPotentialExtendedDynamicRangeColorComponentValue` is the maximum "that might be renderable without clipping… if the display brightness and other features were set appropriately". It returns "1.0… for displays, or display presets, not supporting EDR". `maximumReferenceExtendedDynamicRangeColorComponentValue` is "the maximum EDR value that is guaranteed to be rendered without distortion, such as clipping or tone mapping". It returns "0.0… on displays that do not support reference rendering". The session does not explain reference modes beyond pointing to a "Discover Reference Mode" tech talk. — [WWDC21 10161](https://developer.apple.com/videos/play/wwdc2021/10161/) [vendor session]
- EDR also gives a "true HDR response, even on conventional, standard dynamic range displays… when those displays are viewed in dimmer environments with correspondingly dimmer brightness settings". SDR content "is compatible with EDR as-is in its native 0.0 to 1.0 range". — [WWDC21 10161](https://developer.apple.com/videos/play/wwdc2021/10161/) [vendor session]
- WWDC26 "Bringing Cyberpunk 2077 to Mac": the game "poll[s] `maximumExtendedDynamicRangeColorComponentValue` to get the current maximum EDR value… and then send[s] that to our tone mapper". It enables HDR automatically when "maximum potential EDR value is greater than 2.0". — [WWDC26 session 356](https://developer.apple.com/videos/play/wwdc2026/356/) [vendor session]
- The current MacBook Pro listing (M5 Pro/M5 Max on the page as fetched 2026-11-09) says: "XDR brightness: up to 1000 nits sustained full-screen, 1600 nits peak (HDR content only)", "SDR brightness: up to 1000 nits (outdoor)", "ProMotion technology with adaptive refresh rates up to 120Hz", "Fixed refresh rates: 47.95Hz, 48.00Hz, 50.00Hz, 59.94Hz, 60.00Hz". — [Apple MacBook Pro tech specs](https://www.apple.com/macbook-pro/specs/) [vendor doc]

**Layer setup and formats**
- Apple's EDR recipe is `metalLayer.wantsExtendedDynamicRangeContent = YES; metalLayer.colorspace = CGColorSpaceCreateWithName(kCGColorSpaceExtendedLinearDisplayP3); metalLayer.pixelFormat = MTLPixelFormatRGBA16Float;`. The pixel format must be one "that can represent values above 1.0… usually some form of floating point". — [WWDC21 10161](https://developer.apple.com/videos/play/wwdc2021/10161/) [vendor session]
- For PQ content, Apple's manual path is "converting to linear light by applying the inverse transfer function… dividing by the medium's reference white. For example, 100 nits for PQ content, so that reference white will be mapped to EDR 1.0, and the maximum PQ 10,000 nit value will map to EDR 100." Apple also states that "AVFoundation does not presently decode HDR formats, such as HDR10, to EDR". — [WWDC21 10161](https://developer.apple.com/videos/play/wwdc2021/10161/) [vendor session]
- For HLG, "HLG is decoded to the 0.0 to 12.0 EDR range, with EDR 1.0 representing reference white" (ImageIO). — [WWDC21 10161](https://developer.apple.com/videos/play/wwdc2021/10161/) [vendor session]. Apple's `CAEDRMetadata.hlg` docs reportedly say that for a linear float EDR layer you apply the HLG inverse OETF without normalisation, giving [0, 12]. — [Apple: CAEDRMetadata.hlg](https://developer.apple.com/documentation/quartzcore/caedrmetadata/hlg.md) [search summary]
- moonlight-qt's PQ passthrough pairs `MTLPixelFormatBGR10A2Unorm` with `kCGColorSpaceITUR_2100_PQ` for BT.2020 PQ, `kCGColorSpaceITUR_2020` for BT.2020 non-PQ, and BGRA8 + `kCGColorSpaceITUR_709` / sRGB for SDR. It sets `wantsExtendedDynamicRangeContent = !!(videoFormat & VIDEO_FORMAT_MASK_10BIT)`. — [moonlight-qt vt_metal.mm](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/vt_metal.mm) [code read, master @4113dd2]
- No source I found documents `bgr10_xr` / `MTLPixelFormatBGR10_XR` as an EDR layer format for this use. WWDC21 10161 does not cover bgr10a2 or bgr10_xr. — see Gaps.

**CAEDRMetadata (system tone mapping)**
- "The CAMetalLayer tone mapper is enabled via the 'CAEDRMetadata' attribute and is available on macOS." "System apps, as well as apps employing AVPlayer… use the CAMetalLayer tone mapper to provide media-specific, optical-to-optical transfer function, and soft clip". "Even enabling CAEDRMetadata-based tone mapping involves an extra processing pass. This, in turn, increases latency and bandwidth." — [WWDC21 10161](https://developer.apple.com/videos/play/wwdc2021/10161/) [vendor session]
- `hdr10(minLuminance:maxLuminance:opticalOutputScale:)` is available on macOS 10.15+. "Any content greater than the maximum luminance (`maxNits`) may be clamped." "The values in the drawable's texture are assumed to be proportional to the optical output (in cd/m^2) of the reference display. For example, if the optical output scale is 100, then a value of 1.0 is assumed to be 100 nits. If the content is in a normalized pixel format, set `opticalOutputScale` to 10000." — [Apple: CAEDRMetadata.hdr10(minLuminance:maxLuminance:opticalOutputScale:)](https://developer.apple.com/documentation/quartzcore/caedrmetadata/hdr10(minluminance:maxluminance:opticaloutputscale:).md) [vendor doc]
- `CAMetalLayer.edrMetadata` must be set before calling `nextDrawable()`. — [Apple: CAMetalLayer.edrMetadata](https://developer.apple.com/documentation/quartzcore/cametallayer/edrmetadata.md) [search summary]
- moonlight-qt sets `[CAEDRMetadata HDR10MetadataWithDisplayInfo:<mastering display colour volume> contentInfo:<content light level> opticalOutputScale:203.0]` for PQ streams that have mastering data ("to enable OS tonemapping"), and `EDRMetadata = nullptr` otherwise. — [moonlight-qt vt_metal.mm](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/vt_metal.mm) [code read]
- A developer report from NuvioDesktop PR #1042 (merged 2026-11-04): "`kCGColorSpaceITUR_2100_PQ` layer + `CAEDRMetadata`" playback went near black when "`NSScreen.maximumExtendedDynamicRangeColorComponentValue` is 1.0". This happened at the top two brightness steps on a MacBook Air M2 running macOS 26.6.2, and the fix was confirmed on an M2 with macOS 27. Removing the metadata alone didn't help while the content stayed PQ. The fix uses "`kCGColorSpaceExtendedLinearDisplayP3` with no `CAEDRMetadata`", with the peak set to live headroom × 203 nits, a 0.1 s timer following the headroom, `toneMapMode = never` on macOS 15+, and `preferredDynamicRange = high` plus `contentsHeadroom` on macOS 26+. — [NuvioDesktop PR #1042](https://github.com/NuvioMedia/NuvioDesktop/pull/1042) [single-dev report]
- Best practice: "enable EDR when there is both HDR content and potential EDR headroom available. Disable EDR when this is not the case". Float buffers cost bandwidth and power. — [WWDC21 10161](https://developer.apple.com/videos/play/wwdc2021/10161/) [vendor session]
- wgpu's Metal backend states in a code comment: "`CAMetalLayer` color-matches layer contents to whatever display the window is on, with the compositor tone-mapping where needed, so Display-P3 and HDR (PQ/HLG) color spaces work regardless of the physical display's gamut". — [wgpu-hal metal/adapter.rs (trunk)](https://github.com/gfx-rs/wgpu/blob/trunk/wgpu-hal/src/metal/adapter.rs) [code read; a developer's comment, not Apple's]

**macOS 26/27 changes**
- `CALayer.contentsHeadroom` (a `CGFloat`) is new in macOS/iOS 26.0. The page has no discussion text. — [Apple: CALayer.contentsHeadroom](https://developer.apple.com/documentation/quartzcore/calayer/contentsheadroom.md) [vendor doc]
- An unofficial WWDC25 Camera/Photos lab Q&A says Core Image, ImageKit, Core Animation and Core Graphics gained a system tone mapper, and that `CALayer` has `preferredDynamicRange` (high / constrained / standard). — [WWDC25 lab Q&A gist](https://gist.github.com/samhenrigold/cec7000aaadd55e22bed5f2300422e26) [search summary; unofficial]. One project lists `preferredDynamicRange` as macOS 14+ and `toneMapMode` as macOS 15+. — [MacLC](https://github.com/OZBM/MacLC) [search summary; single dev]
- macOS 27 lets a third-party HDR display keep HDR on at a scaled resolution (on Tahoe, "macOS automatically switches back to Standard Dynamic Range"). It was tested on an M4 MacBook Pro with a Dell U3226Q and did not work on an M1 Max. — [9to5Mac, 2026-10-05](https://9to5mac.com/2026/10/05/macos-27-just-fixed-the-most-annoying-problem-for-third-party-hdr-displays/) [press, single tester]
- A developer forum thread reports that on macOS 26, third-party external displays in HDR mode misbehave after sleep/wake. DTS said engineering would investigate. — [Apple Developer Forums thread 810008](https://www.developer.apple.com/forums/thread/810008) [search summary]
- SDL3 documents `SDL_PROP_WINDOW_SDR_WHITE_LEVEL_FLOAT` as "always 1.0 for EDR content" on Apple platforms, i.e. EDR 1.0 is SDR white. — [SDL3 wiki: SDL_GetWindowProperties](https://wiki.libsdl.org/SDL3/SDL_GetWindowProperties) [vendor doc]

### Inferences
- **Recommended Cha path (a):** use an `Rgba16Float` surface, an extended-linear colour space, and `wantsExtendedDynamicRangeContent = YES` only while an HDR stream plays on a screen whose potential headroom is above 1. Write a shader path for PQ streams: YCbCr→R'G'B' (BT.2020 NCL matrix, already recognised) → PQ EOTF → nits → divide by a reference white → BT.2020→BT.709 (or P3) primaries, letting negative values carry out-of-gamut colour in extended range → tone-map highlights (for example a BT.2390-style roll-off) to the live `maximumExtendedDynamicRangeColorComponentValue`. This keeps tone mapping in our own single pass, avoids Apple's extra CAEDRMetadata pass (Apple says it adds latency), and avoids the PQ-layer black-at-headroom-1.0 failure reported on macOS 26/27.
- **Reference white:** moonlight-qt (`opticalOutputScale:203`) and NuvioDesktop (headroom × 203 nits) both map 203 nits (the BT.2408 HDR reference white) to EDR 1.0. Apple's 2021 talk uses 100 nits. 203 keeps streamed desktop/UI white at macOS SDR white, so it suits game and desktop streams. Make it one constant and A/B it on the M4 Pro panel.
- **Fallback path (b):** an `Rgb10a2Unorm` (BGR10A2) surface with `kCGColorSpaceITUR_2100_PQ` and `CAEDRMetadata.hdr10(displayInfo:contentInfo:opticalOutputScale:203)`. This is moonlight-qt's approach. It needs the least shader work (PQ passes through) and gives the OS soft-clip, but adds a compositor pass and inherits OS tone-mapper behaviour.
- **SDR displays and dim brightness:** when potential headroom ≤ 1.0 (an SDR external display, or EDR not supported), turn EDR off, tone-map PQ→SDR in the shader and present on the existing Bgra8Unorm path. When current headroom is low but potential is high (bright ambient or a high brightness setting), stay in EDR and compress harder, as Cyberpunk's live polling does.
- **XDR reference modes:** with a reference preset selected, `maximumReference…` is non-zero and tone mapping should target that value without exceeding it. This is untested; see Gaps.
- `contentsHeadroom` / `preferredDynamicRange` / `toneMapMode` appear to be the newer per-layer controls that stop the OS re-mapping EDR values. They are documented only as symbols (or not at all), so treat them as optional extras to try on macOS 26+, not as the core design.

### Gaps
- No Apple WWDC25/WWDC26 session dedicated to EDR/HDR rendering was found. The only WWDC26 material is the Cyberpunk case study. "Adaptive HDR" as a named macOS 26/27 developer feature was not found.
- No primary documentation of `CALayer.preferredDynamicRange` / `toneMapMode` semantics or OS versions was found (single-dev and unofficial sources only).
- No measured headroom values for the M4/M4 Pro MacBook Pro at different brightness settings, and no first-party description of how the XDR panel's reference presets change the three NSScreen values on MacBook Pro.
- No source confirms whether `MTLPixelFormatBGR10_XR` works as an EDR layer format, or whether a PQ-tagged `RGBA16Float` layer behaves differently from BGR10A2.

## 2. VideoToolbox HDR decode: P010 output, colour attachments, codecs and latency

### Takeaway
Cha's decoder asks VideoToolbox only for 8-bit NV12, so today any HEVC Main10 stream reaches the shader at 8 bits (presumably converted by VT). The first HDR change is to request `kCVPixelFormatType_420YpCbCr10BiPlanarVideoRange` / `FullRange` (x420/xf20), which the texture path already maps to `R16Unorm`/`RG16Unorm`. HDR10 mastering metadata is a big-endian CFData blob. moonlight-qt takes it from the host's control stream rather than from the bitstream. AV1 hardware decode is M3-and-later only.

### Cited Findings
- Cha code: `VideoToolbox::open` builds the destination attributes from `[kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange, kCVPixelFormatType_420YpCbCr8BiPlanarFullRange]` only, with the comment "The decoder picks among the formats we can draw". The 10-bit constants are imported and used only to classify frames (`is_10bit`, full-range), and the BT.2020 YCbCr matrix attachment is read. No transfer-function attachment is read. — `/home/user/cha-portal/crates/cha-player/src/video/videotoolbox.rs` (around lines 60–110 and 214–233) [code read]
- Cha code: the Metal present module already maps 16-bit planes to `MTLPixelFormat::R16Unorm`→`wgpu::TextureFormat::R16Unorm` and `RG16Unorm`→`Rg16Unorm`. — `/home/user/cha-portal/crates/cha-player/src/present/metal.rs` (around lines 130–141) [code read]. The YCbCr→RGB shader ends with `clamp(rgb, vec3(0.0), vec3(1.0))`. — `/home/user/cha-portal/crates/cha-player/src/render/video.wgsl` line 38 [code read]
- moonlight-qt maps VideoToolbox 10-bit planes to `MTLPixelFormatR16Unorm` / `MTLPixelFormatRG16Unorm` and uses `bitnessScaleFactor` 1 for VT frames (P010-style MSB-aligned samples read directly as 16-bit unorm). — [moonlight-qt vt_metal.mm](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/vt_metal.mm) [code read]
- `kCVImageBufferMasteringDisplayColorVolumeKey` (macOS 10.13+) is a CFData containing "big-endian data to match the payload of ISO/IEC 23008-2:2015(E), D.2.28 mastering display color volume in the supplemental enhancement information (SEI) message". — [Apple: kCVImageBufferMasteringDisplayColorVolumeKey](https://developer.apple.com/documentation/corevideo/kcvimagebuffermasteringdisplaycolorvolumekey.md) [vendor doc]
- moonlight-qt does not rely on VideoToolbox attachments for HDR10 metadata. `VTBaseRenderer::setHdrMode` calls `LiGetHdrMetadata(&hdrMetadata)` (metadata sent by the host over the control stream), byte-swaps primaries and white point (`__builtin_bswap16`) into the SEI layout, and builds the mastering and content-light-level CFData that it passes to `CAEDRMetadata`. It switches to PQ handling when FFmpeg reports `color_trc == AVCOL_TRC_SMPTE2084`. — [moonlight-qt vt_base.mm](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/vt_base.mm), [vt_metal.mm](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/vt_metal.mm) [code read]
- AV1: hardware decode through VideoToolbox is gated to Apple silicon M3 and later. FFmpeg developers note that Apple provides no software AV1 path before M3. — [oxideav-videotoolbox README](https://docs.rs/crate/oxideav-videotoolbox/latest/source/README.md) [single-dev crate]; [FFmpeg trac #10642](https://trac.ffmpeg.org/ticket/10642) [search summary]. `VTIsHardwareDecodeSupported(kCMVideoCodecType_AV1)` returned YES on an iPhone 15 Pro Max. — [Apple Developer Forums 739953](https://developer.apple.com/forums/thread/739953) [search summary]. Calling `VTRegisterSupplementalVideoDecoderIfAvailable()` first was needed to make it return true. — [MacRumors thread](https://forums.macrumors.com/threads/apple-m1-vp9-av1-decoding.2269938/page-4) [search summary; anecdote]. Current MacBook Pro media engines list "AV1 decode", and the playback list includes "HDR with Dolby Vision, HDR10+/HDR10, and HLG". — [Apple MacBook Pro specs](https://www.apple.com/macbook-pro/specs/) [vendor doc]

### Inferences
- **Changes in `videotoolbox.rs`:** (1) add `kCVPixelFormatType_420YpCbCr10BiPlanarVideoRange` and `…FullRange` to the requested formats, at least when the stream's SPS says 10-bit or when the user allows HDR. Requesting 8-bit for a Main10 stream almost certainly makes VT convert, losing the 10-bit PQ precision that HDR needs. (2) On each output `CVPixelBuffer`, read `kCVImageBufferTransferFunctionKey` (`…SMPTE_ST_2084_PQ` / `…ITU_R_2100_HLG`), `kCVImageBufferColorPrimariesKey`, `kCVImageBufferMasteringDisplayColorVolumeKey` and `kCVImageBufferContentLightLevelInfoKey`, and pass them to the renderer the way the matrix already is. Whether VT copies the VUI transfer function and the SEI mastering blobs onto output buffers for a stream created from parameter sets is unverified; log the attachments on a real Main10 PQ stream from the node.
- **Fallback for metadata:** if the node's encoder emits no mastering-display/CLL SEI, Cha should either carry the values on `cha-stream/1` (as GameStream's control channel does for Moonlight) or assume defaults (e.g. 1000-nit max mastering) when tone mapping. Path (a) in §1 only needs MaxCLL/max mastering luminance, and it can fall back to 1000 nits.
- The P010 → `R16Unorm` textures carry 10-bit codes MSB-aligned. Cha's `color.rs` test "ten_bit_codes_land_on_the_same_levels" suggests the existing range scaling already accounts for this, so only the transfer function and clamp need to change for HDR.
- PyroWave (`cha-pyrowave-wgpu`) decodes on the GPU and would need its own HDR plumbing (bit depth and transfer function on the wire). That is outside VT and is not covered here.

### Gaps
- No first-party statement confirming HEVC Main10 hardware decode on M1 and later was retrieved in this session. It is widely assumed but was not fetched here.
- No measurement of VideoToolbox decode latency for 10-bit HEVC or AV1 versus 8-bit on M-series was found.
- Unverified whether VT sets `kCVImageBufferMasteringDisplayColorVolumeKey` / `ContentLightLevelInfoKey` on decoded buffers from in-band SEI.

## 3. wgpu and HDR surfaces (and egui on them)

### Takeaway
wgpu 30 (2026-07-01) added HDR surfaces: `SurfaceConfiguration::color_space`, per-format colour-space capabilities, and `Surface::display_hdr_info` (EDR headroom on Metal). Its Metal backend sets `wantsExtendedDynamicRangeContent` and the layer `colorspace` itself. Two cautions apply. In the latest release (30.0.1, 2026-08-21), configuring `Bt2100Pq`, `Bt2100Hlg` or `ExtendedDisplayP3` on Metal crashes; the fix (#10175) is only on trunk, and its v30 backport (#10672) has been open since 2026-10-20. `Rgba16Float` + `ExtendedSrgbLinear` is not affected. Cha must move from wgpu 29 + egui 0.35 to wgpu 30 + egui 0.36/0.37, and should render egui into an offscreen 8-bit texture composited at EDR 1.0.

In October 2025 the maintainers concluded that surfaces should expose "a data format plus color space bitflags". A fork commit "metal: pin extendedDisplayP3 colorspace for EDR surfaces" (anchpop/wgpu, 2026-06-07) is referenced from the issue. — [wgpu #2920](https://github.com/gfx-rs/wgpu/issues/2920)
- **v30.0.0 (2026-07-01):** "Surfaces can now be configured with an explicit color space… `SurfaceConfiguration` has a new `color_space` field, and `SurfaceCapabilities` reports the supported color spaces for every supported format in a new `format_capabilities` field." `SurfaceColorSpace::Auto` keeps the old behaviour ("extended linear scRGB for `Rgba16Float` where supported, sRGB otherwise; never a wide-gamut or HDR color space"). ### Inferences
- **What Cha must change for HDR on wgpu:**
  1. Bump the workspace `wgpu` to 30.0.1 and `egui`/`egui-wgpu`/`egui-winit` to 0.36.x or 0.37 (winit stays 0.30). Migrate `Queue::present`, the `create_texture_from_hal(..., initial_state)` call in `present/metal.rs`, and the `color_space` field.
  2. For HDR streams, configure `format: Rgba16Float, color_space: ExtendedSrgbLinear`. It works on 30.0.1 because it uses the static `kCGColorSpaceExtendedLinearSRGB`, and wgpu then sets `wantsExtendedDynamicRangeContent = YES` itself. Write linear BT.709-primaries values, negatives allowed for BT.2020 colours outside 709, scaled so 1.0 = SDR white. For SDR streams, reconfigure back to `Bgra8Unorm` + `Srgb` (EDR off, saving power as Apple advises).
  3. Read the headroom each frame or on change with `surface.display_hdr_info(&adapter)` on the main thread (winit's event loop thread), and pass `headroom.current` as a uniform to the tone-map pass.
  4. Wait for #10175 in a release (or use a git dependency or a vendored patch) before trying `Bt2100Pq` on `Rgb10a2Unorm` (path (b)). Otherwise set the PQ colorspace and `edrMetadata` by hand through `as_hal::<Metal>()` → `render_layer()`. wgpu 30 re-sets `colorspace` on every `configure` (resize), so a hand-set colorspace must be reapplied after each configure. Set `edrMetadata` before `get_current_texture`, since Apple requires it before `nextDrawable`.
  5. The fix for oversaturated sRGB on wide-gamut displays (#10286, trunk only) suggests that wgpu 29/30.0.1 SDR surfaces may be left untagged, so Cha's SDR picture may look oversaturated on the MacBook's P3 panel today. Check on the Mac; until a release includes it, an `as_hal` workaround that sets `kCGColorSpaceSRGB` would fix it.
- **egui on an HDR surface:** with `Rgba16Float` (not `is_srgb()`), egui-wgpu would write gamma-encoded values that the EDR layer reads as linear, so the UI would look washed out and too bright in midtones. Render egui into a fixed `Bgra8Unorm` (or `Rgba8Unorm`) offscreen texture, keeping one `egui_wgpu::Renderer` whose output format never changes between SDR and HDR. Then composite it over the video in the final pass, decoding sRGB→linear and scaling by the SDR white (1.0 on macOS EDR, `SdrWhiteLevel/80` on Windows scRGB). The SGSR pass (`cha-upscale`) and PyroWave's render pass must also stop clamping to [0,1] and use a float intermediate when HDR is on.
- The `03_hdr_surface` example in wgpu is the closest reference implementation; read it before writing Cha's path.

## 4. Frame pacing and VRR on macOS: CAMetalDisplayLink, ProMotion, Adaptive-Sync, present APIs, and what wgpu does today

### Takeaway
Today Cha runs wgpu's Metal `Immediate` mode (Mailbox doesn't exist on Metal): `displaySyncEnabled = NO`, `maximumDrawableCount = 2`, presenting each frame as it decodes. `CAMetalDisplayLink` (macOS 14+) is Apple's recommended pacing tool. It hands you a drawable plus a target presentation time, honours `preferredFrameRateRange`, and is how moonlight-qt paces with V-Sync on. Adaptive-Sync on external displays needs native full screen, and one developer measured windowed display-link latency at 5 refreshes against 2 in full screen at 120 Hz. So C2.4 should compare full-screen modes first. wgpu has no display-link or timed-present API, so the paced path has to drive the drawable itself through the hal.

### Cited Findings
**What Cha and wgpu do now**
- Metal offers only `Fifo` (`displaySyncEnabled = true`) and `Immediate` (`false`). Cha's preference list (Mailbox, Immediate, Fifo) therefore resolves to Immediate. `desired_maximum_frame_latency: 1` gives `maximumDrawableCount = 2`, and wgpu sets `allowsNextDrawableTimeout = false`. — [wgpu-hal metal/adapter.rs](https://github.com/gfx-rs/wgpu/blob/trunk/wgpu-hal/src/metal/adapter.rs), [surface.rs](https://github.com/gfx-rs/wgpu/blob/trunk/wgpu-hal/src/metal/surface.rs); `/home/user/cha-portal/crates/cha-player/src/render/mod.rs` [code read]
- moonlight-qt's comment on `m_MetalLayer.displaySyncEnabled = params->enableVsync`: "Allow tearing if V-Sync is off (also requires direct display path)". In other words, a windowed (composited) layer doesn't tear even with display sync off. — [moonlight-qt vt_metal.mm](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/vt_metal.mm) [code read]

**CAMetalDisplayLink**
- Available on macOS 14.0+ / iOS 17+. "A specialized way to interact with variable-rate displays when you need more control over the timing window to render your app's frames." It is created from a `CAMetalLayer` and added to a run loop, and the delegate's `metalDisplayLink(_:needsUpdate:)` is called "based on the `preferredFrameRateRange` and `preferredFrameLatency`… The system makes a best effort to make callbacks at appropriate times." `preferredFrameLatency` is "the amount of time, in frames, your app requests to render a frame". An `Update` carries the drawable and timestamps. — [Apple: CAMetalDisplayLink](https://developer.apple.com/documentation/quartzcore/cametaldisplaylink.md) [vendor doc]
- An Apple DTS engineer (Sep 2024): "For frame pacing in particular we strongly advise using CAMetalDisplayLink over CADisplayLink". "2 drawables is ok on macOS assuming you're within frame budget". `setDisplaySyncEnabled(true)` "attempts to lock display updates to vsync". — [Apple Developer Forums 763426](https://developer.apple.com/forums/thread/763426) [vendor engineer, forum]
- On the same thread, a developer reports that on a ProMotion M1 Max, work finishing well before vsync still waited about 8 ms more, `presentDrawableAfterMinimumDuration` with 4 ms "doesn't seem to make much of a difference", and CAMetalDisplayLink "does not seem to like the Sync being enabled especially if you have an external monitor attached". — [Apple Developer Forums 763426](https://developer.apple.com/forums/thread/763426) [single-dev report]
- **Measured (frameclock PR #9, Oct 2026, a 120 Hz Mac, model and OS not given):** from update to target present, windowed was **41.6 ms (5 refreshes)** and full screen through Spaces was **16.3 ms (2 refreshes)**. Actual present landed within 0.01 ms of the link's target, and `preferredFrameLatency` 1 vs 2 made "no difference". The presented handler ran off the main thread for 235/236 frames. Skipped updates left drawables unpresented while the link kept ticking. — [forest-rs/frameclock PR #9](https://github.com/forest-rs/frameclock/pull/9) [single-dev measurement]
- One app reports that in macOS full screen on a ProMotion built-in display, the display link ticked at about 15 Hz and the game fell to about 30 fps, while a fixed 60 Hz or a zoomed window held 60 (cause unknown). — [nxnative #348](https://github.com/seedds/nxnative/issues/348) [single-dev report; search summary]. Another notes `preferredFrameRateRange` is best effort and that refresh/N requests rounded to exactly 144/n on a 144 Hz panel. — [harmonigraph #1551](https://github.com/yan-h/harmonigraph/issues/1551) [single-dev report; search summary]
- An older iOS developer report: with `maximumDrawableCount = 3`, CPU-to-display latency varied between about 50, 30 and ≤16 ms depending on queue state. `presentDrawable` means "as soon as possible after all the other frames in the queue have been presented". — [Apple Developer Forums 711033](https://developer.apple.com/forums/thread/711033) [single-dev report, 2022, iPhone]

**Adaptive-Sync / VRR and the present APIs**
- WWDC21 "Optimize for variable refresh rate displays": you need "a supported Mac. Any Mac with an Apple Silicon GPU", "a supported Adaptive-Sync display… selecting the new variable refresh rate available in Display System Preferences. And lastly, your app needs to be running in full-screen mode." It detects Adaptive-Sync with `NSScreen.minimumRefreshInterval != maximumRefreshInterval` combined with a full-screen window check. "On an Adaptive-Sync display, your frame is presented to the display immediately after it is done, so your app incurs only a 1ms penalty", whereas on a fixed display a late frame is shown for 16 ms instead of 8. "Once the maximum time has elapsed, the system must refresh the panel." Apple recommends `presentDrawable:afterMinimumDuration:` or `presentDrawable:atTime:` and "present frames at the highest rate your app can do so evenly". Below the display's minimum rate "the display might become unavailable for new frames, which could induce judder". The session's example display runs at 40–120 Hz, and ProMotion adapts "all the way down to 24Hz" (said of iPad). — [WWDC21 10147](https://developer.apple.com/videos/play/wwdc2021/10147/) [vendor session]
- Apple Support: Adaptive-Sync needs macOS Monterey or later, and a Thunderbolt/USB-C/DisplayPort cable: "Do not use an HDMI cable or adapter". It is enabled with Variable/Adaptive in Displays > Refresh Rate, and the range comes from the display. — [Apple Support 102144](https://support.apple.com/102144) [vendor doc; search summary of page]
- moonlight-qt #1509 (M4 Mac mini, macOS 15.2, Jan 2025): VRR worked only in "Fullscreen" with V-Sync on (the monitor followed a 72 fps game at 72 Hz). In borderless windowed mode the monitor stayed at 143 Hz. On 15.3.1, borderless full screen with V-Sync also worked. The issue was closed 2025-10-19 as fixed, with no explanation. — [moonlight-qt #1509](https://github.com/moonlight-stream/moonlight-qt/issues/1509) [user report]
- The built-in MacBook Pro panel: "ProMotion technology with adaptive refresh rates up to 120Hz", plus fixed 47.95/48/50/59.94/60 Hz modes. — [Apple MacBook Pro specs](https://www.apple.com/macbook-pro/specs/) [vendor doc]

**moonlight-qt's pacing on macOS**
- It uses `CAMetalDisplayLink` (macOS 14+) only when `displaySyncEnabled` (V-Sync on) and on Apple silicon. It sets `preferredFrameLatency = 1.0f` and `preferredFrameRateRange = CAFrameRateRangeMake(fps, fps, fps)` (a fixed range at the stream's rate), on the main run loop in common modes. Decoded frames replace any unrendered one (stale frames dropped), and in the callback it waits "up to half the per-frame interval for a new frame". It presents with plain `[commandBuffer presentDrawable:]`, then `commit` and `waitUntilCompleted`, and has no `atTime`/`afterMinimumDuration`. Without the link it calls `nextDrawable` and renders immediately. — [moonlight-qt vt_metal.mm](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/vt_metal.mm) [code read]

### Inferences
- **What Cha should build for C2.4 (in order):**
  1. **Measure first.** Record decode-complete time (VT output callback; PyroWave GPU completion) and the drawable's presented time (`MTLDrawable` presented handler, which frameclock relies on), and report decode-to-photon in the stats panel. wgpu doesn't expose the drawable's presented handler, so this needs the hal path below or a hal accessor. The glass-to-glass rig is still needed for the photon side.
  2. **Modes to A/B on the M4 Pro**, windowed and native full screen (green button): (A) today's Immediate; (B) display-link paced: `CAMetalDisplayLink` on the layer, `preferredFrameRateRange` = (fps, fps, fps) like Moonlight (or (fps, fps, max) to let ProMotion pick), `preferredFrameLatency = 1`, render the newest decoded frame (waiting at most half an interval) into `update.drawable`, present; (C) full-screen VRR (ProMotion or Adaptive-Sync external): present each frame as soon as it is decoded and drawn, with the panel following the source rate. Apple says Adaptive-Sync presents "immediately after it is done", so C should beat B on latency where it applies.
  3. **Integrating with wgpu:** CAMetalDisplayLink supplies its own `CAMetalDrawable`, while wgpu's `get_current_texture` calls `nextDrawable` itself, and two consumers of one layer will compete for its 2–3 drawables. The paced path should bypass `wgpu::Surface` for presentation: wrap `update.drawable.texture` with `create_texture_from_hal::<Metal>` (wgpu 30 needs `initial_state`), render video, upscaling and the egui composite with wgpu, `queue.submit`, then present via a raw `MTLCommandBuffer` committed on wgpu's own `MTLCommandQueue` (from `Queue::as_hal`, same-queue ordering), or order it with `metal::Queue::add_signal_event`. The display link's callbacks arrive on a run loop, so the decoded-frame hand-off must be thread-safe (Moonlight's `m_FrameReady` pattern). No Rust/wgpu project doing exactly this was found.
  4. **Full screen matters:** Adaptive-Sync needs full screen. The frameclock data shows windowed composition adding about 3 refreshes (about 25 ms at 120 Hz), and Game Mode (prior research 09) also needs full screen. Cha's latency target (≤ 12 ms p50 at 120 Hz) is probably reachable only in native full screen. The stats should show whether the window is full screen and `NSScreen.minimumRefreshInterval`/`maximumRefreshInterval`.
  5. Keep `desired_maximum_frame_latency: 1` (2 drawables). DTS says that's fine on macOS within budget. Watch for `nextDrawable` stalls (the forum reports) and fall back to 3 if they appear.
- On ProMotion, a fixed (fps, fps, fps) range at 60 should make the panel run at 60 Hz for a 60 fps stream, avoiding judder from 2:2 pulldown misalignment. Check for the ~15 Hz full-screen anomaly reported by nxnative.

### Gaps
- No independent glass-to-glass measurement on Apple silicon comparing immediate present, display-link pacing and VRR was found (frameclock measures target time, not photons).
- Not confirmed by Apple: whether the built-in ProMotion panel gives true per-frame VRR (present-when-ready) to windowed apps or only in full screen, and the panel's minimum refresh on M4 MacBook Pros (24 Hz is stated only for iPad ProMotion).
- How `presentDrawable:atTime:` interacts with `CAMetalDisplayLink` and ProMotion on macOS 26/27 is undocumented.
- The Apple Support Adaptive-Sync page's supported-Mac list and range rules were seen only through a search summary.

## 5. moonlight-qt and other native clients

### Takeaway
moonlight-qt is the most detailed open reference. On macOS it does PQ passthrough (BGR10A2 + ITUR_2100_PQ + CAEDRMetadata at 203 nits) and paces with CAMetalDisplayLink at a fixed stream rate when V-Sync is on. On Windows it uses a flip-discard D3D11 swap chain with R10G10B10A2 + `SetColorSpace1(G2084_P2020)` and tearing for V-Sync off. Its libplacebo/Vulkan renderer uses FIFO for V-Sync and IMMEDIATE otherwise. Little is documented for Steam Link, Parsec or airwave. GeForce NOW's Mac app advertises HDR, Cloud G-SYNC and up to 360 fps.

### Cited Findings
- **Settings:** the "V-Sync" tooltip reads "Disabling V-Sync allows sub-frame rendering latency, but it can display visible tearing". The "Frame pacing" tooltip reads "Frame pacing reduces micro-stutter by delaying frames that come in too early". — [moonlight-qt SettingsView.qml](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/gui/SettingsView.qml) [code read]
- **Pacer:** a vsync thread drives `handleVsync`. When the stream fps ≥ display fps it keeps "a rolling 500 ms window of pacing queue history" and drops frames only if the queue is consistently above target (drop target 1, or 3 per history). It has DX and Wayland vsync sources. — [moonlight-qt pacer.cpp](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp) [code read]
- **macOS Metal renderer:** see §1 and §4. The fragment shader `ps_draw_biplanar` returns `yuv * cscParams.matrix` after offsets, with no PQ EOTF and no clamp, so PQ code values go straight to a PQ-tagged layer. — [moonlight-qt vt_renderer.metal](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/shaders/vt_renderer.metal) [code read]. `getDecoderColorspace()` returns Rec. 601 ("macOS seems to handle Rec 601 best"). — [vt_metal.mm](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/vt_metal.mm) [code read]
- **macOS AVSampleBufferDisplayLayer renderer:** this older path uses a `CVDisplayLink` output callback to signal vsync to the pacer, and enqueues sample buffers into an `AVSampleBufferDisplayLayer`. — [moonlight-qt vt_avsamplelayer.mm](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/vt_avsamplelayer.mm) [code read]
- **Windows D3D11VA renderer:** `DXGI_SWAP_EFFECT_FLIP_DISCARD`, `BufferCount = 3 + 1 + 1`. It deliberately does not call `SetMaximumFrameLatency(1)`, because "our SyncInterval 0 Present() calls will block on DWM (acting like SyncInterval 1)". It uses `DXGI_FORMAT_R10G10B10A2_UNORM` for 10-bit streams. When V-Sync is off and `DXGI_FEATURE_PRESENT_ALLOW_TEARING` is supported it sets `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING` and presents with `DXGI_PRESENT_ALLOW_TEARING` at sync interval 0. When the frame's transfer function changes it calls `SetColorSpace1(DXGI_COLOR_SPACE_RGB_FULL_G2084_NONE_P2020)` for PQ, or `…G22_NONE_P709` for SDR. At this commit the file has no `SetHDRMetaData` call. — [moonlight-qt d3d11va.cpp](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/d3d11va.cpp) [code read @4113dd2]
- **libplacebo/Vulkan renderer (plvk):** with V-Sync on it uses `VK_PRESENT_MODE_FIFO_KHR` ("FIFO mode improves frame pacing compared with Mailbox"). With V-Sync off it tries IMMEDIATE, then FIFO_RELAXED, then MAILBOX, then FIFO. For HDR it requires a device exposing `VK_COLOR_SPACE_HDR10_ST2084_EXT` and retries without. It sets an initial scRGB colorspace hint "to ensure that MoltenVK sets wantsExtendedDynamicRangeContent", and on frame colour changes calls `pl_swapchain_colorspace_hint`. — [moonlight-qt plvk.cpp](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/plvk.cpp) [code read]
- **Other moonlight work:** PR #1557 (open since 2025-03) adds MetalFX spatial upscaling in `vt_metal.mm`. — [moonlight-qt PR #1557](https://github.com/moonlight-stream/moonlight-qt/pull/1557) (from research note 11). The Nonary moonlight-qt VRR beta builds (v6.1.0-vrr*) target Windows/Linux pacing: "Previously, VRR did not always work as intended because Moonlight's frame pacing was not properly synchronized with the display". — [Nonary/moonlight-qt releases](https://newreleases.io/project/github/Nonary/moonlight-qt/release/v6.1.0-vrr14) [search summary]
- **moonlight-ios PR #535:** decodes with VideoToolbox manually instead of submitting straight to `AVSampleBufferDisplayLayer`, queues frames and submits them from a display-link callback using host PTS. A maintainer expected smoother "low latency pacing mode" but not lower latency, and suggested PTS scheduling only for HDR streams if it regressed pacing. — [moonlight-ios PR #535](https://worker-github.zxx930427.workers.dev/moonlight-stream/moonlight-ios/pull/535) [search summary via a mirror]
- **GeForce NOW (macOS app):** NVIDIA's requirements page says a membership "is required for features like 5K/4K/UW streaming resolutions, NVIDIA RTX, HDR, Cloud G-SYNC, and 90/120/240/360 FPS streaming on the native macOS app". Some regional pages say Ultimate, others Premium. "120 FPS streaming will require a monitor that supports at least 120Hz, such as… a MacBook Pro 14" or 16" with ProMotion". At CES 2026, "streaming at 120 FPS now adapts to follow your game's FPS when it falls below 120 FPS on the native Windows and macOS app". — [NVIDIA GFN system requirements (en-gb)](https://www.nvidia.com/en-gb/geforce/products/geforce-now/system-reqs/), [GFN release highlights](https://www.nvidia.com/en-us/geforce-now/release-highlights/) [vendor doc; search summary; tier conflict unresolved]
- **airwave** (a macOS client in research note 11): its PR #12 measured MetalFX spatial at 5–10 ms GPU per frame on an M3 Pro. No HDR or pacing details were found. — [airwave PR #12](https://github.com/rkanjani/airwave/pull/12)

### Inferences
- Cha can copy two of Moonlight's macOS choices straight away: (1) a fixed `preferredFrameRateRange` equal to the stream fps, with a "newest frame wins, wait ≤ half an interval" hand-off; (2) metadata carried by the session protocol rather than parsed from SEI. It should differ on tone mapping (own shader into extended linear, §1) and on presentation (measure `atTime`/full-screen VRR instead of `waitUntilCompleted`, which blocks the render thread).
- Moonlight's pattern of "V-Sync off → immediate/tearing, V-Sync on → display link/FIFO, plus an optional frame-pacing queue" is a good model for Cha's settings. Cha's C2.4 could expose the same two toggles and default from the measurements.
- GFN's "adapts to follow your game's FPS" on macOS implies it drives ProMotion/VRR at the content rate, which is the behaviour C2.4 wants. Its implementation isn't documented.

### Gaps
- Nothing was found on how Steam Link (macOS), Parsec (macOS) or GeForce NOW implement HDR/EDR or pacing on Macs. Parsec and Steam Link Mac HDR support was not confirmed.
- No moonlight-qt PR or issue explaining why the CAMetalDisplayLink path is limited to V-Sync on with Apple silicon, and no latency numbers for its modes on macOS.
- Whether moonlight-qt on Windows sends HDR metadata some other way (e.g. relying on the OS) was not checked beyond the d3d11va.cpp grep.

## 6. Windows (later player): DXGI HDR10/scRGB, SDR white level, VRR, and wgpu on D3D12/Vulkan

### Takeaway
On Windows, use a flip-model swap chain with either FP16 scRGB (`R16G16B16A16_FLOAT`, the default G10 P709; Microsoft's recommendation for general apps) or `R10G10B10A2_UNORM` + `SetColorSpace1(G2084_NONE_P2020)` (HDR10, for video/full-screen, no alpha blending). Scale SDR UI by `SdrWhiteLevel/80` in scRGB. VRR/tearing needs `ALLOW_TEARING` at sync interval 0. wgpu 30 covers the colour space on DX12 (`ExtendedSrgbLinear`, `Bt2100Pq`) and HDR info on DX12/Vulkan, but has no `SetHDRMetaData`.

### Cited Findings
- **Formats:** Option 1: "use FP16 pixel format and scRGB color space… We recommend that general-purpose apps use Option 1… a swap chain created with a floating point pixel format is treated as if it uses the `DXGI_COLOR_SPACE_RGB_FULL_G10_NONE_P709` color space", where "scRGB (1.0, 1.0, 1.0) encodes the standard D65 white at 80 nits". Option 2: `DXGI_FORMAT_R10G10B10A2_UNORM` with an explicit `IDXGISwapChain3::SetColorSpace1(DXGI_COLOR_SPACE_RGB_FULL_G2084_NONE_P2020)`, "available only if your app… Targets an HDR display, Uses Direct3D 12 or Direct3D 11, Swap chain doesn't require blending with alpha/transparency"; it "might provide better performance if your app is consuming HDR10-encoded content, such as a video player". A flip model (`FLIP_SEQUENTIAL` / `FLIP_DISCARD`) is required. — [Microsoft Learn: Use DirectX with Advanced Color](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range) (updated 2025-09-19) [vendor doc]
- **Detection:** Win32 apps use `IDXGIOutput6::GetDesc1` → `DXGI_OUTPUT_DESC1.ColorSpace` (G22 P709 = SDR, G2084 P2020 = HDR) plus luminance fields. They poll `IDXGIFactory1::IsCurrent` each frame, handle `WM_SIZE`, and pick the output with the greatest window intersection rather than calling `GetContainingOutput`. "SDR displays with Advanced Color capabilities are also reported as… G22_NONE_P709". — [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range) [vendor doc]
- **SDR white:** "Windows allows the user to adjust the *SDR reference white level*… On desktop HDR monitors, SDR reference white levels are typically set to around 200 nits." Desktop apps read it with `DISPLAYCONFIG_SDR_WHITE_LEVEL` and `QueryDisplayConfig`. For FP16/scRGB, "multiply the SDR color value by `SdrWhiteLevelInNits / 80`". If the app composites SDR and HDR into one surface, "you're responsible for performing the SDR reference white level adjustment yourself". On SDR Advanced Color displays, 1.0 is the display's maximum white (display-referred). If the display is in SDR mode, DWM clips an FP16 swap chain to [0, 1]. — [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range) [vendor doc]
- **VRR:** "Variable refresh rate displays require *tearing* to be enabled". It needs `DXGI_SWAP_EFFECT_FLIP_*`, `CheckFeatureSupport(DXGI_FEATURE_PRESENT_ALLOW_TEARING)`, `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING` at creation and on `ResizeBuffers`, and "DXGI_PRESENT_ALLOW_TEARING can only be used with sync interval 0… recommended… when… the app is in a windowed mode - including border-less fullscreen mode". — [Microsoft Learn: Variable refresh rate displays](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/variable-refresh-rate-displays) (updated 2025-04-15) [vendor doc]
- **wgpu:** in v30, DX12 supports `ExtendedSrgbLinear` (scRGB) and `Bt2100Pq` (on `Rgb10a2Unorm`) but not `ExtendedSrgb`, DisplayP3 or HLG. `display_hdr_info` is populated on DX12 and Vulkan on Windows. — [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md), [docs.rs SurfaceColorSpace](https://docs.rs/wgpu/latest/wgpu/enum.SurfaceColorSpace.html). Trunk (unreleased): "On Windows, only wait for the swapchain acquire fence in `Fifo` and `FifoRelaxed` present modes. It added acquire latency in `Immediate` and `Mailbox`" (#10714). — [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md) [changelog]
- moonlight-qt's D3D11 path (flip-discard, 5 buffers, R10G10B10A2 + G2084 P2020, tearing at interval 0, no `SetMaximumFrameLatency(1)`) is described in §5. — [moonlight-qt d3d11va.cpp](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/d3d11va.cpp) [code read]

### Inferences
- A Windows Cha Player built on the same wgpu code can use `Rgba16Float` + `ExtendedSrgbLinear` on DX12. The same extended-linear shader as macOS works, with one difference: 1.0 means 80 nits on Windows HDR versus SDR white on macOS. Multiply the composite by `SdrWhiteLevel/80` for UI and SDR video, and normalise HDR video to nits/80. `Bt2100Pq` on `Rgb10a2Unorm` is the cheaper video-player option. Our egui overlay is composited in-shader, so the no-alpha-blending constraint holds, but the UI must then be PQ-encoded at the SDR white level.
- HDR10 metadata (`IDXGISwapChain4::SetHDRMetaData`) would need `as_hal::<Dx12>()` to reach the raw swap chain. wgpu has no API for it, and Moonlight's current D3D11 path doesn't call it either. This is unverified as to what difference it makes on typical monitors.
- For VRR on Windows, wgpu's `Immediate` on DX12 presumably maps to sync interval 0 with tearing allowed; this is unverified in wgpu-hal source in this session. Trunk #10714 removes an acquire-fence wait that added latency in Immediate/Mailbox, so a Windows player should take the release that contains it.

### Gaps
- wgpu-hal's DX12 present-mode mapping (whether `Immediate` sets `ALLOW_TEARING`) and its handling of `IsCurrent`/output changes were not read.
- No measurement of Windows HDR10 vs scRGB latency or GPU cost for a streaming client was found.

## 7. Linux and Steam Deck OLED (later player): Vulkan HDR colour spaces and metadata, Wayland colour management, gamescope, VRR, present timing, SDL3

### Takeaway
Linux HDR for a Vulkan app is now standard plumbing. Mesa 25.1+ Wayland WSI exposes `VK_EXT_swapchain_colorspace` (HDR10_ST2084) and `VK_EXT_hdr_metadata` on compositors with `wp_color_management_v1` (KDE Plasma 6, GNOME 48+), NVIDIA 595.58.03+ has them too, and gamescope (`--hdr-enabled`) handles the Deck. `VK_EXT_present_timing` (Vulkan 1.4.335, Nov 2025) shipped in Mesa 26.1 for Wayland and was merged for X11 in 26.2. wgpu exposes HDR colour spaces on Vulkan but not present timing; trunk adds pNext hooks that could carry it.

### Cited Findings
- **Mesa colour management:** "The now-merged work for Mesa 25.1 plumbs in the Wayland color management protocol to the Vulkan windowing system integration… allows Mesa Vulkan drivers to support more color-spaces via VK_EXT_swapchain_colorspace and the VK_EXT_hdr_metadata". The work was by KDE's Xaver Hugl. — [Phoronix: Mesa Vulkan WSI supports Wayland colour management](https://www.phoronix.com/news/Mesa-Vulkan-WSI-HDR-CM) [press]
- `VK_COLOR_SPACE_HDR10_ST2084_EXT` is BT.2020 primaries encoded with SMPTE ST 2084 PQ. — [Vulkan: VkColorSpaceKHR](https://docs.vulkan.org/refpages/latest/refpages/source/VkColorSpaceKHR.html) [vendor doc; search summary]. On Wayland, `VK_COLOR_SPACE_PASS_THROUGH_EXT` disables WSI colour management so the app can create its own `wp_color_management_surface_v1`. — [Vulkan WSI chapter](https://docs.vulkan.org/spec/latest/chapters/VK_KHR_surface/wsi.html) [search summary]
- **Drivers and gamescope:** the Arch Wiki says HDR in Vulkan needs `VK_EXT_swapchain_colorspace` and `VK_EXT_hdr_metadata`, which "mesa 25.1 and later includes… by default. nvidia-open 595.58.03 and later also includes these extensions". Gamescope "is a requirement for HDR10 support when playing games", enabled with `--hdr-enabled`, and doesn't work with the KWin `vk-hdr-layer` (`ENABLE_HDR_WSI` must not be 1). VRR plus HDR can stutter from "long HDR compositing times"; on AMD the fix is experimental AMD colour management using hardware planes. — [Arch Wiki: HDR](https://wiki.archlinux.org/title/HDR), [Arch Wiki: Gamescope](https://wiki.archlinux.org/title/Gamescope) [community doc; search summary]
- **GNOME:** "Wayland color management 'wp_color_management_v1' protocol support was merged as a late addition to the GNOME 48 codebase". — [Phoronix](https://www.phoronix.com/news/GNOME-wp_color_management_v1) [press]. Heise says GNOME 48's HDR mostly affects GTK4 programs while other apps lag. — [heise](https://heise.de/-10321177) [press; search summary]. A secondary blog says a Mutter 50 RC NEWS file includes "Disable tone mapping with HDR". — [youngju.dev](https://www.youngju.dev/blog/2026-07-17-wayland-color-management-hdr-shipping-timeline-xserver.en) [search summary; secondary]
- **Present timing:** `VK_EXT_present_timing` arrived with Vulkan 1.4.335 (November 2025). Mesa 26.1.0 (2026-05-06) lists it for RADV, NVK, Turnip, ANV, Honeykrisp and panvk, with the Wayland implementation. X11/XWayland support by Valve's Hans-Kristian Arntzen was merged for Mesa 26.2. — [Mesa 26.1.0 release notes](https://docs.mesa3d.org/relnotes/26.1.0.html), [Phoronix: Mesa 26.2 X11 present timing](https://www.phoronix.com/news/Mesa-26.2-X11-Present-Timing) [vendor doc, press; search summary]
- **wgpu Vulkan hooks (trunk, unreleased):** `wgpu_hal::vulkan::Surface::set_next_present_chain` attaches a caller-provided `pNext` chain to the next `VkPresentInfoKHR` "for presentation extensions wgpu has no dedicated support for" (#9847). `set_next_swapchain_create_chain` / `Queue::set_next_submit_chain` make `VK_NV_low_latency2` (Reflex) usable (#10095). — [wgpu CHANGELOG](https://github.com/gfx-rs/wgpu/blob/trunk/CHANGELOG.md) [changelog]
- **SDL3:** `SDL_PROP_WINDOW_HDR_ENABLED_BOOLEAN` ("true if the window has HDR headroom above the SDR white point"), `SDL_PROP_WINDOW_SDR_WHITE_LEVEL_FLOAT` ("the scale factor to apply to an sRGB value of 1.0 to display it as SDR white in SDL_COLORSPACE_SRGB_LINEAR… On Windows this corresponds to the SDR white level in scRGB… On Apple platforms this is always 1.0 for EDR content") and `SDL_PROP_WINDOW_HDR_HEADROOM_FLOAT` (max brightness as a multiple of SDR white; 1.0 without HDR). All three can change on `SDL_EVENT_WINDOW_HDR_STATE_CHANGED`. — [SDL3 wiki: SDL_GetWindowProperties](https://wiki.libsdl.org/SDL3/SDL_GetWindowProperties) [vendor doc]
- **Steam Deck OLED:** "HDR OLED", 1280×800, "up to 90Hz", "1,000 nits peak brightness (HDR)", "600 nits (SDR)", "110% P3", and "Display port over Type C; up to 8K @60Hz or 4K @120Hz". The page doesn't mention VRR. — [Steam Deck tech specs](https://www.steamdeck.com/en/tech) [vendor doc]
- moonlight-qt's Vulkan renderer (FIFO/IMMEDIATE, HDR10_ST2084 check, libplacebo colorspace hints) is described in §5. — [moonlight-qt plvk.cpp](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/video/ffmpeg-renderers/plvk.cpp) [code read]

### Inferences
- A Linux Cha Player on wgpu/Vulkan can request `Bt2100Pq` (or `ExtendedSrgbLinear`) where `format_capabilities` reports it. That needs Mesa ≥ 25.1 or NVIDIA ≥ 595.58.03 and a colour-managed compositor (Plasma 6 / GNOME 48+), or gamescope with `--hdr-enabled` on the Deck. If a surface offers no HDR colour space, it should fall back to SDR tone mapping.
- The Deck OLED's SDR-to-HDR ratio is only about 1.7× (1000 nits peak vs 600 SDR, from Valve's specs), so tone mapping there should target a small headroom, much like an SDR-ish Mac display.
- Present timing on Linux would go through `VK_EXT_present_timing` structures passed with `set_next_present_chain` (trunk wgpu-hal) once it ships in a release. `vkSetHdrMetadataEXT` would need the raw `VkSwapchainKHR` via `as_hal::<Vulkan>()`. Neither is wrapped by wgpu.
- VRR on Linux is a compositor setting (adaptive sync per output) combined with FIFO/IMMEDIATE presentation, which is what moonlight-qt's plvk uses. No app API beyond present mode was found.

### Gaps
- No Valve documentation was found on whether the Deck OLED's internal panel does VRR, or on gamescope's HDR/VRR behaviour for external displays.
- GNOME 49/50 HDR status for Vulkan clients (beyond the GTK4 note and the Mutter 50 RC line) was not confirmed. NVIDIA's Wayland HDR10 swapchain exposure was seen only on the Arch Wiki.
- Mesa 26.2's release date and the present-timing feature matrix on NVIDIA proprietary drivers were not confirmed.
